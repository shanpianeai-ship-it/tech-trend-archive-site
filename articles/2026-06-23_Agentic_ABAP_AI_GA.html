Summary

SAP CommunityのSapphire 2026 recapでは、Joule for DevelopersのABAP AI capabilitiesがagentic orchestration、ABAP MCP Server、ADT for VS Code、S/4HANA...

Agentic ABAP AI GAはABAP保守とS/4移行の作業単位を変える

要約

SAP CommunityのSapphire 2026 recapでは、Joule for DevelopersのABAP AI capabilitiesがagentic orchestration、ABAP MCP Server、ADT for VS Code、S/4HANA custom code migration支援へ広がり、2026年6月初旬から一般提供に入ったことが整理されている。

今回のDiscordポールは、該当ポールの poll.results.answer_counts に投票がなかった。そのため、運用ルールの選定基準に沿って候補一覧から6番「Agentic ABAP AI GA」を採用した。理由は、SAP運用・ABAP保守・ECCからS/4HANA移行の実務に直接効き、一次情報がSAP CommunityとSAP公式ページで確認できるため。

結論として、これは「ABAP用のコード補完が賢くなる」話ではない。ABAP開発ツールの外側にあるAI assistant、orchestrator、LLMを、ABAP Language ServerとABAP MCP Server経由でSAP開発作業に接続し、ATC分析、quick fix、AI修正案、transport request、レビューを含む作業フローへ組み込む動きとして見るべき。

背景

SAPはSapphire 2026で、ABAP AIを単独の補助機能からエージェント型の開発支援へ進める方針を示した。発表の中心は、ABAP Language ServerとABAP MCP Serverを土台に、EclipseやVS CodeからGitHub Copilot、Amazon Qなどのagentic assistantへABAP開発能力を開くことにある。

これにより、AIがただコードを生成するだけでなく、ABAP開発環境のツールを呼び出し、ATC結果を読み、修正候補を適用し、必要に応じて開発者へ確認を求める形に近づく。

特に大きいのは、ECCからSAP S/4HANAへのcustom code migrationを対象にしたAgentだ。SAPの別記事では、S/4HANA readinessのATC分析、結果分類、deterministic quick fix、AI-generated fix、transport requestへの記録、最終レビューという流れが説明されている。

何が重要か

ABAP MCP Serverが外部AIエージェントとの接続点になる

従来のABAP AIは、SAPの開発ツール内でコード説明、テスト生成、補完、検索を支援する色が強かった。今回の重要点は、MCP Serverによって、外部のAI assistantやorchestratorがABAP開発ツールの機能を構造化されたツールとして扱えるようになること。

観点従来の見方今回の変化
AIの役割コード補完、説明、検索複数ステップの開発作業を進めるAgent
接続点IDE内の個別AI機能ABAP Language ServerとABAP MCP Server
対象IDE主にEclipse中心Eclipseに加えてVS Codeも一般提供へ
外部連携SAP提供機能中心GitHub Copilot、Amazon Qなどのassistantも視野
実務影響開発者の局所的な時短移行・保守作業の単位を再設計する可能性

SAP側がMCPを採用する意味は大きい。エンタープライズ開発では、AIを単発チャットに閉じ込めるより、権限付きのツール呼び出し、開発環境、テスト、transport、レビューに接続できるかが効いてくる。

Custom Code Migration Agentは移行作業をバッチ処理化する

S/4HANA Custom Code Migration Agentの記事では、ECC由来のカスタムコードをS/4HANA対応へ直す作業を、Agentがある程度まとまった単位で処理する流れが示されている。開発者はパッケージ、ATC variant、対象システム、transport requestなどを指定し、AgentがATC実行、結果整理、quick fix、AI修正案の適用へ進む。

フェーズAgentが支援すること人間が見るべきこと
分析ATCでS/4HANA readinessを確認variant、対象パッケージ、前提Notes
分類findingを複雑度や修正手段で整理業務影響、対象オブジェクトの優先度
修正deterministic quick fixと高信頼AI fixを適用差分レビュー、syntax、回帰リスク
記録同一transport requestに変更を記録変更単位、承認、リリース計画
最終確認進捗と結果を要約activate、最終ATC、テスト、業務検証

ここで重要なのは、Agentが「すべて自動で本番品質にする」わけではないこと。記事ではhuman-in-the-loop、confirmation、review、activation、final ATCが明確に残っている。つまり、移行作業を完全自動化するというより、反復的な分析と修正をまとめて進め、人間を判断とレビューへ寄せる設計に近い。

Basis/運用者にも関係する

一見すると開発者向けの話だが、Basis/ERP運用者にも関係がある。AI AgentがABAP開発環境、BTP上のhub service、Cloud Identity Services、AI Unit消費、外部AI assistant、transport requestへまたがるため、導入時の確認項目は開発チームだけでは閉じない。

領域確認ポイント
権限Joule for Developers、Cloud Identity Services、ADT、対象ABAP systemの権限
接続BTP hub service、AI Core、IDE、MCP host、ローカルMCP server
ライセンスAI Units、Joule for Developersの割当、外部assistantのライセンス
監査Agentが実行したATC、quick fix、AI fix、transportへの記録
変更管理Agent適用差分を通常のtransport、レビュー、テストにどう載せるか
セキュリティMCP token、ローカルserver、外部assistantへ渡るコンテキスト範囲

特にMCP Serverは、AI assistantに開発ツールを操作させる入口になる。便利な一方で、誰が、どのシステムに、どの権限で、どのツールを呼べるかを明確にしないと、AI導入後の監査説明が弱くなる。

「Clean Core」と移行プロジェクトの作業設計に効く

S/4HANA移行では、カスタムコードの棚卸し、ATC対応、簡素化項目への追随、Clean Core化、Fiori化が重い。今回のAgentic ABAP AIは、この重い部分をAIで薄くするというより、作業の分解方法を変える。

まずAgentに広い範囲を処理させ、決定論的に直せるものを先に片付け、高信頼のAI修正を適用し、曖昧なものや低信頼のものを人間レビューへ残す。これは移行プロジェクトの工数見積り、レビュー体制、transport分割、テスト計画に影響する。

自分向けには、S/4HANA移行案件で次の順に見るとよさそう。

  • Agentが対応できるATC findingの種類を先に確認する。
  • deterministic quick fixとAI fixを分けてレビュー基準を作る。
  • Agent用transport requestをどう切るか決める。
  • 低信頼AI fixをコメント提案として残す運用をレビュー手順に入れる。
  • 最終ATC、単体テスト、業務シナリオテストは従来どおり必須にする。

自分向けメモ

  • ABAP MCP Serverは、SAP開発における「AIエージェント用ツール口」になる。MCP host、token、権限、監査の設計をセットで見る。
  • Custom Code Migration Agentは、ECCからS/4HANA移行のATC対応をバッチ的に進める材料。完全自動化ではなく、反復作業をAgentへ寄せ、人間はレビューと業務判断へ寄せる。
  • 導入前に、AI Units、Joule for Developers entitlement、Cloud Identity Services、BTP hub service、外部assistantライセンスを確認する。
  • SAP Basis目線では、MCP serverを有効化する端末、接続先ABAP system、transport request、ログ、token管理を運用手順化したい。
  • 公開ブログでは「ABAP開発のAI化」より「S/4HANA移行の作業設計がAgent前提に変わる」と書くと実務寄りに伝わる。
