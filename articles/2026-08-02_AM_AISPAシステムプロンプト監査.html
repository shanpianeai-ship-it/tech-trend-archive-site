2026-08-02 AI / LLM / Agent importance: high
Summary

AISPAは商用AI製品のシステムプロンプトを、ユーザー保護と問題指示の両面から監査する枠組み。AIアプリの透明性、監査、調達評価を考える材料になる。

AISPAシステムプロンプト監査

要約

arXivに投稿された「AISPA: User-Centric System Prompt Auditing for Large Language Model Applications」は、商用AI製品のシステムプロンプトをユーザー視点で監査するための枠組みを提案している。AISPAはArtificial Intelligence System Prompt Assuranceの略で、システムプロンプト内の指示をユーザー保護に資するものと、ユーザー利益に反し得るものに分類し、8つの観点で評価する。

論文では、88の商用AI製品から3,249件のシステムプロンプト指示を集めて分析している。結果として、98.9%の製品には少なくとも1つの保護的指示がある一方、AISPAの8分類すべてをカバーする製品は24%にとどまる。また、約40%の製品にはユーザー利益に反し得る問題指示が少なくとも1つ含まれており、保護的指示と問題指示が同じプロンプト内に共存している例も多い。

ポイントは、システムプロンプトを単なる内部実装やプロンプト職人芸ではなく、製品仕様、統制、監査対象として扱っていることだ。企業がAIアプリを調達・導入するときに、「モデルが何を守るよう設計されているか」「誰の利益を優先しているか」「外部監査に耐えるか」を問うための語彙として使える。

背景

システムプロンプトは、AIアプリの振る舞いを決める開発者側の指示であり、モデル本体、RAG、ツール、UIと並ぶ重要な制御層になっている。ところが多くの商用AI製品では、システムプロンプトは公開されず、ユーザーや規制当局が中身を確認できない。

この非公開性は、AIサービスを利用する側にとって厄介だ。AIが「安全に配慮している」と説明されても、その安全がユーザー保護なのか、ベンダー責任回避なのか、広告・課金・データ収集上の都合なのかは見えにくい。モデルカードやプライバシーポリシーだけでは、実際の会話や操作でどのような指示が優先されるかまでは追い切れない。

AISPAはここに監査フレームワークを置く。論文は、システムプロンプトを「AI製品がユーザーと結ぶ暗黙の運用契約」として読み、そこにユーザーにとって重要な保護が入っているか、逆にユーザー利益を損ねる指示がないかを分類する。

何が重要か

システムプロンプトが監査対象になる

AISPAが実務的に面白いのは、プロンプトを品質保証や内部統制の対象として扱う点だ。従来のAI評価は、出力の正確性、毒性、ハルシネーション、ベンチマークスコアに寄りがちだった。AISPAはそれより上流の「製品側がAIに何を命じているか」を見る。

観点従来の見方AISPA的な見方
評価対象モデル出力やベンチマーク結果システムプロンプト内の指示
主な問い正しい答えを返すかユーザー保護を明示しているか
リスク誤回答、危険出力、漏えいベンダー都合の優先、透明性不足、保護範囲の偏り
実務用途モデル選定、品質評価調達、監査、AIガバナンス、契約確認

これはAIエージェントや業務AIの導入時に効く。社内データ、顧客情報、購買、財務、開発環境などにAIが入ると、出力品質だけでなく、AIがどの利益を優先する設計かが問題になる。システムプロンプト監査は、その確認項目を作る入口になる。

保護的指示は普及しているが浅い

論文の数字で重要なのは、保護的指示が「あるかないか」だけでは不十分という点だ。98.9%の製品に少なくとも1つの保護的指示があるなら、表面的には多くの製品が安全配慮をしているように見える。しかし、8分類すべてをカバーしている製品は24%にとどまる。

つまり、AI製品の安全指示は広く導入されているが、体系的ではない可能性がある。ある製品はプライバシーに厚く、別の製品は有害コンテンツ回避に厚いが、ユーザーの自律性、透明性、データ利用、責任ある拒否などは抜けるかもしれない。

実務では「安全対策あり」という宣言ではなく、どの保護領域をカバーしているかを見る必要がある。これはセキュリティのチェックリストと同じで、1つの対策があることより、重要なリスク領域に穴がないことのほうが大事だ。

問題指示が混在することを前提に見る

約40%の製品にユーザー利益に反し得る問題指示があるという指摘も重い。論文の要旨では、保護的指示と問題指示が同じシステムプロンプト内に共存することが強調されている。

これは現実的には自然でもある。AI製品は、ユーザー保護、ベンダー保護、法務、マーケティング、収益化、負荷削減、ブランド維持など複数の目的を同時に背負う。その結果、ある指示はユーザーの安全を守り、別の指示はユーザーにとって不透明な制限や誘導になる。

調達や社内導入で見るべきなのは、ベンダーが「安全です」と言うかどうかではなく、次のような問いになる。

確認項目見る理由
ユーザー保護の指示範囲何を守る設計かを確認する
ベンダー利益を優先する指示ユーザー判断を歪める可能性を見る
透明性の扱いAIが制約や不確実性を説明するかを見る
データ利用の境界入力や会話がどう扱われるかを見る
外部監査可能性契約・規制・内部統制に載せられるかを見る

AIアプリの調達質問に落とせる

AISPAは論文としては研究色があるが、すぐ使えるのは調達・リスク評価の質問項目だ。商用AI製品や業務AIエージェントを導入するとき、モデル名やSOC2、ISO、DPAだけでなく、システムプロンプト運用について聞くべきことが増える。

例としては、「システムプロンプトは内部監査されていますか」「ユーザー保護指示の分類体系はありますか」「プロンプト更新時の変更管理はありますか」「顧客に説明できる範囲はどこまでですか」「問題指示を検出・除去するレビューがありますか」といった質問になる。

全部のシステムプロンプトを公開させるのは現実的でないとしても、監査済み分類、更新履歴、外部評価、ユーザー保護ポリシーとの対応表を要求する流れはあり得る。

自分向けメモ

  • AI製品のシステムプロンプトは、もはや「中の人のプロンプト」ではなく、製品仕様・運用統制・監査証跡として扱うべき。
  • 「安全指示がある」だけでは弱い。どのユーザー保護領域をカバーしていて、どこが抜けているかを見る。
  • 問題指示は悪意だけでなく、ベンダー法務、広告、負荷制御、ブランド保護などから自然に混ざる。だから第三者監査が必要になる。
  • 業務AI、特にSAP/ERP/CRM連携エージェントでは、システムプロンプト監査を権限設計、監査ログ、データ利用契約とセットで考える。
  • 自分のOpenClaw/Codex運用でも、常駐指示やスキルは「人格」だけでなく統制面を持つ。外部送信、ファイル操作、承認境界の指示は定期的に棚卸しする。
