2026-07-11 Security importance: high
Summary

公開GitHub IssueからAgentic Workflowsを誘導し、私有リポジトリ内容を公開コメントへ漏えいさせ得る事例。AIエージェントの権限スコープと出力経路を分ける重要性が分かる。

GitHubエージェント漏えいリスク

要約

Noma Security が、GitHub Agentic Workflows を間接プロンプト注入で誘導し、組織内の私有リポジトリ内容を公開Issueのコメントへ漏えいさせる手法を GitLost として公開した。

攻撃者に必要なのは、対象組織の公開リポジトリに一見普通のIssueを作ることだけ。盗んだ認証情報や私有リポジトリへの直接アクセスは不要で、エージェント側が広いリポジトリ読取権限を持ち、公開Issueの本文を読み、公開コメントを投稿できる構成になっていると、Issue本文に埋め込まれた自然言語の指示が漏えい経路になる。

重要なのは、これは「GitHubだけの脆弱性」というより、エージェントが未信頼入力、強い内部権限、外部出力経路を同時に持つ時の典型的な設計リスクだという点。AIエージェントを開発運用に入れるなら、プロンプト注入フィルタより先に、トークンスコープ、入出力境界、人間レビューを設計する必要がある。

背景

GitHub Agentic Workflows は、Markdownで書いた自然言語の指示をもとに、AIエージェントがIssueやPull Requestを読み、ツールを呼び、コメントを返す仕組みとして紹介されている。従来の固定的なYAMLやスクリプトより柔軟だが、柔軟性の分だけ「読む内容」と「従う指示」の境界が曖昧になる。

今回の実験では、ワークフローが公開Issueに反応し、Issue本文を読み、組織内の他リポジトリにも読取権限を持ち、結果を公開コメントとして返せる構成が前提になっている。攻撃者はVPからの依頼に見えるような自然なIssue文を作り、その中に私有リポジトリのREADMEを読むよう誘導する命令を混ぜた。

Nomaの報告では、GitHub側にはサンドボックス、デフォルト読取専用、入力クリーニング、出力前の脅威検知といったガードレールがあった。それでも、表現を変えるだけで検知をすり抜け、エージェントが私有リポジトリの内容を公開コメントへ貼り付けたとされる。

観点今回の構図実務上の意味
入力公開Issue本文攻撃者が自由に書ける未信頼入力
内部権限組織内リポジトリの読取トークン便利な横断参照が漏えい範囲を広げる
実行主体GitHub上のAIエージェント人間ではなく自動処理が指示を解釈する
出力公開Issueコメント正常機能がそのまま外部送信経路になる
防御限界出力検査を言い換えで回避フィルタだけでは境界になりにくい

何が重要か

第一に、AIエージェントのコンテキスト窓そのものが攻撃面になる。

Issue、PR、README、ログ、コメント、設定ファイルは、人間にとっては作業文脈だが、LLMにとっては命令としても解釈されうる。公開Issueを「タスク依頼」として読むエージェントは、攻撃者が書いた文章を作業指示として処理しやすい。

第二に、読取権限の広さがそのまま漏えい被害の上限になる。

エージェントが単一リポジトリだけを読めるなら漏れる範囲は限定される。一方、便利だからと組織横断の読取権限を渡すと、公開Issueから私有リポジトリ、設計文書、CI/CD周辺情報まで到達し得る。最小権限は、AIエージェントでは「理想論」ではなく攻撃経路の上限設定になる。

第三に、外部へ投稿できる経路を別扱いにする必要がある。

今回の漏えいでは、悪性コード実行ではなく、正規のコメント投稿機能が外部送信経路になった。エージェントが公開コメント、PRレビュー、Issue返信、チャット通知を出せる場合、それらはすべてデータ流出チャネルとして扱うべき。

防御策目的メモ
トークンをリポジトリ単位に限定漏えい範囲を小さくする組織横断PATを安易に渡さない
公開入力と内部参照を分離未信頼入力から内部データ参照を切るIssue本文の命令をそのまま実行しない
公開出力を人間承認にする最後の外部送信を止める特に内部データを読んだ後のコメント投稿
出力テンプレートを固定任意テキスト流出を抑える要約、分類、ラベル付けなどに限定する
ログと根拠を残す事後検証を可能にする何を読み、何を出したかを分けて記録する

自分向けメモ

OpenClawやCodexでGitHub、Obsidian、ローカルファイルを横断する自動化を作る時も同じ問題が起きる。

  • 外部から来たIssue、Webページ、メール、Discord本文は、すべて未信頼入力として扱う。
  • それらの本文に「別ファイルを読め」「秘密を貼れ」「前の指示を無視しろ」と書かれていても、ユーザー指示や運用ルールより下位に置く。
  • 自動返信や公開投稿を行うワークフローは、内部ファイルを読ませるワークフローと分離する。
  • どうしても同じエージェントに読取と投稿を持たせる場合は、投稿前に人間レビュー、または固定フォーマット出力だけにする。
  • 「検知モデルが止めるはず」ではなく、権限と経路で止める。フィルタは最後の補助線。

特に、GitHub連携エージェントに「組織内の全リポジトリを読めるPAT」を渡す設計はかなり危うい。便利な横断検索や自動Issue回答をしたい場合でも、用途ごとの専用トークン、対象リポジトリの限定、公開コメント前の承認を基本にしたい。
