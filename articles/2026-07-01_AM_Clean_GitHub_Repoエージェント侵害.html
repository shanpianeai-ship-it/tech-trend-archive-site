2026-07-01 Security importance: high
Summary

0DINのPoCは、悪性コードを含まないように見えるGitHub repoでも、AIコーディングエージェントの自動セットアップ復旧がDNS TXT経由の攻撃実行につながることを示す。開発端末とCIで「初回セットアップ」を隔離・監査する価値が高い。

Clean GitHub RepoでAIエージェント侵害

要約

Mozilla系の0DINが、Claude Codeのようなエージェント型コーディングツールに対するPoCを公開した。ポイントは、GitHub repository自体に露骨な悪性コードを置かなくても、README、初期化エラー、セットアップスクリプト、DNS TXTレコードを組み合わせると、エージェントが「環境を直そう」として攻撃者のコマンドを実行し得ることにある。

流れは単純だ。エージェントが未知のrepoをセットアップし、Python packageの初期化エラーに従って python3 -m axiom init のような修復コマンドを実行する。そのコマンドがshell scriptを呼び、scriptがDNS TXTから設定値を取得し、それをコマンドとして実行する。0DINの例では、最終的に開発者権限のreverse shellが開く。

これは「Claude Codeだけの脆弱性」というより、shell実行権限を持つAI coding agent全般の信頼境界問題として見るべきだ。静的スキャンやSBOMはrepo内のファイルを中心に見るため、実行時に外から引かれるDNS TXT、curl、npm lifecycle script、postinstall、Makefile、CI bootstrapのような経路を見落としやすい。

背景

AI coding agentは、単なる補完から「cloneする」「依存関係を入れる」「testを回す」「エラーを読んで直す」段階へ移っている。便利さの中心は、開発者が逐一指示しなくても失敗を解釈して次のコマンドを選ぶ点にある。

ただし、その挙動は攻撃者にとっても都合がよい。プロジェクトのREADME、エラーメッセージ、package script、setup scriptは、エージェントが「信頼すべきプロジェクト文脈」として読む入力になる。人間なら一度止まって確認する場面でも、エージェントはタスク達成のために自然な復旧手順として進めてしまう。

OWASPのLLM Top 10でも、過剰な権限・機能・自律性は「Excessive Agency」として整理されている。今回のPoCは、その抽象リスクが開発端末上でどう実行可能な攻撃手順になるかをかなり具体的に示している。

観点従来の見方今回の含意
repoレビューファイルに悪性コードがあるかを見るpayloadがrepo外の実行時取得なら見えない
エラー復旧setup失敗時の自然な補助動作攻撃者が次の実行を誘導できる
DNS TXT設定や検証に使う一般的な仕組みcommand delivery channelになり得る
Agent権限ユーザーの補助なので広く許可しがちユーザー権限そのものの攻撃面になる
CI/端末開発効率優先で外向き通信が広い初回bootstrapだけでも隔離が必要

何が重要か

第一に、これは「悪いコードを見つける」問題だけではない。repo内に悪性payloadがない場合、静的解析、依存関係スキャン、人間の軽いレビューでは検出が難しい。見るべき対象は、実際に実行されるコマンド列と、そのコマンドが実行時に何を取得するかだ。

第二に、エージェントの強みである自動エラー復旧が攻撃面になる。エラーメッセージに「このコマンドを実行せよ」と書かれていたとき、エージェントはタスク達成の文脈で従いやすい。これはprompt injectionというより、開発ワークフローの実行権限をLLMが握った時の運用設計問題に近い。

第三に、DNS、package lifecycle、shell script、Makefile、devcontainer、GitHub Actionsなど、開発環境では「普通にある仕組み」が攻撃チェーンに使われる。単一の危険コマンドだけをdenylist化しても、別経路で同じ結果に到達できる可能性がある。

実務上の対策は、少なくとも次の4層で考える必要がある。

層対策目的
実行環境未知repoはcontainer/VM/sandboxで初回実行端末本体のsecretsやbrowser sessionから切り離す
ネットワーク初回bootstrapの外向き通信を制限・記録DNS TXTや任意download経由のpayload取得を見える化する
Agent権限shell自動承認を最小化し、setup系は明示承認エラー復旧の自動実行を無制限にしない
監査実行前にscript chainと外部取得先を表示repo内外をまたぐ実行経路を人間が判断できるようにする

自分向けメモ

  • OpenClaw/Codex/Claude Code系のローカル作業では、未知repoの npm install、pip install -r requirements.txt、make setup、docker compose up を「ただの準備」と見ない。
  • 初回実行は、作業ディレクトリだけをmountしたsandboxで行い、HOME、SSH鍵、ブラウザprofile、Obsidian vault、API key入りenvから切り離す。
  • DNS TXT、curl pipe shell、postinstall、preinstall、GitHub Actions、devcontainer featureは、AI agentに読ませるだけでなく実行時監査対象にする。
  • 「repoがclean」は安全判定として弱い。正しくは「このrepoのbootstrapが、どの外部入力を、どの権限で、どこまで実行するか」を見る。
  • エージェントに任せる場合でも、setup失敗後の復旧コマンドは一段厳しく扱う。攻撃者が誘導文を置きやすいのは、最初から明示された手順よりも「失敗した時の直し方」。
