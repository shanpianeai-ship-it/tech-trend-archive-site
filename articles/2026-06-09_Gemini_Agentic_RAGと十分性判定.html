Gemini Agentic RAGと十分性判定

要約

Google Research / Google Cloud が、Gemini Enterprise Agent Platform 上の Cross-Corpus Retrieval powered by Agentic RAG を紹介した。従来の単発検索型RAGではなく、Planner、Query Rewriter、Search Fanout、Sufficient Context Agent、Synthesis Agent のように役割を分け、複数コーパスをまたいで検索計画、追加検索、根拠十分性の判定を繰り返す設計。

自分向けには、「企業RAGの品質」は検索ランキングだけでなく、どの情報源を選ぶか、足りない根拠を検知できるか、根拠が揃うまで探索を続けられるかに移っている、という話として重要。SAPや社内ナレッジ検索でも、業務データが複数システムに分かれている前提にかなり近い。

背景

企業内の質問は、1つの文書検索だけで完結しないことが多い。たとえば「Project Xで使われたサーバの仕様」を聞く場合、プロジェクト資料にはサーバIDしかなく、別の構成管理DBや資産台帳をもう一度引く必要がある。

Googleの説明では、今回のAgentic RAGはこのような multi-source / multi-hop の業務質問を想定している。Root Agent が依頼を分解し、Planner Agent がどのコーパスを見に行くかを決め、Query Rewriter が検索しやすい質問へ分解し、RAG Agent が検索する。

そこで止まらない点が特徴。Sufficient Context Agent が、取得したスニペット、途中ドラフト、元の質問を比べて「回答に十分な根拠があるか」を確認する。不足があれば、何が足りないかをフィードバックし、追加検索を回す。

何が重要か

RAGの失敗を「検索漏れ」として検知する

従来のRAGでは、最初の検索で足りない情報を拾えないと、曖昧な回答、部分回答、または「情報がありません」で終わりやすい。今回の設計は、そこを品質管理ポイントとして明示している。

観点単発RAGAgentic RAG
検索単位1回の検索中心計画、分解、再検索を含む
情報源事前指定や単一コーパス寄り複数コーパスから選択
不足検知生成時の曖昧さに埋もれやすいSufficient Context Agent が不足を判定
監査性どこで足りなかったか見えにくい不足理由と追加検索のログを残しやすい

これはエージェントの「賢さ」というより、業務上の回答品質を運用できる形に分解している点が大きい。

コーパス説明がルーティング品質を左右する

Google Cloud の Cross Corpus Retrieval ドキュメントでは、RAG corpus 作成時の description が重要で、作成後に編集できないと明記されている。Planning Agent はコーパス説明を見て、質問のどの部分をどのコーパスへ投げるかを決める。

設計項目実務上の意味
corpus description「このコーパスに何が入っているか」をAIが判断する台帳
corpus boundary業務、部門、システム、データ分類の境界設計
routing plan全検索ではなく、必要な情報源へ絞るための計画
SCA feedback不足情報を再検索させるための制御信号

社内RAGでは、データ投入よりも先に「コーパスをどう分け、どう説明するか」を設計しないと、Agentic Retrieval の利点が出にくい。

SAP/ERP文脈ではかなり現実的な問題

SAP周辺では、業務質問の答えが1つの場所にない。伝票、品目、BP、ワークフロー、ジョブログ、監査証跡、運用手順、外部連携ログが分かれている。

業務質問例必要になりそうな情報源
受注遅延の原因は何かSD伝票、在庫、配送、外部倉庫連携、ジョブログ
月次締めで止まった処理は何かFI/COジョブ、エラー一覧、運用手順、担当者メモ
この取引先の与信判断は妥当かBPマスタ、与信、過去入金、承認履歴、社内規程
この変更は監査上説明できるか変更管理、Transport、承認、実機ログ、設計書

単純な文書検索では、この種の質問に対して「それっぽい断片」は出せても、根拠の揃った回答にしにくい。Agentic RAGのポイントは、複数システムをまたぐ前提をRAG側の設計に入れていること。

数字は有望だが、評価方法は見る必要がある

Google Research は、FramesQA を使った評価で、標準RAGに対して最大34%の精度改善、cross-corpus設定でも90.1%の正答率を示したとしている。cross-corpusでもsingle-corpusとほぼ同等の精度に近づき、レイテンシも平均3%以内の差と説明されている。

ただし、これはベンチマーク上の結果で、実企業データではコーパス説明、アクセス権、古い文書、重複、機密情報、監査要件が絡む。特に医療・ERP・セキュリティ運用では、正答率だけでなく、根拠提示、否定回答、権限境界、ログ保存を合わせて評価する必要がある。

自分向けメモ

  • 社内RAGを作る時は、まず「検索対象」ではなく「コーパス境界」と「説明文」を設計する。
  • RAG評価では、最終回答の正誤だけでなく、足りない情報を足りないと言えたか、追加検索へ回せたかを見る。
  • SAP運用に接続するなら、業務データ、運用手順、ログ、監査証跡を別コーパスにし、質問分解でどこを引くべきかを明示する。
  • Agentic RAGは便利な反面、検索回数、権限、レイテンシ、コストが増える。全質問に使うのではなく、複数情報源が必要な質問に限定する設計がよさそう。
  • Sufficient Context Agent 相当の判定は、OpenClaw/Codexの調査系Cronにも応用できる。ノート作成時に「根拠が足りない項目」を明示させると品質が上がる。
