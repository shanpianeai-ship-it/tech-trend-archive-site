2026-07-03 AI / LLM / Agent importance: high
Summary

ScarfBenchは、AIエージェントがSpring、Jakarta EE、Quarkus間の企業Java移行をどこまで実行できるか測るベンチマーク。ビルド成功だけでは移行品質を判断できない点が実務上重要。

ScarfBench企業Java移行評価

要約

IBM Researchが公開したScarfBenchは、AI coding agentに企業Javaのフレームワーク移行を任せたとき、単にコードが生成できるかではなく、ビルド、デプロイ、振る舞い維持まで通るかを評価するベンチマークである。

対象はSpring、Jakarta EE、Quarkusの3系統。34個のアプリケーションファミリから102個のフレームワーク別実装を作り、204個の移行タスクとして評価する。評価には1,331件の専門家作成テストとコンテナ化された実行ハーネスが使われる。

重要なのは、現在の強いAIエージェントでも結果がかなり厳しいこと。論文要旨では、最良のエージェントでもfocused-layer移行の集計テスト通過率は15.3%、whole-application移行は12.2%にとどまり、204タスク中で完全に振る舞い等価な移行は1件だけだったとされている。

背景

企業Javaのモダナイズは、Javaバージョン更新よりも難しいことが多い。SpringからJakarta EE、Jakarta EEからQuarkusのような移行では、アノテーション置換だけでなく、依存性注入、永続化設定、クエリ、HTTP層、ビルド設定、デプロイ記述子まで同時に変わる。

AI coding agentは、こうした横断的な修正を高速に試行できるため、移行案件で期待されやすい。一方で、生成コードがコンパイルできても、アプリケーションが起動しない、起動しても振る舞いが違う、テスト観点が抜ける、という問題は残る。

ScarfBenchはこのズレを測るために、以下のような実務寄りの評価にしている。

観点ScarfBenchでの扱い実務上の意味
対象Spring / Jakarta EE / Quarkus企業Javaで実際に出やすい移行先
規模34アプリ、102実装、204移行タスク小さな関数変換ではなくアプリ単位
判定build / deploy / behavioral testsコンパイル成功だけで合格にしない
テスト1,331件の専門家作成テスト仕様保持をテストで確認する
出力ベンチマーク、ハーネス、トレースツール比較と失敗分析に使える

何が重要か

1. 「移行できた」の定義を厳しくしている

多くのコード生成評価は、正解コードとの類似度、単体テスト通過、ビルド成功に寄りがちである。ScarfBenchは、移行後アプリが対象ランタイムでデプロイでき、外部から見える振る舞いを保つかまで見る。

これはSAP周辺や基幹系Javaの移行判断にも近い。実務では「ビルドが通った」は中間地点であり、業務機能、運用設定、性能、監視、障害時挙動が保たれて初めて移行候補になる。

2. 現時点のエージェント性能に冷静な線を引いている

論文要旨では、最良のエージェントでも集計テスト通過率は限定的で、完全成功は204タスク中1件だけとされる。これは「AIでJava移行を丸投げできる」という話ではなく、「AIに任せられる部分と、人間が設計・検証すべき部分を分ける必要がある」という結果に見える。

特にJakarta EEを移行先にするタスクは難度が高いとされており、アプリケーションサーバ、仕様準拠、設定ファイル、ランタイム差分を含む移行は、一般的なコード補完能力だけでは足りない。

3. AIエージェント導入時の評価軸として使いやすい

企業がAI coding agentを採用する場合、通常のLeetCode型ベンチや小規模バグ修正ベンチだけでは、基幹システム保守への適性を測りにくい。ScarfBenchのような評価は、次のような調達・PoC観点に落とし込める。

  • 自社の移行対象に近い技術スタックで評価する
  • ビルド成功率ではなく、業務テスト通過率を見る
  • 失敗トレースを残し、どの層で壊れたか分類する
  • AIにコード変更だけでなく、検証計画とロールバック案も出させる
  • 人間レビューの重点を、設定、永続化、トランザクション境界、起動時挙動に置く

自分向けメモ

  • SAP/Basis視点では、これは「AIがABAPやJava移行を全部やる」話ではなく、「移行作業をテスト可能な小単位に分け、AIの失敗を測るための型」として読むのがよい。
  • Java基幹システムのモダナイズでは、AI agentにいきなり全体移行を任せるより、DI層、永続化層、REST層、設定ファイルなどに分けた評価ハーネスを先に作るべき。
  • 「コンパイル成功」「デプロイ成功」「振る舞い維持」を別メトリクスにする考え方は、SAP移行や周辺Javaアプリの更改にも使える。
  • 将来、社内移行PoCを作るなら、ScarfBench型に近い最小アプリ群とテストを作り、複数エージェントを同じ条件で比較するのが現実的。
  • エージェントの価値は、完全自動化よりも、移行差分の初稿作成、失敗ログの分類、テスト不足箇所の指摘、移行プレイブック作成に出やすい。
