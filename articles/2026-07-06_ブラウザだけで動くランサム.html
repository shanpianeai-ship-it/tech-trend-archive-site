2026-07-06 Security importance: high
Summary

Check Point Researchのブラウザ単体ランサムPoCは、File System Access APIとAI生成コードが結びつく攻撃面を示す。Android Chromeの写真フォルダ権限をどう扱うべきかを考える材料になる。

ブラウザだけで動くランサム

要約

Check Point Researchは、LLMが生成した不完全な悪性サンプルを起点に、ブラウザだけで成立し得るランサムウェア手法を分析した。中心にあるのはFile System Access APIで、ユーザーがWebページへフォルダアクセスを許可すると、ページ側が選択フォルダ内のファイルを列挙、読み取り、書き換えできる。

今回の重要点は、ブラウザの脆弱性を突く話ではないこと。APKのインストール、ネイティブペイロード、root権限、ブラウザエクスプロイトなしに、正規の権限プロンプトとソーシャルエンジニアリングだけで攻撃フローが組める。特にAndroid Chromeでは写真ディレクトリが自然な誘導先になり、AI画像補正やアバター高画質化のような画面なら、ユーザーがフォルダ編集権限を合理化しやすい。

もう一つの論点は、LLMの「幻覚」が防御側にとっても無視できないこと。不完全なマルウェア風コードでも、モデルが悪意ある目的を既存APIに接続すると、理論上のリスクが実装可能なPoCへ近づく。AI悪用対策は、既知マルウェアの再生成だけでなく、正規APIの危険な組み合わせをどう早く検出するかに寄っていく。

背景

File System Access APIは、Web版エディタ、IDE、画像処理ツールのようなアプリが、ユーザーの許可を得てローカルファイルを扱うための正規機能。MDNも、File System APIとFile System Access API拡張により、端末上のファイルに対する読み取り、書き込み、管理機能が提供されると説明している。

便利な一方で、このAPIはブラウザのサンドボックスとローカルファイルの境界をユーザー許可でまたぐ。Check Point Researchが見つけたDeepSeek由来とされるサンプルは、DiscordアバターAIアップスケーラーを装い、ブラウザ内でファイルアクセス、情報収集、ランサム風表示を組み合わせようとしていた。

多くの機能はブラウザ制約で破綻していた。通常のWebページはOS全体のスクリーンショット、任意のキーログ、他オリジンのトークン窃取、永続化を自由には実行できない。ただし、ファイルアクセス部分だけは実在するAPIに接続されており、攻撃として具体性があった。

何が重要か

1. ブラウザが実行環境になる

従来のランサムウェア防御は、実行ファイル、スクリプト、アプリインストール、権限昇格、脆弱性悪用を主な観測点にする。今回のPoCは、その前提をずらす。

観点従来の見方今回の見方
実行場所端末上のバイナリやスクリプトブラウザ内のWebページ
権限取得脆弱性、マルウェア実行、OS権限正規のフォルダアクセス許可
誘導添付ファイル、偽アプリ、更新通知AI画像補正、アバター加工、Webツール
防御の盲点未知バイナリ、難読化正規APIと自然な許可プロンプト

ブラウザフォルダアクセスの許可は、ユーザーにとって「アプリを実行する」ほど重く見えない。ここが攻撃側の余地になる。

2. Androidでは写真フォルダの価値が高い

Check Point Researchは、Android ChromeでFile System Access APIを使い、写真ディレクトリを対象にしたPoCを検証している。Chrome 132でAndroidとWebViewにFile System Accessのサポートが広がり、同社の検証時点ではChrome 148でもDCIMフォルダのルート選択が可能だったという。

写真フォルダは単なる画像置き場ではない。スマホでは、身分証、銀行画面、医療情報、復旧コード、旅行書類、業務写真、家族写真などが混ざる。暗号化だけでなく、読み取りと持ち出しが組み合わさると、恐喝、公開脅迫、なりすまし、業務情報漏えいに発展し得る。

環境攻撃面リスクの質
Android Chrome写真・動画ディレクトリへのWebページ権限個人情報、復旧情報、業務写真の暗号化や流出
Windows ChromePicturesなど選択可能フォルダ個人ファイルの破壊、Webツール経由の持ち出し
iOS Safari / Chrome on iOS同等のFile System Access APIは未実装現時点では同じPoCの成立性は低い

全ディスクを自由に暗号化できるわけではないが、スマホの写真ライブラリだけでも十分に高価値な標的になる。

3. LLMは既存APIを攻撃目的へ接続する

Check Point Researchの観察で面白いのは、最初のサンプルが「完成度の高いマルウェア」ではなかった点。不完全でノイズの多いコードだったが、モデルは不可能なWebマルウェア要求を満たそうとする過程で、File System Access APIという実在の機能へ到達していた。

これはAI悪用の見方を少し変える。問題は、LLMが既存マルウェアを再実装することだけではない。攻撃者が知らないAPIや設計上の注意点を、モデルが自然言語の目的から探索し、攻撃フローに組み込む可能性がある。

LLM悪用の段階防御側の見方
既存コードの生成既知TTP、既知マルウェア分類で追いやすい
部品ごとの生成UI、ファイル処理、暗号化、通知を別々に生成される
API接続の発見正規機能が悪用フローへ組み込まれる
使い捨て化サンプルごとの特徴がばらけ、シグネチャ依存が弱くなる

モデルの出力が技術的に間違っていても、その間違いが「どの正規機能を悪用し得るか」を示すことがある。

自分向けメモ

  • ブラウザの「フォルダ内のファイルを編集できます」系プロンプトは、アプリインストールに近い重さのセキュリティ判断として扱う。
  • AI画像補正、PDF変換、音声変換、開発支援など、ローカルファイル処理が自然に見えるWebツールほど警戒する。
  • AndroidではDCIM、Pictures、VideosをWebページへ渡さない。試す場合は空の一時フォルダを作る。
  • 企業端末では、Chromium系ブラウザのFile System Access API制御、DLP、ブラウザ権限ログ、拡張管理ポリシーを確認する。
  • AI安全評価では「マルウェアを作れるか」だけでなく、「正規APIを危険な組み合わせへ接続するか」をテスト観点に入れる。
