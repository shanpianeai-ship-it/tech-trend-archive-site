AI開発環境サプライチェーン攻撃

要約

Cordyceps、Miasma、IronWorm は、AI開発環境がサプライチェーン攻撃の主戦場になりつつあることを示す一連の事例。

Cordyceps は、GitHub Actions などの CI/CD ワークフローで、未信頼の Pull Request、コメント、ブランチ名、成果物が高権限ワークフローへ渡る構成ミスを悪用する攻撃パターン。Novee は約3万の高影響リポジトリを調査し、654件をフラグし、300件超を完全に悪用可能と確認したとしている。

Miasma と IronWorm は npm エコシステム経由の自己増殖型サプライチェーン攻撃で、Claude Code、Cursor、Gemini CLI、VS Code などの設定ディレクトリや AI API キーを明示的に狙っている。つまり、AIコーディングツールは単なる開発補助ではなく、認証情報、実行フック、CI/CD、クラウド権限へつながる攻撃面として扱う必要がある。

背景

従来の開発環境リスクは、npm パッケージ、GitHub Actions、クラウド認証情報、CI/CD シークレット、IDE 設定を別々に見がちだった。しかし AI コーディングツールが普及すると、これらが同じ作業フローに束ねられる。

開発者は AI API キーを .env、shell profile、ツール設定、CI 変数に置き、AIツールはリポジトリ内のルール、hooks、tasks、設定ファイルを読み込む。さらに、エージェント型ツールはコマンド実行、ファイル編集、テスト実行、Git操作まで担う。

このため攻撃者から見ると、AI開発環境は次のような複合的な侵入口になる。

層従来の見方いま問題になること
npm / package依存ライブラリの侵害install 時に AI ツール設定や CI 認証情報まで狙う
CI/CDビルド設定PR、コメント、artifact 経由で高権限ワークフローへ昇格する
AIツール設定個人の補助設定hooks、rules、tasks が永続的な実行面になる
APIキーモデル利用の認証情報盗まれると費用、データ、接続先システムへ影響する
エージェント操作開発効率化侵害済み設定を読んで、攻撃者の意図どおりに作業する可能性がある

何が重要か

1. CI/CD YAML は設定ではなくコードとして扱う必要がある

Cordyceps のポイントは、GitHub Actions の単一行の危険パターンだけではなく、複数ワークフローをまたぐ信頼境界の破綻にある。

たとえば、低権限の PR ワークフローで生成された成果物が、高権限の release workflow でそのまま使われる。PR コメントやブランチ名が shell や github-script に渡る。外部貢献者の入力が、メンテナ権限の token や cloud role と同じ実行文脈に入る。

これはアプリケーションコードなら command injection や権限昇格として扱われる。しかし CI/CD YAML では「設定」と見なされ、レビューもスキャンも甘くなりやすい。

2. AIツール設定ディレクトリが信頼境界になった

CSA の整理では、Miasma は .claude/、.cursor/、.gemini/、.vscode/ などに永続的な実行ファイルや設定を仕込む。Claude Code の SessionStart hooks、Cursor の常時適用ルール、VS Code の folder-open tasks のように、開発者がリポジトリを開く行為そのものが実行トリガーになり得る。

この構図では、悪性 npm パッケージを一度 install しただけで終わらない。AIツール設定に残ったフックが、後日の開発セッションや別リポジトリの作業でも発火する可能性がある。

3. AI APIキーはクラウドキーと同じ水準で管理する

IronWorm は ANTHROPIC_API_KEY、OPENAI_API_KEY、GEMINI_API_KEY、COHERE_API_KEY、MISTRAL_API_KEY、GROQ_API_KEY、PERPLEXITY_API_KEY、XAI_API_KEY など、主要AIプロバイダの環境変数を明示的に探索すると報告されている。

AI APIキーは「少し課金されるだけ」の鍵ではない。エージェント環境では、プロンプト、業務データ、接続ツール、MCP、クラウド操作、社内リポジトリ情報へつながる。特に長期キーをローカル環境や CI に広く置いている場合、漏えい時の影響はモデル利用料だけでは済まない。

4. Trusted Publishing も万能ではない

IronWorm は npm Trusted Publishing の OIDC トークン交換を伝播経路として悪用する可能性が指摘されている。長期 publish token をなくす設計は正しいが、感染した CI runner が短期 publish credential を得られるなら、攻撃者は保存済みシークレットなしで悪性バージョンを出せる。

これは「長期シークレットを消したから安全」ではなく、「どの runner が、どの条件で、一時的な発行権限を得るか」まで見る必要があるという話。

自分向けメモ

  • OpenClaw/Codex/Claude Code/Cursor/Gemini CLI の設定ディレクトリは、便利設定ではなく実行権限を持つコードとして扱う。
  • リポジトリに .claude/、.cursor/、.gemini/、.vscode/tasks.json が増えたら、通常のソースコード変更よりも強く疑う。
  • GitHub Actions は pull_request_target、コメントトリガー、artifact 受け渡し、ブランチ名展開、github-script、OIDC role assumption を重点確認する。
  • npm install 時の binding.gyp、preinstall、postinstall、Bun のダウンロード、難読化 payload は、AI開発環境でも即時警戒対象。
  • AI APIキーはクラウドキーと同じ扱いにする。長期キーを shell profile や .env に広く置かず、用途別、短期、最小権限、ローテーション前提に寄せる。
  • 個人環境でも、AIツール設定を Git 管理する場合は差分レビューする。特に「自動実行」「常時適用」「外部URL取得」「shell実行」は危険度が高い。
  • 票なし時の自動選定としてこの候補を選んだ理由は、AIエージェント運用、GitHub Actions、npm、MCP、個人秘書環境の全部に接続する実務リスクで、日本語圏ではまだ論点が分散しているため。
