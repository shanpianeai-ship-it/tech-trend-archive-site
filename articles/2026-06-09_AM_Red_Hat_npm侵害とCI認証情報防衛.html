Red Hat npm侵害とCI認証情報防衛

要約

Red Hat は 2026-06-01 に、@redhat-cloud-services npm 名前空間の複数パッケージでサプライチェーン侵害が公表されたと説明した。Red Hat の初期調査では、侵害された GitHub アカウントから RedHatInsights 配下のリポジトリへ不正コミットが入り、npm へ悪性バージョンが公開された流れとされている。

StepSecurity の解析では、悪性パッケージは preinstall hook で npm install 時に実行され、GitHub Actions secrets、AWS、GCP、Azure、Kubernetes、Vault、npm、CircleCI などの認証情報を狙う多段の credential harvester とされる。さらに盗んだ npm token と bypass_2fa パラメータを使い、別パッケージへ自己伝播する挙動も報告されている。

自分向けには、「有名ベンダーの公式スコープなら安全」と見なせない点が重要。CI/CD の OIDC trusted publishing、npm token、install script、開発端末の環境変数まで含めて、サプライチェーン防御を運用設計として見直す案件。

背景

npm サプライチェーン攻撃は、typosquatting や新規悪性パッケージだけでなく、正規パッケージ、正規メンテナ、正規CI/CD経路を踏み台にする方向へ寄っている。今回の特徴は、Red Hat 関連の公式っぽい npm スコープで、フロントエンド系ライブラリが複数影響したこと。

Red Hat の bulletin では、影響パッケージは Hybrid Cloud Console の Web UI で使われる frontend JavaScript libraries だが、侵害期間中に Hybrid Cloud Console のリリースは公開されておらず、console.redhat.com へのデプロイ前に install-time scripts を取り除く保護もあると説明している。また、ARO / OSD / ROSA / ACS Cloud Service / AAP Managed などの Red Hat managed cloud services とは関係しないとしている。

一方で、StepSecurity は、影響バージョンを開発端末やCIでインストールした場合は、すでに認証情報が抜かれた前提で扱うべきだと強く警告している。つまり、Red Hat サービス利用者全体の障害ではなく、対象 npm バージョンを引いた開発・CI環境の侵害リスクとして読むのが妥当。

何が重要か

install script は「依存解決」ではなくコード実行面

npm install は依存パッケージを取得するだけではない。preinstall / install / postinstall があれば、その時点でコードが動く。今回のように、悪性コードがアプリ起動前に CI runner や開発端末の環境変数、設定ファイル、トークンへアクセスできる構図になる。

観点従来の見方今回の教訓
依存導入パッケージを取るだけinstall hook で任意コード実行になり得る
信頼判断公式スコープ、知名度、2FAGitHubアカウントやCI経路の侵害で崩れる
影響範囲アプリに取り込んだ時点npm install した開発端末・CIまで
初動パッケージ更新や削除認証情報ローテーションと実行ログ確認

特に CI は secrets、OIDC、クラウド認証、npm token が集中する。依存パッケージ更新PRを自動で通す運用ほど、install script 実行のリスクを明示的に制御する必要がある。

OIDC trusted publishing も万能ではない

OIDC trusted publishing は長期 npm token を減らせる点では有効だが、「正規リポジトリのワークフロー自体が不正に動かされる」ケースまでは防げない。StepSecurity は、影響パッケージが GitHub Actions OIDC 経由で公開されたと見ている。

防御策効くこと残る問題
npm 2FAアカウント直接乗っ取り対策CI発行や bypass_2fa 悪用に弱い場合がある
OIDC trusted publishing長期公開トークン削減正規CIが侵害されると正規経路で公開される
lockfile 固定意図しない更新抑制更新PRや新規環境構築時は拾う可能性がある
registry cooldown公開直後の悪性版を保留業務に導入しないと効果がない
CI egress制御C2通信や外部送信の抑止例外設定と監視設計が必要

「tokenを消せば終わり」ではなく、誰が、どのworkflowで、どのパッケージを、どの条件で公開できるかを見る必要がある。

開発端末の侵害も同じ重さで扱う

CIだけを守っても、開発者がローカルで影響バージョンを npm install していれば、SSH key、クラウドCLI設定、npm token、AIツール設定、環境変数などが抜かれる可能性がある。StepSecurity も、開発端末側の検出と影響端末特定を強調している。

企業環境では、被害確認をリポジトリ単位だけで閉じず、以下を追う必要がある。

  • lockfile と package manager cache に影響バージョンが残っていないか
  • CI runner の該当時刻の outbound connection と process execution
  • npm / GitHub / cloud / Vault / CircleCI token の発行・利用ログ
  • 開発端末での npm install 実行履歴、EDRログ、npm cache
  • GitHub Actions の権限、OIDC subject condition、environment protection

自分向けメモ

  • npm パッケージ更新は「コードレビュー」だけでなく「インストール時コード実行レビュー」として扱う。
  • GitHub Actions のデフォルト権限は最小化し、contents: read を基本にする。公開やリリース用 workflow は分離し、手動承認や protected environment を使う。
  • OIDC を使う場合も、cloud側の subject / repository / branch / workflow 条件を絞る。pull_request や任意branchから強い権限を出さない。
  • private registry / proxy に cooldown を置く価値が高い。公開直後のバージョンを即CIに入れないだけで、今回のような短時間検出案件では被弾率を下げられる。
  • 影響パッケージを引いた可能性がある場合は、ビルド再実行より先に token rotation。特に npm token、GitHub PAT、cloud keys、Vault token、CircleCI token を優先。
  • SAP/Basis文脈では、フロントエンドや周辺ツールの npm 依存も本番影響になり得る。ABAPやBTPだけでなく、管理UI、拡張アプリ、CIテンプレートの依存棚卸しが必要。
