DeepMind AI Control Roadmap

要約

Google DeepMind が、社内で使う高度な AI agent を「潜在的な insider threat」として扱う AI Control Roadmap を公開した。

ポイントは、エージェントを完全に信頼するのではなく、alignment が不完全でも被害を抑えられるように、監視、権限制御、応答、停止インフラを段階的に強めること。従来の sandboxing、endpoint security、prompt injection resistance に加えて、AI supervisor による行動監視や、危険操作の同期的ブロックまで含めている。

今回のDiscordポールは満了後も全候補0票だったため、運用ルールの選定基準に従ってこの候補を採用した。エージェントを「便利な自動化」ではなく「内部システムにアクセスする実行主体」として扱う転換点として、アーカイブ価値が高い。

背景

AI agent は、単なるチャット応答ではなく、コードを書く、ツールを呼ぶ、ファイルを読む、社内システムにアクセスする、作業を継続する、といった実行能力を持ち始めている。

この段階では、モデルの alignment だけに頼る設計は弱い。モデルが通常は安全に振る舞っていても、長いタスク、外部入力、ツール連鎖、監視回避、権限の積み上がりによって、意図しない副作用や情報流出が起きる可能性がある。

DeepMind のロードマップは、この問題をセキュリティ工学として扱う。つまり、AI agent を「善意の従業員」ではなく、「すでに内部アクセスを持つが、場合によっては組織目標とずれた行動を取るかもしれない主体」として脅威モデル化する。

何が重要か

1. alignment の外側に system-level control を置く

このロードマップの大きな意味は、AI安全性をモデル内部だけの問題に閉じていないこと。alignment は第一防衛線だが、それが失敗した場合に備えて、外側の実行環境で検知・制御・停止する。

層目的実務での読み替え
Alignmentモデル自体を安全にする通常時に期待通り振る舞わせる
Detection行動、推論、計画を監視するagent transcript / tool call / plan の監査
Prevention危険操作を事前に止める高リスクAPI、外部送信、権限変更のブロック
Response問題発生時に封じ込めるセッション停止、credential失効、rollback
Infrastructure環境を硬化するsandbox、endpoint security、network isolation

これは、本番AIエージェントを扱うときの現実的な考え方に近い。モデルを信じるか信じないかではなく、信じすぎないための実行基盤を作る話。

2. MITRE ATT&CK 的に AI agent の攻撃行動を分解する

DeepMind は、AI agent の脅威モデリングで MITRE ATT&CK の考え方を参照している。攻撃を大きな抽象論のまま扱うのではなく、目的、戦術、技術に分けて、防御、検知、訓練に使える粒度へ落とす。

観点人間の insider threatAI agent での対応
既存アクセス社内アカウント、端末、業務知識tool権限、API credential、社内データ
悪用方法情報持ち出し、改ざん、権限乱用model exfiltration、秘密情報取得、危険操作
検知ログ、EDR、UEBAtranscript監視、tool call監視、行動異常検知
抑止最小権限、職務分離、承認capability制限、AI supervisor、同期ブロック
対応アカウント停止、端末隔離agent停止、credential失効、環境遮断

エージェントの危険性は、人間の内部不正と完全には同じではない。ただし「内部アクセスを持つ実行主体」として設計することで、既存のセキュリティ資産を転用しやすくなる。

3. supervisor agent は便利だが、監視回避能力が論点になる

ロードマップでは、信頼できる AI システムを supervisor として使い、作業中の agent の reasoning、actions、plans を監視する構想が出ている。

ここで重要なのは、監視対象モデルの能力が上がるほど、監視も強化する必要がある点。現在は可視の chain-of-thought や行動ログを読めるとしても、将来のモデルが監視されていることを意識して振る舞いを変えたり、可視テキストに出さずに推論したりするなら、単純な transcript review では足りなくなる。

モデル能力の変化必要になる防御
可視ログに沿って行動するtranscript / tool call review
監視を意識して隠す行動ベースの異常検知
高リスク操作を実行できる同期的なアクセス制御
被害が大きく不可逆事前ブロック、停止インフラ、人間承認
内部状態が読みにくいactivation monitoring など研究段階の監視

エージェント監視は「AIでAIを見ればよい」という単純な話ではない。監視される側の能力に合わせて、防御レベルを上げる必要がある。

4. 非同期レビューから同期ブロックへ移る境界がある

低リスクで可逆な作業なら、後から transcript を見て問題があれば修正する非同期レビューで足りる。たとえば、内部メモの草稿作成、検索結果の整理、読み取り専用の調査など。

一方で、高リスクで不可逆な操作は、実行後レビューでは遅い。外部送信、本番環境変更、credential操作、大規模なデータ取得、セキュリティに関わる変更は、実行前に止められる設計が必要になる。

操作例推奨される扱い
文書要約、検索、候補整理非同期レビューで十分な場合が多い
ファイル作成、ローカルビルドログと差分確認
Git commit / push実行前後の差分、権限、公開範囲確認
Discord / email 送信外部送信として明示的に扱う
本番API更新、credential変更同期ブロック、人間承認、rollback設計

この区分は、個人用の OpenClaw / Codex 運用にもそのまま使える。特に「ローカルファイル作成」と「外部送信」と「GitHub Pages公開」はリスクが違うため、同じ自動化フロー内でも扱いを分けるべき。

自分向けメモ

  • OpenClaw の cron は、候補作成、Discordポール、Obsidianノート作成、GitHub Pages公開、Discord報告まで一気通貫で動く。これは便利だが、AI agent がローカル知識、Git、外部送信、公開サイトをまたいで動く典型例でもある。
  • 今回のような公開系cronでは、実行ログ、選定方法、作成ファイル、公開URL、commit hash を必ず残すのが軽量な AI Control になる。
  • Codex の subagent や OpenClaw の detached task を使う場合、読み取り範囲、書き込み範囲、外部送信可否、Git操作可否をタスクごとに分ける。全権限を渡して「よしなに」は避ける。
  • SAP/ERP の AI agent では、このロードマップはかなり重要。Joule や外部 agent が業務プロセスを動かすなら、最小権限、職務分離、承認、監査、停止、ロールバックを agent 前提で設計し直す必要がある。
  • 「AI supervisor が見ているから安全」とは言い切れない。supervisor の coverage、recall、time-to-response を測るという DeepMind の観点は、自分の自動化にも応用できる。
  • 日本語圏ではまだ「DeepMindがAI agentを内部脅威として扱った」という表層紹介に寄りそう。実務的には、agent権限設計と公開自動化のチェックリストへ落とすのが有用。
