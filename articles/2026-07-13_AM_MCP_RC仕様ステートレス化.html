2026-07-13 AI / LLM / Agent importance: high
Summary

Model Context ProtocolのRCは、セッション固定型の運用からHTTPステートレス設計へ移行し、認可強化と拡張ガバナンスを一本化する。AI接続基盤の運用負荷や移行戦略を見直す価値が高い。

MCP RC仕様ステートレス化

要約

MCPの次期仕様RCは、クライアントごとのセッション固定を前提としていた設計を外し、HTTP上でインスタンスを横断して処理できるステートレス運用を正式化した。これにより、サーバー側でセッションを保持して負荷分散を難しくしていた構成を簡素化できる。

また、MCP AppsやTasksを拡張フレームワークとして扱う方向へ寄せ、拡張ごとの独立公開・検証周期を明確化。併せてOAuth/OIDC整合を意識した認可強化と機能寿命管理を入れ、長期運用での破壊的変更リスクを下げる構えだ。

背景

2025-11-25系の仕様では、tools/callの前提としてinitializeとセッションID付与が必要だった。RCでは、MCP-Protocol-VersionやMcp-Method、Mcp-Nameヘッダを使う方式へ変更し、初期ハンドシェイクを不要化している。

さらに、応答系をttlMsやcacheScopeで制御できるようにし、キャッシュ戦略と再利用可否をクライアント側が明示判断できるようにしている。これにより、SSE前提や長寿命接続依存を減らし、HTTP基盤全体の設計自由度を上げる。

何が重要か

1. ステートレス化はインフラ運用コストを直接下げる

以前はMcp-Session-Idベースの粘着ルーティングや共有セッションストアが必要だったが、RCではヘッダ駆動で任意インスタンスへ振り分け可能になる。これは、

項目変更前RC後
ルーティング条件主にセッションID貼り付けMcp-Method/Mcp-Name中心
水平スケール実装依存で複雑原則ラウンドロビン寄りが前提
状態管理トランスポート層に依存アプリ層で明示ハンドル化

ただし、状態を持つ処理そのものは不要化しない。記事の通り、業務上必要な状態はハンドルとして明示し、次のツール呼び出しに渡す方式が推奨される。

2. 拡張をコアと分離する設計は更新速度を上げる

TasksやMCP Appsのような高頻度変化領域は、コアを壊しにくく拡張トラックで育てる構造に寄せる。これは、AIエージェント基盤で頻発する仕様追従コストを抑える上で実務的に効く。

3. 認可強化は運用事故を減らす土台

iss検証やOIDCアプリケーション種別登録など、実装面が実デプロイで起こりやすいミスを仕様側で詰める方向。これ自体は「導入時のバグ」ではなく「本番運用時の事故予防」に直結するため、監査観点でも重要。

4. 機能寿命方針は更新計画を組みやすくする

機能を Active/Deprecated/Removed で扱い、削除までに猶予を設ける方針は、実装・保守フェーズの計画を立てやすくする。特に社内導入では「いつ止めるか」「何を先に移すか」が曖昧になりがちなため、ロードマップ整備向きだ。

自分向けメモ

  • MCPクライアント実装は、セッション固定思考を捨て、_metaを含む毎リクエスト情報の明示設計に寄せる。
  • バックエンド側は状態保持を外部ストレージ化し、モデルへ状態参照キーを戻す設計（例: basket_id）を取り入れる。
  • 監視導線（trace）がtraceparentベースで揃う前提なら、分散トレース整備の前倒しが有効。
  • MCP Apps/Taksを使うなら、UIレビューや権限制御の監査線をJSON-RPC経由の既存パスに統合する考えを先に決める。
  • 機能の廃止タイムラインを前提に、運用アプリ/社内ガイドを更新してから本番反映する。
