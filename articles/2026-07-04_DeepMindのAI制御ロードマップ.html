2026-07-04 AI / LLM / Agent importance: high
Summary

Google DeepMindのAI Control Roadmapは、AIエージェントを内部脅威として扱い、監視・権限制御・即時停止を設計するための実務的な枠組み。

DeepMindのAI制御ロードマップ

要約

Google DeepMindが公開したAI Control Roadmapは、社内で動かす高能力AIエージェントを「完全に信頼できる従業員」ではなく、「権限を持つ可能性のある内部脅威」として扱うためのセキュリティ設計である。

中心にあるのは、モデルのアラインメントだけに頼らず、サンドボックス、エンドポイント防御、プロンプトインジェクション耐性、AI supervisor、権限制御、ブロック機構を重ねる防御多層化の考え方。DeepMindはMITRE ATT&CKのような脅威モデリングをAIエージェントにも適用し、監視対象範囲、検知率、対応時間を測るべき指標として挙げている。

自分向けには、OpenClaw、Codex、Claude Code、Gemini系の自律実行環境を運用するときの「権限をいつ渡すか」「危険操作をどう止めるか」「ログを何で評価するか」の設計資料として読む価値が高い。

背景

AIエージェントは、チャット応答だけでなく、コード編集、シェル実行、ブラウザ操作、社内文書検索、チケット更新、クラウド操作まで担当する方向へ進んでいる。モデルが賢くなるほど、単なる補助ツールではなく、業務システム上の実行主体に近づく。

従来のAI安全性は、モデルが危険な指示を拒否できるか、望ましい振る舞いを学習しているかに注目しがちだった。しかし、実行権限を持つエージェントでは「モデルが概ね安全」だけでは足りない。外部入力、プロンプトインジェクション、誤解、過剰な目的達成、ツール実装バグ、権限設定ミスが組み合わさると、アラインメント済みモデルでも望まない操作を実行し得る。

DeepMindのロードマップは、この前提を正面から置いている。つまり「もし高能力AIエージェントがこちらの意図とズレた行動をしたらどうするか」を、情報セキュリティの脅威モデルとして扱う。

何が重要か

1. エージェントを内部脅威として扱う発想

DeepMindは、未信頼のAIエージェントを、社内アクセス権を持つ不正従業員に近い存在としてモデル化している。これは強い言い方だが、エージェントにファイル、API、ブラウザ、リポジトリ、クラウド権限を渡すなら自然な見方である。

観点従来の見方AI Control的な見方
安全性モデルが危険要求を拒否する実行時に監視・制限・停止できる
権限便利な作業に必要な許可検証済み行動に応じて段階的に渡す
ログ後から確認する履歴検知・遮断・訓練データの材料
外部入力参考情報エージェント行動を変える未信頼データ
失敗原因悪意ある命令誤解、過剰達成、監視回避、実装バグも含む

この視点は、個人のAI秘書環境にもそのまま効く。特にOpenClawのように、ローカルファイル、Discord、Obsidian、Git、ブラウザ、cronを横断するエージェントでは、権限境界を人間の感覚だけで管理すると破綻しやすい。

2. 監視AIを置くだけではなく、測定指標を定義している

ロードマップでは、AI supervisorが作業中エージェントの推論、行動、計画を確認し、逸脱を検知したらブロックする考え方が示されている。ただし重要なのは、監視AIの存在そのものではなく、監視の性能を測る指標が明示されている点。

指標意味運用上の問い
coverage監視できているトラフィック割合どのツール呼び出しが未監視か
recall問題行動を捕まえる割合危険操作をどれだけ見逃すか
time-to-response検知から対応までの時間実害が出る前に止められるか

この3つは、エージェント運用のSLOに近い。単に「ログを取っています」ではなく、「どの操作は同期的に止める必要があるか」「どの操作は非同期レビューでよいか」を分ける必要がある。

3. D1-D4 / R1-R3 の段階設計が実務に使える

DeepMindは、防御レベルをモデル能力に合わせて上げる考え方を示している。検知側は、モデルが監視を回避できる能力に応じてD1からD4へ強化する。対応側は、実行できる害の大きさに応じてR1からR3へ強化する。

軸低リスク側高リスク側
Detection可視の思考・ログを後から読む行動分析や内部状態の検査まで必要
Prevention / Response非同期レビューと後処理で足りる実行前に同期的にブロックする

この区分は、自分の環境では次のように置き換えられる。

操作必要そうな対応
Obsidianにノートを作る非同期ログ確認でよい
Git commit / push実行前差分確認と結果確認が必要
Discordへ送信送信先・本文・添付の同期チェックが必要
外部Webフォーム送信原則人間確認
rm、認証情報、公開投稿自動実行させない、または強い承認ゲート

4. 100万件のコーディングエージェント軌跡を監視設計に使っている

DeepMindは、非同期監視システムの内部プロトタイプで100万件のコーディングエージェントタスクを分析したとしている。ここで重要なのは、多くのフラグは敵対的意図ではなく、エージェントの誤解や過剰な目的達成から生じるという指摘である。

これは実感に近い。AIエージェントは、悪意がなくても「依頼を完了させる」方向へ強く進み、不要なファイル変更、過剰なリファクタ、危険なコマンド、外部送信を選ぶことがある。したがって、監視は「攻撃者を探す」だけではなく、「善意の暴走を止める」目的でも必要になる。

自分向けメモ

  • エージェント運用では、モデルの賢さよりも、権限の段階付与、監視範囲、停止条件を先に設計する。
  • cronは特に危険。人間が画面を見ていない時間帯に、ファイル操作、Git操作、Discord送信、Web公開まで行うため、成功条件と失敗条件を明確にする。
  • 「投票読み取りだけで完了扱いにしない」のような実行条件は、AI Controlでいうtime-to-responseやcoverageの一部と考えられる。期待ファイル、ビルド、commit、push、公開URL確認までを成功判定に含める。
  • 低リスクな情報整理と、高リスクな外部送信・公開・削除を同じ自動化レベルで扱わない。
  • Supervisor役を置くなら、自然言語の感想ではなく、ツール呼び出し、差分、公開URL、送信先、認証情報混入のような構造化チェックを見せるべき。
  • 票なし時の自動選定としてこの候補を選んだ理由は、AIエージェントの運用設計、セキュリティ、個人秘書環境の権限管理に直結し、日本語圏ではまだ実装・運用レベルの解説が少ないため。
