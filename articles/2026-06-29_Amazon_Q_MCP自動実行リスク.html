2026-06-29 Security importance: high
Summary

Amazon Q DeveloperのMCP設定自動実行問題は、AIコーディングツールがIDE拡張、ローカル実行、クラウド認証情報をまたぐ信頼境界になったことを示す事例。

Amazon QのMCP自動実行リスク

要約

Wiz Researchは、Amazon Q DeveloperのVS Code拡張で、ワークスペース内の.amazonq/mcp.jsonが明示的なMCP実行同意なしに読み込まれ、MCPサーバーとして指定されたコマンドが起動される問題を公開した。Wizの説明では、悪意あるリポジトリを開きAmazon Qを有効化するだけで、攻撃者が用意したコマンドが開発者端末上で実行され、AWS認証情報やAPIキーなどの環境変数へアクセスできる。

AWSのSecurity Bulletinでは、この問題はCVE-2026-12957として扱われ、Language Servers for AWS 1.65.0未満の「trust boundary enforcement」問題と説明されている。AWSは関連するCVE-2026-12958も含め、Language Servers for AWS 1.69.0および対応するAmazon Q Developer IDEプラグインへの更新を推奨している。

重要なのは、これはAmazon Qだけの個別不具合ではなく、AIコーディングツールが「リポジトリ設定を読む」「ローカルプロセスを起動する」「クラウド認証情報を持つ開発者環境で動く」という3点を同時に満たす時代の信頼境界問題だということ。MCP、IDE拡張、エージェント型開発支援を導入する時は、便利機能ではなく実行権限を持つ攻撃面として扱う必要がある。

背景

MCPは、AIアシスタントが外部ツールやローカルリソースへ接続するための標準化された仕組みとして普及している。実務上は、MCPサーバーを起動するということは、npx、python、bashなどのローカルプロセスを実行することに近い。

開発者端末には、次のような認証情報が残りやすい。

種別例漏えい時の影響
クラウド認証情報AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_SESSION_TOKENクラウド資産の列挙、変更、永続化
CLI認証情報AWS CLI, gcloud, az, GitHub CLI操作済みアカウントの権限でAPI実行
APIキーAI APIキー、SaaS APIキー課金、データ取得、ツール連携悪用
SSH/署名キーSSH agent socket, signing keyリポジトリ、サーバー、署名経路への横展開
VPN/社内接続VPN接続中の端末内部サービスへの到達可能性を攻撃者に渡す

従来も「未信頼リポジトリを開く」ことにはリスクがあった。ただし、VS CodeのWorkspace Trustなどにより、タスクや拡張の一部実行を抑える設計が入っている。今回の論点は、AI拡張がリポジトリ内のMCP設定をどう扱うか、そしてその実行にどの程度の同意と環境分離が必要かという点にある。

何が重要か

1. MCP設定は設定ファイルではなく実行計画として見る

.amazonq/mcp.jsonのようなファイルは、見た目は設定ファイルでも、内容は「どのコマンドを、どの引数と環境で起動するか」を指定する実行計画に近い。

Wizが示したPoCでは、MCPサーバー設定からshellを起動し、AWSの呼び出し結果を外部へ送る流れが説明されている。細部の実装は製品ごとに違っても、MCPサーバーの起動権限がある時点で、リポジトリ所有者が開発者端末上のプロセス起動に影響できる。

観点安全寄りの扱い危険な扱い
MCP設定ユーザーが内容を確認して許可ワークスペースから自動ロード
実行環境必要最小限の環境変数だけ渡す親プロセスの環境を丸ごと継承
未信頼リポジトリWorkspace Trustや隔離環境で扱う通常の作業端末で即オープン
監査MCP設定差分をレビュー対象にするコード以外の補助設定として見逃す

2. 環境変数の継承がクラウド侵害に直結する

今回のリスクは、単に「ローカルで任意コマンドが動く」だけではない。開発者がAWSやSaaSへログインした状態で作業しているため、起動されたプロセスが認証情報にアクセスできる。

AWSのbulletinでは、CVE-2026-12957はローカルユーザーが悪意あるワークスペースを開いた場合に、プロジェクト設定ファイル内のコマンドが自動実行され得る問題として整理されている。Wiz側は、MCPサーバーがフル環境を継承することで、クラウド認証情報窃取までつながる点を強調している。

この差分は運用上かなり重要。脆弱性票では「ユーザー操作が必要」と見えても、実務では「PRレビュー、サンプルリポジトリ、採用課題、検証用OSS」を開く日常作業の延長で踏む可能性がある。

3. AIコーディングツール横断のパターンとして扱う

Wizは、類似のMCP自動実行やワークスペース設定実行の問題が、Claude Code、Cursor、Windsurfなどにも報告されていると整理している。個別製品名で終わらせず、次のパターンとして見る方が実用的。

パターン典型例防御観点
ワークスペース内設定の自動実行.amazonq/, .vscode/, AIツール用設定未信頼リポジトリでは自動実行しない
エージェント用ツール起動MCP server, hooks, tasks実行前同意、コマンド表示、許可リスト
環境の過剰継承shell環境、APIキー、SSH agent最小環境、用途別キー、短期認証
便利な常時適用ルールAI rules, project instructionsリポジトリ由来ルールを信頼しない
開発者端末からクラウドへ横展開AWS CLI, GitHub CLI, VPN権限分離、検証用プロファイル、隔離VM

4. 「最新版へ更新」だけでは運用設計として足りない

AWSはLanguage Servers for AWS 1.69.0と対応プラグインへの更新を推奨している。これは直近対応として必須。ただし、今後も別のAI拡張やMCPクライアントで同じ種類の設計ミスが出る可能性は高い。

自分の環境では、ツールごとに次を見たい。

  • リポジトリ内MCP設定を自動で読むか。
  • 実行前にコマンド、引数、環境変数差分を表示するか。
  • ワークスペース信頼状態と連動するか。
  • MCPサーバーが親プロセス環境を丸ごと継承するか。
  • 拒否、単発許可、恒久許可、リポジトリ単位許可を分けられるか。
  • ログとして「いつ、どの設定から、何を起動したか」が残るか。

自分向けメモ

  • 未信頼リポジトリを開く時は、Amazon Q、Claude Code、Cursor、Windsurf、VS Code拡張、OpenClaw/Codex系のMCP自動起動をすべて疑う。
  • .amazonq/, .vscode/, .cursor/, .claude/, .mcp.*, mcp.json, tasks.json はソースコードと同じか、それ以上に強くレビューする。
  • AIツールの設定ファイルは「モデルへの指示」だけでなく「ローカル実行権限」を持つ場合がある。リポジトリに入っているからといって信用しない。
  • AWSやGitHubにログインしたメイン環境で、採用課題、謎のPoC、未確認OSSを開かない。必要なら一時VM、コンテナ、別OSユーザー、クラウド権限なしプロファイルで見る。
  • MCPサーバーには、親shellの環境変数を丸ごと渡さない設計が望ましい。OpenClaw/Codex側でも、コネクタやMCPの許可は「実行前に見える」「後で監査できる」を基準にする。
  • Amazon Q利用者は、VS Code拡張2.20以上、JetBrains 4.3以上、Eclipse 2.7.4以上、Visual Studio Toolkit 1.94.0.0以上を最低ラインとして確認する。Language Servers for AWSは1.69.0以上を目安にする。
  • 票なし時の自動選定としてこの候補を選んだ理由は、AIエージェント運用、MCP、IDE拡張、クラウド資格情報の境界が一つの具体事例になっており、日本語圏でまだ一般的な運用チェックリストに落ち切っていないため。
