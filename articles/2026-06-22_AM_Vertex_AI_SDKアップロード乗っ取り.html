Summary

Unit 42 は 2026-06-16 に、Google Cloud Vertex AI SDK for Python の Model.upload() に関する bucket squatting 型の脆弱性を公開した。

Vertex AI SDKアップロード乗っ取り

要約

Unit 42 は 2026-06-16 に、Google Cloud Vertex AI SDK for Python の Model.upload() に関する bucket squatting 型の脆弱性を公開した。対象は google-cloud-aiplatform SDK v1.139.0 と v1.140.0 で、修正版は v1.148.0。

問題は、SDK がデフォルトの staging bucket 名を project ID と region から予測可能に作り、同名 bucket が存在した場合に所有者確認をしない点にあった。攻撃者が先に同名 bucket を自分の Google Cloud project に作っておくと、被害者のモデルアップロードが攻撃者 bucket へ流れ、短い時間窓でモデル artifact を差し替えられる。

差し替え後、被害者が Vertex AI endpoint へ model を deploy すると、serving container 側で pickle / joblib の deserialization が発火し、managed tenant project 内で任意コード実行につながる。AI/ML基盤の「学習・登録・デプロイ」経路そのものがサプライチェーン攻撃面になる例として重要。

背景

Vertex AI の Model Registry へ model を upload する場合、SDK は一度 Cloud Storage bucket に model artifact を stage し、その後 Model Registry がその artifact を参照する。被害者が明示的な staging_bucket を指定しないと、SDK はデフォルト名を組み立てる。

Unit 42 の調査では、脆弱なSDKはこの default bucket について「存在するか」は確認していたが、「その bucket が呼び出し元 project の所有物か」は確認していなかった。Cloud Storage bucket 名はグローバル一意なので、攻撃者が予測した bucket 名を先に取れると、被害者の SDK はそれを既存 bucket として扱ってしまう。

攻撃成立条件は限定的だが、現実的な線がある。

条件内容実務上の見方
SDK versionv1.139.0 / v1.140.0古い notebook / pipeline image に残りやすい
bucket対象 region の default staging bucket が未作成新規 project / 新 region 利用時に起きやすい
設定staging_bucket を明示していないサンプルコードや個人実験でありがち
攻撃者情報project ID と region を推測できるproject ID は公開ログやURLから漏れやすい
artifact形式pickle / joblib などコード実行性のある形式Python ML標準運用と衝突する

Google 側では、v1.144.0 で auto-created GCS staging bucket 名を予測しにくくする修正が入り、v1.148.0 で Model.upload() に bucket ownership verification が追加された。

何が重要か

1. MLモデル登録経路がクラウド境界をまたぐ攻撃面になる

この件は「モデルファイルが悪意ある pickle だった」という単純な話ではない。問題の本体は、SDK、Cloud Storage、Model Registry、serving infrastructure、Google-managed tenant project が連鎖する中で、staging bucket という一時領域の所有権確認が抜けていた点。

攻撃段階何が起きるか防御で見る点
予測project ID と region から bucket 名を推測project ID露出、命名規則、default依存
先取り攻撃者 project に同名 bucket を作成bucket ownership確認、組織ポリシー
アップロード誘導被害者SDKが攻撃者bucketへartifactを送る明示的な staging bucket、SDK更新
差し替えCloud Function 等で model artifact を即時置換artifact integrity、署名、hash検証
実行deploy時に joblib / pickle load でコード実行unsafe serialization排除、runtime権限制限

一時領域は監視や設計レビューから漏れやすい。だが ML pipeline では、preprocess artifact、model artifact、evaluation output、registry連携など、一時領域が本番実行に直結する。

2. 「普通のSDK利用」でも攻撃経路になる

被害者側は特別に危険なAPIを呼んでいるわけではない。標準的に aiplatform.init() し、Model.upload() し、endpointへdeployするだけで攻撃経路に入る。

これは AI/ML 運用でかなり厄介。開発者はクラウド内部の staging 実装を意識せず、SDKが安全に処理してくれる前提で使う。Notebook、CI、MLOps pipeline、AutoML周辺のサンプルコードほど default 設定に寄りやすい。

3. pickle / joblib はモデル配布形式として引き続き危険

Unit 42 のPoCでは、差し替えた joblib file の __reduce__ により、deserialization 時にコード実行させている。これは Python の pickle 系 format の既知リスクだが、MLでは scikit-learn などの流れで自然に使われる。

形式/運用利点リスク
pickle / joblibPython MLで扱いやすいload時に任意コード実行の余地
container image実行環境ごと固定しやすいimage supply chainとregistry権限が重要
model署名/hashartifact改ざんを検知しやすいpipeline全体へ組み込む必要
専用format実行性を下げやすいframework差、互換性、変換コスト

ML基盤では「モデルはデータ」と見がちだが、pickle系 artifact は実質的にコードとして扱うべき。

4. 修正済みでも棚卸し対象は残る

Google の修正により、最新 SDK では bucket 名の予測困難化と ownership verification が入っている。ただし実務では、古い base image、古い notebook runtime、固定された requirements.txt、長期稼働 pipeline が残りやすい。

すぐ見るべき項目は次の通り。

  • google-cloud-aiplatform が v1.148.0 以上か。
  • Vertex AI の Model.upload() を使う pipeline で staging_bucket を明示しているか。
  • 明示した bucket が自組織 project / folder / perimeter の管理下にあるか。
  • model artifact の hash / 署名 / provenance を registry 登録前後で検証しているか。
  • pickle / joblib の load を前提にする serving container の権限が過大でないか。
  • 古い training / deployment image に SDK version が固定されていないか。

自分向けメモ

  • AI/ML基盤の脆弱性は、モデルAPIだけでなく「SDKの便利機能」「一時bucket」「managed service agent」「tenant project」まで見る必要がある。
  • 個人や小チームのAI実験でも、project ID は外に出やすい。Cloud Storage bucket 名が予測可能か、default bucket に依存していないかは確認したい。
  • pickle / joblib は便利だが、外部由来 artifact だけでなく「途中で差し替えられる可能性のある artifact」も危険扱いにする。
  • Vertex AIを使う手順書を作るなら、pip install --upgrade google-cloud-aiplatform と明示的 staging bucket 指定を標準手順に入れる。
  • SAP / ERP のAI連携でも、業務データを使ったML pipelineは一時領域とartifact検証が盲点になりやすい。Basis運用目線では bucket/IAM/署名/ログをセットで見る。
