MCP Python SDK v2 alpha

要約

MCP Python SDKのv2.0.0a1は、2026-07-28予定のMCP仕様変更に向けた最初のalpha。現行のv1系利用者がすぐ自動更新されるものではないが、stable v2が出る前に依存上限と移行方針を決めておく必要がある。

最大の論点は、MCPのプロトコル層が長期セッション前提から、stateless request/response寄りへ大きく変わること。Python SDK v1は長期セッション中心に作られているため、v2では中核が置き換わり、サーバー/クライアント実装の抽象も変わる。

自分向けには、OpenClawやCodex周辺でMCPサーバーを増やす前に、「今はv1で固定する」「v2対応は別ブランチ/別環境で試す」「長期状態はプロトコルのセッションではなく明示的なIDやタスク状態として持つ」という設計メモとして重要。

背景

MCPは、LLMアプリケーションやエージェントが外部ツール、リソース、プロンプトへ接続するための共通プロトコルとして広がっている。Python SDKは、自作MCPサーバーやクライアントを作るときの主要実装の一つ。

2026-07-28仕様RCでは、MCPは次の方向へ寄っている。

項目2025-11-25系の見方2026-07-28系の方向
セッションinitialize後にMcp-Session-Idを持ち回るプロトコル層のセッションをなくす
ルーティングsticky sessionや共有session storeが必要になりやすい任意のサーバーインスタンスへ回しやすい
状態管理transport/sessionに隠れやすいtool引数やtask handleなど明示的な状態へ寄せる
拡張core仕様に入りがちExtensions frameworkで独立進化させる
観測性実装ごとの工夫が混ざるTrace Contextやheadersで追いやすくする

Python SDK v2 alphaは、この仕様変更に合わせた先行実装。v2.0.0a1時点では2025-11-25仕様機能のみの対応で、2026-07-28機能はalpha期間中に追加され、betaは2026-06-30、stable v2は2026-07-28前後を目標としている。

何が重要か

依存上限を入れないPythonパッケージが一斉に壊れる可能性

リリースノートでは、PyPI上でmcpに依存する多数のパッケージが上限を指定していない点が明示されている。stable v2が出た日に、mcp>=1.xのような指定がv2を解決してしまうと、利用者側で予期せぬ破壊的変更を踏む。

立場今やること理由
MCPサーバー利用者mcp>=1.27,<2のように上限を入れるstable v2公開時の自動混入を防ぐ
ライブラリ作者pre-release依存はpre-releaseだけに閉じる利用者をalphaへ巻き込まない
運用者lockfileとCIでSDKバージョンを固定するCronや常駐エージェントの突然死を防ぐ
検証者v2は別環境で試すalpha間でも破壊的変更があり得る

これは派手な新機能というより、依存管理の事故予防として重要。

長期セッション前提の設計を見直す必要がある

MCP 2026-07-28 RCでは、initialize/initialized handshakeとMcp-Session-Idがなくなる方向。状態が必要なアプリケーションは、プロトコルが裏で持つsessionではなく、toolが返す明示的なhandleを次の呼び出しに渡す設計へ寄る。

状態の種類v1的な置き場所v2以降で考える置き場所
作業中のブラウザ/買い物かごsessionに紐づく内部状態browser_idやbasket_idをtool結果で返す
長時間処理coreのTasks実験機能Tasks extensionのhandleで追う
利用者文脈接続単位の暗黙状態_meta、認証主体、明示的な入力で渡す
監査/追跡実装ごとのログTrace Contextとgateway側ログでつなぐ

OpenClawのような長時間エージェント環境では、この変更はかなり自然に見える。裏の接続に状態を隠すより、ファイル、タスクID、候補一覧、Discord message id、commit hashのように、後から追える形で状態を持った方が復旧しやすい。

SDK APIも単なる型追加ではなく中核が変わる

v2 alphaでは、サーバー側でServerSessionを置き換えるDispatcher pipelineが入り、low-level Server interfaceも変わる。handlerはdecoratorではなくconstructor parameterになり、戻り値のauto-wrapもなくなる。FastMCPはMCPServerへrenameされる。

変更影響
Dispatcher pipelinesession中心の実装からrequest処理中心へ読み替えが必要
handler定義変更サーバー実装の書き換えが必要になり得る
return value auto-wrap廃止型とレスポンス生成を明示する必要
snake_case field names / stricter validation既存コードの暗黙変換に頼れない
FastMCP renameimportやドキュメント、サンプルの更新が必要

「pipを上げれば終わり」ではなく、自作MCPサーバーの構造を一度棚卸しする種類の移行。

仕様変更は運用面では悪い話だけではない

stateless化は破壊的だが、運用面ではかなり筋がよい。MCPサーバーを普通のHTTP基盤に載せやすくなり、load balancer、cache、rate limit、traceの扱いが素直になる。

運用論点期待できる改善
horizontal scalesticky sessionや共有session storeへの依存を減らせる
gateway制御Mcp-MethodやMcp-Nameでルーティング/制限しやすい
キャッシュtools/listなどにTTL/スコープを持たせられる
observabilityTrace Contextでhostからserver、その先の外部APIまで追いやすい
セキュリティOAuth/OIDC寄りの認可強化、issuer検証が入る

企業内MCPや個人環境の常駐MCPでも、「どのtoolが呼ばれたか」「どのユーザー/エージェントが呼んだか」「どの外部APIへつながったか」を追いやすくなる方向。

自分向けメモ

  • 自作/利用中のMCP Python依存は、stable v2前に<2上限を入れる。特にCronや常駐エージェントの裏で使うものはlockfileも確認する。
  • v2 alphaは本番へ入れない。試すならmcp==2.0.0a1を明示し、検証用venvや別コンテナで見る。
  • MCPサーバー設計では、transport sessionに状態を隠さず、tool結果として明示的なIDを返す設計へ寄せる。
  • 長時間処理は「sessionが生きているから続く」ではなく、task handle、ファイル、DB、キューで復元できるようにする。
  • OpenClaw/Codexの外部ツール連携でも、Discord message id、候補一覧frontmatter、commit hashのような追跡可能な状態を残す方針を続ける。
  • 2026-06-30 beta、2026-07-28 stable予定を追う。v2 migration guideが更新されたら、既存MCP利用箇所を棚卸しする。
