SAP APIポリシーと組織記憶

要約

SAP Sapphire 2026後の論点として、SAP API Policyの更新と「organizational memory」が同じ文脈で語られている。ポイントは、AIエージェントがSAP上の業務データや操作に入るほど、単なるAPI開放ではなく、認証、監査、利用量制御、文脈管理が必要になるということ。

今回のdiginomica記事はSAP CTO Philipp Herzigへの取材を軸に、APIポリシー変更の理由、ユーザー会の反応、MCP/A2Aのような新しいエージェント連携標準がSAPアーキテクチャに与える圧力を整理している。

背景

SAPは2026年5月のSapphireで、SAP Business AI Platform、SAP Autonomous Suite、Joule Workを含むAutonomous Enterprise構想を発表した。SAP公式発表では、AIエージェントを業務プロセス、データ、ガバナンスに結びつけ、正確で準拠性のある業務実行を狙うと説明している。

一方で、エージェントがAPIを大量・自律的に呼び出す時代になると、従来の「人間や固定バッチが呼ぶAPI」とは負荷・権限・監査の前提が変わる。SAPのFAQでも、API PolicyはAPIの意図通りの利用、安定性とセキュリティ、誤用防止、AI/自動化の増加に対応したスケーラブルな利用を目的にした枠組みだと説明されている。

何が重要か

論点従来の見方エージェント時代の見方Basis/運用で見る点
API利用量連携ごとの想定負荷を見積もる1プロンプトが多数API呼び出しへ展開し得るrate limit、throttling、監視値
API種別動けば使えるインターフェースも残りがちPublished APIか、非公開/内部APIかがより重要Business Accelerator Hub、Help Portal、ATC確認
認証技術ユーザーや連携ユーザーで管理エージェントごとの識別と監査証跡が必要デジタルID、権限分離、監査ログ
データ抽出ODP/RFCや独自抽出の実績を重視大規模分析はBDC Connectなど統制された経路へ寄せるデータ出口の標準化
AI連携外部LLM/ツールからSAPを呼ぶJoule、A2A、MCP Gatewayなど統制レイヤが前提化アーキテクチャ承認、例外管理

SAP FAQでは、既存の契約権利やライセンスを変更するものではなく、公開・文書化されたAPIを制御内で使う統合は大きく壊さない姿勢が示されている。ただし、SAP内部向けAPIや非公開API、特にODP-RFCのような本来用途外の使い方は、セキュリティと監査性の観点で見直し対象になる。

同時に、diginomicaが強調する「organizational memory」は、AIエージェントに必要な業務文脈の話だ。構造化データだけでなく、なぜその判断をしたのか、どの例外が過去に認められたのか、どの業務慣習が実際に機能しているのかといった意思決定の痕跡をAIが参照できないと、ERP上の自律実行は危うい。

自分向けメモ

  • SAPのAPI Policyは「外部AIを閉め出す話」とだけ見ると雑すぎる。実務上は、AIエージェントのAPI連打、データ持ち出し、誤更新、監査不能性をどう抑えるかの話。
  • Basis観点では、Clean Core、Published API、BTP Integration Suite、Joule/A2A/MCP Gateway、BDC Connectを1枚の統制図に並べたい。
  • ODP-RFCのような歴史的連携は、動いているかではなく「今後も監査可能でサポートされる経路か」で棚卸しする。
  • 組織記憶はRAGの社内文書検索より広い。業務ルール、例外判断、承認履歴、障害対応、変更理由まで含めないと、AIはERPを安全に動かせない。
  • SAPがJoule経由を強く推すほど、顧客側は「SAP推奨経路の安心」と「外部エージェント/OSS/MCPの柔軟性」の間で設計判断を迫られる。
