Cloudflare脆弱性ハーネス

要約

Cloudflare が、AI を使った脆弱性探索を「単発のコードレビュー」ではなく、永続状態を持つハーネスとして運用する設計を公開した。

中核は Vulnerability Discovery Harness (VDH) と Vulnerability Validation System (VVS) の二段構え。探索側と検証側で別モデルを使い、発見、検証、重複排除、本番到達性判断、修正案生成までを分ける。

重要なのは、AI が脆弱性を「見つける」話ではなく、ノイズ、幻覚、重複、途中失敗、コンテキスト枯渇を運用設計で抑える話になっている点。

背景

AI エージェントによるセキュリティレビューは、単一リポジトリに対して一回プロンプトを投げるだけなら始めやすい。しかし実運用では、以下の問題がすぐに出る。

課題単発エージェントの弱点Cloudflareの設計
コンテキスト枯渇長時間調査で記憶が圧迫される状態をDBへ外出しする
偽陽性もっともらしいだけの報告が混ざる別モデルと決定的チェックで潰す
再実行性途中失敗で最初からやり直しrun_id / repo / stage 単位で再開
横断影響依存先・利用側を見落とすdependency graph で追跡
修正信頼性AIが壊す修正を出すfail to pass のテストゲートを要求

Cloudflare は、初期の security-audit skill から始め、Recon、Hunt、Validate、Report などの段階をハーネスに移した。最小構成でも Recon、Hunt、Validate をDBで管理し、Validator は自分では発見を登録できない役割にする、という考え方が実務的。

何が重要か

第一に、AI セキュリティ運用の主戦場が「モデル性能」から「状態管理と検証アーキテクチャ」に移っている。

Cloudflare は、モデルを固定した前提で設計していない。探索側のモデルと検証側のモデルを分け、モデルプロバイダの変化や推論挙動の揺れを吸収する前提にしている。これは、AIエージェント基盤を長く運用するなら必須の発想。

第二に、脆弱性発見の成果物を人間がレビューできる単位に落としている。

成果物目的
threat modelどの攻撃者がどの境界を破るのかを明確にする
PoC test元コードに対して実際に再現するか確認する
proposed patch修正方針をレビュー可能にする
mechanical validationパス、行番号、スキーマ、テスト形式を決定的に確認する
independent validation別エージェントが発見を否定しにいく

第三に、AIが自分で作った脆弱性を報告する問題に明確な対策を置いている。

モデルがソースを改変して自分のPoCを通してしまう、脅威モデルが空虚なまま報告してしまう、という失敗はAIレビューで起きやすい。Cloudflareは「元のコードに対する再現テスト」「Validatorは発見を登録できない」「Fixerは自動マージしない」という境界で抑えている。

自分向けメモ

OpenClaw / Codex 系の自動レビューにも、そのまま使える発想が多い。

  • 長い調査はチャット履歴ではなく、ファイルまたはDBに状態を残す。
  • 探索役と検証役を分け、検証役には「否定する」役割を与える。
  • 成果物は Markdown だけでなく、構造化JSONと機械チェックを通す。
  • 「ツールがない」「環境がない」場合は、無理に進めず wishlist 的な待ち行列にする。
  • 成功判定は例外の有無だけで見ない。本文上のエラーや空実行も失敗として分類する。

特にCron運用では、Cloudflare記事中の「200 OK のストリームに一時エラー文が返っても、例外としては落ちない」という注意が刺さる。今後の自動化では、コマンド終了コード、出力内容、期待ファイル更新、公開URL確認を合わせて成功判定するべき。
