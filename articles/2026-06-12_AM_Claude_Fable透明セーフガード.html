Claude Fable 5の透明なセーフガード運用

要約

Anthropic は 2026年6月9日、Claude Fable 5 と Claude Mythos 5 を発表した。Fable 5 は一般提供される Mythos-class モデル、Mythos 5 は同じ基盤モデルから一部セーフガードを外した限定提供版という構成。

前日に作成したノートでは、Fable / Mythos の提供階層、refusal、fallback、30日データ保持を中心に整理した。今回はその後に出た「隠れたセーフガード」批判と、Anthropic が透明性を高める方向へ修正した点を追記観点として見る。

重要なのは、フロンティアモデルの安全運用が「拒否するか、しないか」だけではなく、「ユーザーに安全制御が発動したことを見せるか」「代替モデルへ流したことをどう説明するか」というプロダクト設計の問題になっていること。

背景

公式発表では、Claude Fable 5 はサイバーセキュリティ、バイオ、化学、モデル蒸留など一部の高リスク領域で、Fable 5 がそのまま回答せず Claude Opus 4.8 へフォールバックする設計とされていた。Anthropic は、この安全分類器が平均で5%未満のセッションに発動すると説明している。

Claude API Docs では、Fable 5 の refusal は HTTP 200 の正常応答として返り、stop_reason: "refusal" と分類器情報をアプリ側で扱う必要があると説明されている。また、Fable 5 / Mythos 5 は 30日データ保持の Covered Models とされ、ゼロデータ保持では使えない。

その後、モデル蒸留関連の安全制御で、ユーザーに明示せず出力を劣化・変更する設計が批判された。The Verge の報道によると、Anthropic はこの判断を謝罪し、蒸留関連のクエリでも Opus 4.8 へのフォールバックを明示する方向へ変えるとしている。

何が重要か

1. セーフガードはUI/ログ設計まで含めて評価する

論点見えない制御見える制御
ユーザー体験一見スムーズだが、出力品質低下に気づきにくい拒否やフォールバックが見えるため納得しやすい
評価・検証ベンチマークや研究評価を歪める可能性があるどの条件で制御されたか記録しやすい
悪用対策制御条件を推測されにくい回避探索の対象になりやすい
業務運用隠れた品質差が事故原因になり得る監査ログ、説明責任、再実行判断に乗せやすい

Fable 5 の件は、単に Anthropic 固有の炎上ではなく、今後の高性能AI全般に出る問題。強いモデルほど安全制御が複雑になり、アプリ利用者は「モデルが答えた」と思っていても、実際には別モデル・別ポリシー・別品質の出力を受け取る可能性がある。

2. API利用では refusal をエラーではなく分岐として扱う

Fable 5 の refusal は通信失敗ではない。HTTP 200 で返る正常なモデル判断なので、アプリ側では次のような分岐を持つ必要がある。

  • refusal が返ったら、画面とログに理由カテゴリを残す
  • Opus 4.8 など代替モデルへ送る場合、ユーザーへモデル変更を明示する
  • 高リスク領域の入力は、業務上必要なものと危険なものを分けて扱う
  • refusal / fallback の頻度をメトリクス化し、プロンプトや業務設計を見直す
  • 自動再試行で、同じ危険な文脈を必要以上に別モデルへ渡さない

これは、チャットUIだけでなく、エージェント、コードレビュー、セキュリティ調査、社内ナレッジ検索にも関係する。

3. 「強いモデルを使う権利」は用途と信頼度で分かれる

モデル位置づけ自分の運用での見方
Claude Fable 5一般提供される高性能レーン長時間調査、コード改修、複雑な整理に使う。ただし拒否・データ保持前提
Claude Mythos 5Project Glasswing など限定提供サイバー防衛や研究の信頼済みアクセス例として観察する
Claude Opus 4.8Fable拒否時の受け皿高リスク領域では現実的な代替先。品質差をログに残す

モデル能力が上がるほど、全員に同じ能力を同じ条件で出す設計は難しくなる。今後は「一般公開モデル」「信頼済み研究者向け」「政府・重要インフラ向け」「社内限定」などの階層が普通になる可能性が高い。

4. データ保持と透明性は企業導入の足切りになる

Fable 5 / Mythos 5 は高性能だが、API Docs 上は30日データ保持が前提になっている。コード、顧客情報、脆弱性情報、未公開設計を扱う企業では、性能より先にここで止まることがある。

さらに、見えないセーフガードがあった場合、業務監査では「なぜこの出力になったか」を説明しづらい。AIを基幹業務やセキュリティ運用に入れるなら、モデル名、拒否理由、fallback先、データ保持条件をログに残すことが最低ラインになる。

自分向けメモ

  • Fable 5 は「最強モデル」ではなく、「安全制御込みで運用する高性能実行環境」として見る。
  • 自分のOpenClaw / Obsidian / コード作業に置き換えるなら、モデル切替、拒否、再試行、出典ログを見える形で残す設計が重要。
  • 調査ノート作成では、モデルが出した答えより「どの情報源を根拠にしたか」「どこで安全制御が入ったか」を残す方が将来役に立つ。
  • SAP / ERP 領域では、Business AI やエージェントを導入するときに、基幹データを30日保持モデルへ渡してよいかが先に問題になる。
  • セキュリティ領域では、防御目的の調査でも分類器に当たりやすい。正当業務の妨げになるなら、信頼済みアクセスや専用環境が必要になる。
