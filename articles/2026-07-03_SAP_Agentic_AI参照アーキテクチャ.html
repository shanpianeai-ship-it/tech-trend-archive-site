2026-07-03 SAP / ERP importance: high
Summary

SAP公式のAgentic AI参照アーキテクチャを、Joule、Agent Gateway、A2A、MCP Gatewayの役割分担から読む。ERPエージェントを本番運用へ載せる際の接続・統制・監査ポイントが見える。

SAP Agentic AI参照アーキテクチャはERPエージェントの接続境界を示している

要約

2026年5月更新のSAP Architecture Center「Agentic AI & AI Agents」は、SAP BTP上でJoule、Joule Studio、SAP Cloud SDK for AI、Generative AI Hub、SAP Cloud Identity Services、A2A、MCPを組み合わせる参照アーキテクチャを示している。Jouleをユーザー接点兼オーケストレータとして置き、ローコードのJoule StudioとプロコードのSAP Cloud SDK for AIを分け、SAP内外のエージェントやツールを接続する設計だ。

今回の夜枠Discordポールでは、対象ポールの poll.results.answer_counts が空で投票がなかったため、候補一覧から選定基準に沿って6番「SAP Agentic AI参照アーキテクチャ」を採用した。理由は、日本語圏ではJouleやSAP Business AIの紹介は多い一方で、A2A、MCP Gateway、Agent Gateway、片方向通信の制約まで含めたアーキテクチャ解説はまだ薄いからだ。

結論として、これは「SAPもAIエージェントをやる」という一般論ではなく、ERPエージェントを本番業務へ接続する時の境界設計資料として読むべきものだ。SAPはA2Aをエージェント間連携、MCPをツール接続に使い分け、ID・権限・監視・ガバナンスをSAP Cloud Identity ServicesやIntegration Suite側に寄せようとしている。ただしAgent GatewayはまだGAではなく、現時点の参照アーキテクチャは片方向通信の過渡期である点を前提に置く必要がある。

背景

SAPは2026年に入って、Jouleを単なるCopilotではなく、業務プロセスへ接続するエージェント実行面として押し出している。Joule Studio、SAP Business AI Platform、SAP Knowledge Graph、SAP Business Data Cloud、SAP Cloud SDK for AIといった部品は、いずれも「ERPの業務文脈をAIエージェントが使えるようにする」方向の構成要素だ。

今回の参照アーキテクチャでは、Jouleが中心に置かれる。Jouleはユーザーインターフェースであり、会話管理とオーケストレーションの役割も持つ。カスタムエージェントはSAP BTP上に作られ、SAP S/4HANA、SuccessFactors、Business Data Cloud、Concur、Customer Experience、Business NetworksなどのSAP Cloud Solutionsや、外部クラウド・外部エージェント・外部APIと接続する。

開発経路は大きく2つある。ローコード側はJoule Studioで、視覚的な設定や自動登録、管理されたランタイムを使う。プロコード側はSAP Cloud SDK for AIで、PythonやTypeScriptからLangGraph、AG2、CrewAI、Smolagentsなどを使い、A2AプロトコルでJouleへ接続する。

何が重要か

A2AとMCPを同じものとして扱わない設計になっている

SAP Architecture Centerの「A2A and MCP for Interoperability」は、A2AとMCPの役割を明確に分けている。A2Aは自律エージェント同士の委譲や協調、MCPはエージェントが外部ツールやAPIを発見・実行するための接続規格として扱われる。

観点A2AMCP
主な対象エージェント同士の通信ツール、API、データソース
SAP内の位置づけJouleと外部/カスタムエージェントの連携Joule Agentsや外部エージェントのツール利用
典型用途タスク委譲、能力照会、複数エージェント協調OData、REST API、Integration Flow、外部MCP Serverの利用
統制ポイントAgent Gateway、IAS App2App、A2A endpointIntegration Suite MCP Gateway、認証、レート制限、監視

この分離はかなり重要だ。ERP運用では、エージェントを増やすことよりも、誰がどのツールを呼べるか、どのシステムに書き込めるか、結果をどう監査できるかが問題になる。A2AとMCPを分けて設計すれば、「エージェントの委譲」と「業務APIの実行権限」を別々に統制できる。

Agent Gatewayは有望だが、まだ過渡期である

参照アーキテクチャは、Agent Gatewayがまだ一般提供ではなく、現在の構成では片方向のアウトバウンド通信のみをサポートすると明記している。つまり、外部システムからSAP管理のJoule Agentsを本格的に双方向利用する構成は、ロードマップ込みで読む必要がある。

一方で、設計思想ははっきりしている。Agent Gatewayは、外部クライアントや外部エージェントがA2AでJoule Agentsを利用する入口になる。SAP管理ドメイン上の外部到達可能なエンドポイント、A2A 0.3.0、HTTP+JSON transport、SAP Cloud Identity ServicesのIAS App2App tokens、named user context、長時間実行向けのcallback型応答が構成要素として示されている。

領域現時点で見るべきこと
可用性Agent Gatewayは未GA。導入計画では正式提供時期と制約確認が必要
通信方向参照アーキテクチャ上は過渡期。双方向A2Aを前提にしすぎない
認証IAS App2App、named user context、外部エージェントの信頼関係
実行方式同期応答だけでなく、長時間タスクのcallback設計が必要
監査外部からどのJoule scenarioが呼ばれ、誰の文脈で実行されたか

Basis/アーキテクト目線では、ここを「便利なAI連携入口」と見るだけでは足りない。外部からERP文脈のエージェントへ入る境界なので、API Gateway、Cloud Connector、Integration Suite、BTP Destination、監査ログと同じ重さで設計する必要がある。

MCP GatewayはIntegration Suiteの役割をAIツール統制へ広げる

SAPはMCP GatewayをSAP Integration Suiteの中に位置づけている。これは、SAP API、非SAP API、外部MCP Server、Integration Flow、データソースを、AIエージェントが利用できるMCP準拠ツールとして公開・管理する構想だ。

重要なのは、MCP Gatewayが単なる接続アダプタではなく、顧客管理の統制面として説明されている点だ。認証・認可、OIDC、レート制限、ペイロード保護、トラフィック管理、監視、トレーシング、分析が並んでいる。これは、従来のIntegration Suite運用を「AIエージェントがツールを呼ぶ世界」に拡張する話に近い。

従来のIntegration Suite観点MCP Gatewayで追加される観点
システム間IF、API公開、変換、ルーティングAIエージェントに公開するツール定義
API利用者や連携先システムの認証エージェント単位、利用者文脈、ツール権限
メッセージ監視、エラー再処理エージェントがどの理由でどのツールを呼んだか
IF仕様書、マッピング、SLAtool manifest、入出力schema、プロンプト依存の実行条件

ERP側の実務では、MCP Gatewayに公開してよいAPIと、公開してはいけないAPIを分ける棚卸しが必要になる。読み取り専用、通知、照会、チケット起票のような低リスク操作から始め、伝票登録、マスタ変更、支払、購買承認のような高リスク操作は、人間承認や追加検証を挟む設計が現実的だ。

ローコードとプロコードの二層運用になる

Joule Studioは、SAP Buildの中でローコードにエージェントを作る導線として説明されている。一方でSAP Cloud SDK for AIは、Python/TypeScriptや外部エージェントフレームワークを使うプロコード導線だ。SAPはこの2つを競合ではなく補完関係として置いている。

開発経路向いている用途運用上の注意
Joule Studio定型的な業務エージェント、RAG、SAP標準寄りの業務支援設定変更、利用権限、業務部門による作成範囲
SAP Cloud SDK for AI独自推論、外部フレームワーク、複雑なマルチエージェント処理コード管理、CI/CD、脆弱性管理、実行環境
MCP GatewayAPIやIntegration Flowのツール化ツール公開範囲、監視、レート制限、schema管理
Agent Gateway/A2A外部エージェント連携、Joule Agentsの外部利用未GA制約、IAS trust、callback、監査

この二層化は、ERP組織の役割分担にも影響する。業務部門やCoEがJoule Studioでエージェントを作り、IT/Basis/開発チームがSDK、A2A、MCP Gateway、Integration Suiteを管理する形になりやすい。結果として、エージェントの棚卸し、所有者、権限、変更履歴、実行ログ、廃止判断を管理する台帳が必要になる。

自分向けメモ

  • SAPのエージェント戦略は、Jouleを入口にしてA2Aでエージェントをつなぎ、MCP Gatewayでツール/APIを統制する方向に整理されつつある。
  • 「MCPを入れればSAP連携できる」ではなく、Integration Suite側でどのAPIをMCP toolとして公開するかが本番設計の焦点になる。
  • Agent Gatewayは未GAで片方向制約もあるため、今すぐ本番計画に組み込む場合はPoC前提で制約確認が必要。
  • SAP Basis/ERP運用では、従来のジョブ監視、IF監視、API管理に加えて、エージェント、ツール、プロンプト、モデル、実行ユーザー、callback URLを監査対象にする必要がある。
  • 最初の導入対象は、読み取り、要約、例外分類、通知、チケット起票までに絞るのが現実的。更新系・承認系は人間確認と二重実行防止を先に設計する。
