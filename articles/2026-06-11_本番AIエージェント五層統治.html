Summary

Five-Plane Reference Architecture論文は、本番AIエージェントを単なるモデル出力ではなく、企業システムに対する委任実行主体として統治する枠組みを示す。

本番AIエージェント五層統治

要約

arXiv に投稿された "A Five-Plane Reference Architecture for Runtime Governance of Production AI Agents" は、本番AIエージェントを「モデル出力」ではなく「企業システムに対する委任された実行主体」として統治する参照アーキテクチャを提案している。

中核は、reasoning plane が意図、委任チェーン、セッション状態を一度だけ判定し、その判定を network / identity / endpoint / data の4つの実行面へ投影する設計。従来の「APIリクエスト単位」「単一ユーザー単位」「allow / deny 単位」の認可では、エージェントの連続行動、委任、ツール連鎖、監査証跡を扱い切れないという問題意識がある。

自分向けには、OpenClaw / Codex / MCP のようなツール実行型エージェントを業務利用する時に、どこで止めるか、どこで権限を細らせるか、どの証跡を残すかを設計するための地図として有用。

背景

企業セキュリティは長く、データ境界とリクエスト境界を守る形で発展してきた。ネットワーク境界、アプリ境界、DLP、IAM、ゼロトラスト、サービスメッシュなどは、基本的には「誰が、どのリソースへ、どの通信でアクセスするか」を判定する。

本番AIエージェントでは、守る対象が少し変わる。エージェントは文書を読み、検索し、ツールを呼び、別エージェントへ委任し、メールやチケットやERPのような systems of record を更新する。単発のアクセスが許可されていても、連続した行動全体としては許可されていない業務変更や情報流出になる。

論文はこのズレを、既存のポリシーエンジンの5つの不足として整理している。

不足従来型エージェントで必要なもの
単位単発リクエスト実行計画と行動列
主体単一principal人間、planner、executor、toolを含む委任チェーン
権限絶対的なscope委任ごとに狭まるcapability
状態ステートレスセッション内で読んだデータや過去判断
結果allow / denypause, escalate, narrow, modify, defer, rollback

つまり、モデルの安全性やプロンプト防御だけではなく、実行時の行動統治レイヤーが必要になる。

何が重要か

1. 五層モデルは「判断」と「実行」を分ける

この論文の五層は、1つの reasoning plane と4つの infrastructure plane で構成される。

Plane役割既存基盤で近いもの
Reasoning意図、計画、委任チェーン、状態を判定policy engine, orchestrator, agent runtime
Network接続先、mTLS、rate limit、通信制御firewall, service mesh
Identity短命credential、scope、委任された権限IdP, OAuth/OBO, token service
Endpoint実行環境、姿勢、attestationEDR, container/runtime policy
Data取得候補、分類、lineage、residencyDLP, data catalog, access gateway

ポイントは、各planeがバラバラに判断しないこと。Reasoning plane が「このエージェントのこの行動は、この委任権限と状態で許可できるか」を一度判定し、その結果を各planeが実現する。監査証跡も1つの構造化された evidence record として束ねる。

これはゼロトラストの延長として読むと分かりやすい。ゼロトラストは信頼判断をネットワーク境界からリクエスト境界へ寄せた。五層アーキテクチャは、さらにエージェントの「次の実行ステップ」へ寄せる。

2. 「止める場所」が7つある

論文は stop-anywhere mediation として、エージェントの実行ループに7つの介入点を置く。

介入点何を見るか効く脅威
MP1 Plan formation計画全体、連鎖効果prompt injection, tool chain abuse, workflow改変
MP2 Context retrieval取得候補、検索範囲connector overreach
MP3 Tool selection使うツール過剰ツール権限
MP4 Argument generationtool引数生ID、外部宛先、危険パラメータ
MP5 Action commit実際の副作用直前最後の阻止点
MP6 Output returntool応答汚染された応答、次計画への混入
MP7 Audit emission証跡の完全性監査不能

多くの現行エージェント基盤は MP5、つまり tool call の直前でしか止めにくい。だが、危険な行動は計画段階で見た方が安いし、読み取り範囲は取得前に絞った方が安全。MP1やMP2をランタイムが露出できるかが、今後のエージェント基盤の差になる。

3. allow / deny だけでは足りない

本番運用では、全てを許可するか止めるかだけでは使い物にならない。論文は6つの interruption primitive を挙げる。

Primitive意味実務例
Pause条件が解決するまで一時停止最新権限の再評価待ち
Escalate人間や上位権限へ承認依頼高額返金、外部送信、デプロイ
Narrow権限を狭めて続行mailbox全体ではなく1スレッドだけ許可
Modify計画、検索、引数、応答を書き換えraw IDをtoken化、外部宛先を社内宛へ変更
Defer後続条件が満たされるまで延期endpoint posture確認待ち
Rollback副作用を補償して戻すデプロイrollback、レコード更新取り消し

特に Narrow はMCP運用と相性がよい。MCPサーバやコネクタは広い権限を持ちがちなので、タスク単位で「今回だけ読める範囲」を狭める設計が必要になる。

4. 委任チェーンを明示する

論文の composite principal は、単に「誰が呼んだか」ではなく、誰から誰へ権限が委任されたかを順序付きチェーンとして持つ。

例:

``text human -> planner agent -> executor agent -> tool host ``

各ステップの capability set は親の capability set の部分集合でなければならず、実効権限はチェーン全体の積集合になる。途中のエージェントが侵害されても、親から委任されていない権限を突然持てない。

これは confused deputy 問題への対策としても重要。強い権限を持つツールやエージェントが、弱い権限の依頼者に誘導されて強権限を使ってしまう事故を、委任チェーンの交差で抑える。

5. 対象脅威が実務に近い

論文は、以下の7つを本番エージェントの主要脅威として挙げている。

脅威ざっくり内容自分向けの読み替え
T1 Indirect prompt injection読み取った文書やtool応答が計画を汚染Web検索、メール、Obsidian、添付ファイルに混じる指示
T2 Tool chain abuse個別には合法な操作列が全体では危険読むのはOK、外部送信もOK、でも同一文脈の組合せはNG
T3 Connector overreach必要以上に広い範囲を読むDrive全体、メールボックス全体、Vault全体を読ませる問題
T4 Approval evasion承認が必要な効果を別経路で達成送金ではなく権限変更や値引きで実質同じ効果
T5 Delegation chain exploitation委任途中で権限が膨らむsubagentが親より強い操作を持つ
T6 Audit opacity後から再構成できない「なぜ送ったか」「何を読んだか」が分からない
T7 Workflow integrity loss業務プロセス自体が変わるERP伝票、承認、デプロイ、顧客対応の流れが変質

この分類はかなり実務寄り。特にT2とT7は、単純なアクセス制御では見落としやすい。

自分向けメモ

  • OpenClaw/Codex運用では、ツール実行前の確認だけでは不足。候補選定、ファイル読み取り、外部送信、Git操作、Discord投稿の各段階を別の介入点として見る。
  • MCPサーバは「便利なコネクタ」ではなく、権限を持つ実行面。タスクごとの Narrow、短命credential、監査証跡が必要。
  • サブエージェントへ任せる時は、親の権限をそのまま渡さない。ファイル範囲、ネットワーク、書き込み先、外部送信可否を明示的に狭める設計が要る。
  • SAP/ERP領域では、AIエージェントが伝票、マスタ、承認、ジョブ、移送を触るなら、単一API認可では足りない。プロセス全体としての許可、承認、rollback、監査を設計する必要がある。
  • ただし、論文自身も限界を明示している。参照実装はpolicy-engine coreの検証で、ライブエージェントベンチマークでのフルシステム評価は今後。MP1を露出しない既存ランタイムでは防御価値が落ちる。
  • 一番大事な実装論点は「計画形成フック」。エージェントが何をしようとしているかを構造化して出せないと、結局MP5のtool call直前チェックに戻ってしまう。
