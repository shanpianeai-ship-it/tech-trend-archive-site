2026-07-02 Security importance: high
Summary

@redhat-cloud-services npm侵害は、正規CIで作られたSLSA provenance付き成果物でも、侵害済みパイプラインなら悪性になり得ることを示す。

Red Hat npm SLSA provenanceの落とし穴

要約

Unit 42は、2026-06-01に@redhat-cloud-services npm名前空間の少なくとも32パッケージが侵害され、Miasmaと呼ばれるペイロードが配布されたと整理している。攻撃者は侵害したRed Hat従業員のGitHubアカウントを使い、RedHatInsights配下のリポジトリへ不正コミットを入れ、GitHub Actions経由で悪性パッケージを公開した。

この件で一番重要なのは、悪性パッケージに有効なSLSA provenanceが付いていた点。provenanceは「どのビルド基盤が、どの入力・ワークフローで成果物を作ったか」を検証する材料だが、「そのワークフローや入力が侵害されていなかった」ことまでは自動的に保証しない。

自分向けには、署名、SLSA、trusted publishingを「安全判定の終点」ではなく、「調査を始めるための証跡」として扱うべき案件。CI/CDの権限、OIDC subject条件、install-time実行、公開直後の依存取り込みをセットで見ないと、正規経路のまま悪性コードを配れる。

背景

Red Hat公式bulletinでは、2026-06-01に@redhat-cloud-services配下の複数npmパッケージでサプライチェーン侵害が公表され、初期調査として侵害されたGitHubアカウントからRed Hat GitHub organization内のパッケージへ悪性コードが注入されたと説明している。

Red Hatは、影響パッケージはHybrid Cloud ConsoleのWeb UIで使われるフロントエンドJavaScriptライブラリであり、侵害期間中にHybrid Cloud Consoleのリリースは行われておらず、console.redhat.comへのデプロイ前にinstall-time scriptsを取り除く保護もあるとしている。したがって、Red Hatの顧客向け本番サービス障害としてではなく、該当npmパッケージを開発端末やCIで取得した場合の開発・ビルド環境侵害として読むのが妥当。

一方、Wiz、JFrog、Unit 42などの解析は、攻撃の技術的意味をより広く捉えている。MiasmaはMini Shai-Hulud系の手口を引き継ぎ、npm install時に実行されるコードでGitHub、npm、クラウド、Kubernetes、Vault、CI/CD関連の認証情報を狙う。さらに、正規のGitHub Actions OIDC経路を使ってnpmへ公開したため、成果物にvalid SLSA provenanceが付いた。

何が重要か

provenanceは「経路の証明」であって「内容の善性」ではない

SLSA provenanceは、成果物がどのビルド定義、入力、ビルダー、実行情報から作られたかを記録する。これは改ざん検知や再現性、ポリシー検証に有効だが、信頼の前提はビルド基盤と入力が想定どおりであることに置かれる。

今回のように、正規リポジトリや正規ワークフロー側が侵害されると、「確かにそのCIで作られた」という証明と、「作られたものが悪性である」という事実が両立する。

観点provenanceが言えることprovenanceだけでは言えないこと
出所どのビルダー、ワークフロー、入力から作られたか入力やワークフローがレビュー済みだったか
完全性公開物と証跡の対応build中のキャッシュ、依存、runner状態が健全だったか
ポリシー許可されたbuilderかそのbuilderを起動できる人・branch・workflowが適切だったか
監査事故後に追跡しやすい事故そのものを必ず防ぐ

この差分を誤ると、「SLSA付きだから安全」「trusted publisherだから安全」という雑な許可ルールになり、侵害済みCIから出た悪性パッケージを自動的に通してしまう。

OIDC trusted publishingは権限の細粒度設計が本体

npmのtrusted publishingやGitHub Actions OIDCは、長期npm tokenを減らせるので導入価値は高い。ただし、実務上の安全性は「どのworkflow、branch、environment、repository ownerから発行されたOIDCを信頼するか」に依存する。

Wizの解析では、不正コミットに含まれた最小workflowがid-token: writeを要求し、npm公開に使えるOIDCトークンを得ていた。ここで重要なのは、OIDC自体が壊れたのではなく、OIDCを発行できる条件と、それをnpm側が信頼する条件が攻撃者に利用されたこと。

設計項目弱い設定の例強めたい設定
branch条件任意branchのpushで公開可能protected branchやrelease tagだけ許可
workflow条件どのworkflowでもid-token発行公開専用workflow名に限定
environment承認なしでpublishprotected environmentと手動承認
repo権限広い書き込み権限release担当者とbotを分離
npm側信頼repository単位で広く信頼workflow、branch、tag条件まで絞る

つまり、OIDCは「tokenを置かなくてよい」仕組みであって、「誰が何を公開できるか」を代わりに設計してくれる仕組みではない。

install-time実行は依存更新の最大リスク面になる

JFrogの解析では、影響パッケージは正規の@redhat-cloud-services名前空間にあり、悪性コードはアプリケーションがimportする前、npm lifecycle hookの段階で実行される。型定義やフロントエンド部品のように見えるパッケージでも、preinstallやbinding.gyp経由でコード実行面になり得る。

リスク面なぜ危険か実務対策
preinstallinstallだけでコードが動くCIで--ignore-scriptsを検討、例外制にする
大きな難読化JS型・小型パッケージでは異常パッケージサイズ差分を監視
公開直後の最新版検出前にCIへ入るregistry proxyのcooldownを置く
正規namespacereputationで通りやすい名前空間ではなく挙動で見る
CI runnersecretsとクラウド権限が集まるegress制御、短命runner、secret最小化

依存更新PRのレビューでは、ソース差分だけでなく、公開tarball、lifecycle scripts、package size、provenance、publish元workflowをまとめて見る必要がある。

「署名済み悪性物」を前提に検知を組む

今回の教訓は、署名やprovenanceを捨てることではない。むしろ、署名やprovenanceを使って「どの正規経路が悪用されたか」を素早く絞るべき。ただし、自動許可の唯一条件にしてはいけない。

実務では次の組み合わせが必要になる。

  • provenance検証: 許可されたbuilder、workflow、branch、tagかを見る。
  • パッケージ挙動検査: lifecycle scripts、binding.gyp、難読化、大幅なサイズ増加を見る。
  • runner監視: npm install中のnode、bun、curl、unzip、外部通信を追う。
  • secret管理: npm、GitHub、cloud、Vault、CI tokenを短命化し、利用ログを取る。
  • 取り込み遅延: 公開直後のバージョンを即時に本番CIへ入れない。

自分向けメモ

  • SLSA provenanceは「信頼してよいか」の答えではなく、「どのビルド経路を検証すべきか」の索引として扱う。
  • GitHub Actions OIDCは、sub条件をrepositoryだけでなくbranch、tag、workflow、environmentまで絞る。任意branchからid-token: writeを出せる構成は危険。
  • npm依存更新では、GitHubのソースだけでなくnpm tarball側を見る。公開物にだけ混入する攻撃がある。
  • CIではnpm ci --ignore-scriptsを標準にできる領域を分け、必要なinstall scriptだけ例外許可する。
  • 開発端末も侵害面に含める。ローカルnpm installでGitHub CLI token、cloud CLI設定、SSH key、.envが抜かれ得る。
  • SAP/BTPや企業向けフロントエンド運用では、UI部品やAPI clientのnpm依存がBasis運用の外に置かれがち。S/4やBTP本体だけでなく、管理画面・拡張アプリ・CIテンプレートの依存も棚卸し対象にする。
  • 票なし時の自動選定としてこの候補を選んだ理由は、6/9の初報から一歩進めて、provenance/署名/CI信頼境界の運用判断に落とせるため。
