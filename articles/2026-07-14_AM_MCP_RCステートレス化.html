MCP RC（2026-07-28）候補は、セッションID固定前提のMCPをステートレス化し、通常HTTPインフラでの水平分散と監査設計を同時に進める改訂版。導入設計判断を先行しておきたい実務者向けの価値が高い。

MCP RC 2026-07-28 (Release Candidate): ステートレス化での運用転換

要約

Model Context Protocol（MCP）の次期仕様 RC は、Mcp-Session-Id に依存した接続固定方式を撤廃し、HTTPヘッダ主導で任意インスタンスに振り分け可能なステートレス化を採用した。加えて、MCP Apps/Tasks を拡張枠へ切り出し、OAuth/OIDC 連携に沿った認可強化、公式な機能データ管理方針をまとめている。結果として、

  • セッション共有ストレージや粘着ルーティングへの依存を下げられる
  • 長期実行処理やUIを含む拡張を、コア変更と分離して進化させやすくなる
  • 脆弱性低減に効く監査・トレーサビリティ方針を設計しやすくなる

の3点が同時に進む、基盤設計上の大きい変更である。

背景

記事（The 2026-07-28 MCP Specification Release Candidate）では、2025-11-25系のinitializeで開始するセッション前提からの脱却が中心テーマ。

  • 以前: POST /mcp 呼び出し後に Mcp-Session-Id が返る前提で、同一インスタンスへのルーティングが実質要件だった。
  • 変更後: MCP-Protocol-Version と Mcp-Method、Mcp-Name を明示する単発リクエスト構造に移行し、tools/call などの操作がインスタンス横断で処理可能。

同記事では、同時に Extensions framework（ext-*）、Tasks、MCP Apps の公式化、OAuth/OIDC への適合を意識した認可仕様の明文化、廃止ポリシー（Active/Deprecated/Removed）を導入したとされる。

何が重要か

1. 運用のボトルネックを減らす基盤変更

ステートレス化は、MCP の水平スケール構成を単純化し、従来必要だった「セッションID固定＋共用状態」依存を下げる。

観点旧版（2025-11-25前提）RC（2026-07-28候補）
ルーティングセッション固定寄りMcp-Method/Mcp-Nameで本文前提にしないヘッダルーティング
共有状態接続ごとの状態を保持しやすい構成_meta等のリクエスト内情報で文脈を受け渡し
障害時運用柔軟な自動フェイルオーバを組む場合は設計が複雑化LB での振り分け設計がしやすい

2. 長期実行/対話を拡張で扱える

Tasks を拡張に寄せることで、実験的な拡張機能とコア仕様の更新を分離し、運用側は必要機能のみ有効化して更新速度を上げやすくなる。

3. セキュリティ・監査面の整備

  • iss 検証など OAuth/OIDC 近い実運用強化
  • traceparent など追跡キーの標準化
  • 非推奨化の期限付き運用が追加され、削除時の移行設計が可能

これにより、PoCだけでなく本番導入を想定した監査観点まで視野を広げられる。

4. 選定しやすさの観点

本選定は1時間後ポーリング時点で poll.results.answer_counts がすべて 0 のため、 運用ルールの選定基準（公式性・将来性・実装価値）に照らして候補1を採用。

自分向けメモ

  • まずインフラ側で、これまで前提としていた sticky session 条件を排し、Mcp-Method ベースの経路制御設計へ寄せる。
  • 既存サーバ/クライアントの initialize 前提は、移行チェックリストで明示して段階的互換を取る。
  • tools/call の状態引き継ぎはセッション隠蔽ではなく、明示ハンドル（例: basket_id）で扱う設計に置き換える。
  • タスク長期化が増える導線では、監査ログ/トレース ID の付与ルールを先に決める。
