2026-07-13 Security importance: high
Summary

Coder AI Bridge Proxyが既定設定でTLS検証を無効化し、AIエージェント連携経路のトラフィックが中間者攻撃に晒されると、トークンやプロンプト・レスポンスが窃取され得る脆弱性。

GHSA-84rm: Coder AI Bridge TLS検証不備

要約

Coder の AI Bridge Proxy（aibridgeproxyd）は、v2.30.0 以降のデフォルト設定で TLS 検証用トランスポートの初期化が不十分で、特定条件下ではサーバ証明書を厳密に検証しません。結果として、AI Bridge と Coder 本体間の HTTPS 通信が、同一ネットワーク上の中間者により盗聴・改ざんされるリスクが生じます。

脅威成立時には Coder のセッション情報やユーザー提供の API キー（BYOK）に加え、プロンプト/レスポンス本文まで取得可能で、AI連携基盤の秘密情報が一気に露出します。GitHub Advisory の公開情報では、リリース v2.32.7, 2.33.8, 2.34.2 で修正済みであり、現状は運用環境のバージョン確認とネットワーク境界見直しが優先です。

背景

AI Bridge Proxy は Coder のエンタープライズ向けAI連携を単純化する反面、運用上の初期設定がセキュリティ境界に直結します。公開情報では、デフォルトの transport 設定で InsecureSkipVerify: true が使われ、上流プロキシ設定の有無によって secure transport の適用挙動が分岐していたことが指摘されています。

重要なポイントは「デフォルト構成そのもの」が危険で、管理者が意図的に緩く設定しなくても、環境変数 HTTP_PROXY / HTTPS_PROXY や誤設定経路の影響で通信誘導が可能という点です。さらに、同じネットワーク内でAI BridgeとCoderが loopback 接続される構成では影響が小さい一方、社内ネットワーク越しで分離された導線だと MITM 成立条件が現実的になります。

何が重要か

観点脆弱性で起きる事想定される影響
通信安全TLS 検証無効化機密情報の傍受・改ざん
情報漏えいセッションID・トークン・BYOK不正利用、外部データ取得
操作リスクプロンプト/実行結果窃取実行内容推定、攻撃面拡大
運用工数リモート接続での再設定パッチ適用 + 設定監査が必須

この脆弱性は直接RCE等を即起こすものではありませんが、AI エコシステムの中核となる認証情報を経路上で奪取されるという点で、実務インパクトは大きいです。特に複数AIツールが同じ実行基盤を共有する環境では、一本の脆弱なプロキシが横断的な情報流出導線になります。

自分向けメモ

  • Coder 導入環境は github.com/coder/coder の該当バージョンを確認し、少なくとも 2.34.2 / 2.33.8 / 2.32.7 以降へ更新。
  • aibridgeproxyd を公開ネットワーク越しで使う場合、必ず経路を再評価し、可能なら loopback / mTLS / 通信経路監視を前提にする。
  • 環境変数由来の Proxy 設定 (HTTP_PROXY, HTTPS_PROXY) をインベントリ化し、意図しない再送先を許可しない。
  • AI Bridge が扱うプロンプト・レスポンスは社外情報資産扱いとして、ログ保全と token/権限ローテーション計画を明文化する。
  • 既存運用の「AIツール用APIキーを使う前提」を前提として、ネットワーク制御（DNS, ARP 保護, VLAN 分離）を優先順位に加える。
