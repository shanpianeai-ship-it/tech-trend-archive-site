SAP Cloud ERP横断セキュリティ設計

要約

SAP Communityの公式ブログは、現代のSAP Cloud ERPセキュリティを「S/4HANA Cloud Privateだけを守る話」ではなく、SAP BTP、SaaS、Integration Suite、AI、クラウド基盤まで含む多層ランドスケープの統制問題として整理している。

重要なのは、各サービスに個別のセキュリティモデル、管理方法、ID/権限、運用責任があるため、ひとつのレイヤーの統制が自動的に他レイヤーへ効くわけではない、という指摘。特にJouleやSAP Business AIのようなAI機能が入ると、プロンプト、検索文脈、モデル呼び出し、AI支援アクションが新しいデータフローになる。

Basis/ERP運用目線では、これは「Cloud ERPはSAPが運用するから安全」という話ではない。認証、認可、ログ、データ分類、契約、監査証跡を、SAPアプリ横断でどう確認するかという実務設計の話になる。

背景

SAP Cloud ERP環境は、単一システムではなくなっている。典型的には、SAP Cloud ERP Private、SAP BTP、SuccessFactorsやAribaなどのSaaS、Integration Suite、SAP AI Foundation、Joule、生成AI Hub、外部ID基盤、非SAPシステムが組み合わさる。

この構成では、縦方向の防御と横方向の統制を分けて考える必要がある。縦方向は、各レイヤーをアプリケーションからインフラまで守る見方。横方向は、ID、ログ、暗号化、プライバシー、監査、インシデント対応をサービス横断でそろえる見方。

SAP Trust CenterのCloud ERPセキュリティページでも、ネットワーク、クラウドセキュリティ態勢管理、脅威・脆弱性管理、事業継続、データ保護、ログ監視、規制対応、インシデント対応、IAMがCloud ERPの主要セキュリティ領域として示されている。つまり、ERP移行後の運用論点はBasisだけで閉じず、クラウド運用、ID管理、契約・監査まで広がる。

何が重要か

境界はシステム単位ではなく責任単位で見る

記事では、SAP Cloud ERPの典型的な構成を6つのレイヤーに分けている。運用設計では、このレイヤーごとに「誰が何を守るのか」を明示する必要がある。

レイヤー典型範囲主な確認点
AI / IntelligenceJoule、SAP Business AI、AI Foundation、生成AI Hub、Joule Studioプロンプト、grounding、検索文脈、モデル経路、保持、契約、監査
SAP SaaSSuccessFactors、Ariba、Concur、Fieldglass、CXなどテナント分離、管理者権限、ロール、データ所在地、監査レポート
Integration SuiteCloud Integration、API Management、Event Mesh、証明書、destination資格情報、証明書、payload、API scope、イベント購読
Core ERPSAP Cloud ERP Private、S/4HANA、ECS管理コンポーネントBasis、DB、OS、network、backup、変更、監視、顧客設定の責任分界
SAP BTPsubaccount、extension、Datasphere、SAC、Build、AI Foundationentitlement、destination、secret、audit log、custom code、接続
Cloud InfrastructureSAP運用またはSAP管理のDC/hyperscalerリージョン、冗長化、backup、物理/ネットワーク、コンプライアンス

ここでの実務ポイントは、「SAPが運用する範囲」と「顧客が設計・設定・判断する範囲」を混ぜないこと。ECSやSaaSでは基盤運用はSAP側に寄るが、業務ロール、承認、データ分類、カスタムコード、接続先、監査解釈は顧客側に残る。

AIはUI機能ではなくデータフローとして扱う

JouleやSAP Business AIを有効化すると、ユーザーが見ている画面の裏で、プロンプト、回答、検索文脈、モデル選択、外部/内部モデル連携、AI支援アクションが発生する。記事はこのAI interactionを、単なるUI機能ではなく、統制されたデータフローとして扱うべきだとしている。

リスク具体例運用側の確認
Prompt injection外部文書や入力がAIの動作を誘導する入力元、ツール実行権限、危険指示の扱い
Over-broad grounding本来不要な業務データまで検索文脈に入るユーザー権限、検索対象、最小化、RLS/field制御
Shadow AIカスタム拡張が未承認LLMを直接呼ぶBTP destination、API利用、外部送信先、契約
Output misuseAI出力を検証せず業務判断に使う人間承認、根拠表示、ログ、業務ルールチェック

SAP JouleのIAM参照アーキテクチャでも、SAP Cloud Identity Servicesを標準のID基盤として使い、Global User ID、SCIM、OIDC、principal propagation、SAP BTP Destination Serviceを組み合わせて、ユーザー文脈でJoule Function/APIを呼ぶ流れが説明されている。つまり、AIの便利さは、IDと権限伝播が崩れていないことが前提になる。

「中央認証」と「中央認可」は別物

記事の実務的な警告は、SAP Cloud Identity Servicesや企業IdPで入口をそろえても、各SaaSの業務ロールや権限が自動で統一されるわけではないという点。

たとえば、SuccessFactors、Ariba、Concur、Cloud ERP、BTP拡張では、同じ人がログインできても、給与、購買承認、支払先銀行情報、旅費、顧客情報、API scopeへのアクセスは別々に管理される。MFAやSSOだけでは、過剰権限、非アクティブ特権ユーザー、OAuth client、技術ユーザー、証明書、管理委任の棚卸し不足は解消しない。

見る対象よくある落とし穴チェック観点
ユーザー退職・異動後の残存権限joiner/mover/leaver、IPS/SCIM同期、棚卸し
管理者サービスごとに特権が残るprivileged user review、職務分掌
技術ユーザーAPI連携用に広すぎる権限scope、期限、所有者、ローテーション
OAuth client使途不明のclientが残る登録理由、redirect、secret管理、ログ
SaaS固有ロールIdP側では見えない業務権限アプリ内ロール、承認、field-level permission

Basis担当がCloud ERP案件を見る場合も、IdP連携が終わったかどうかだけでなく、アプリ別の認可と技術アクセス棚卸しまで見る必要がある。

Integration Suiteは「便利な接続」ではなく露出境界

Integration Suiteは、SAPと非SAPの間でデータが動く場所。ここでは資格情報、証明書、endpoint、payload、mapping、event subscriptionが、静かにデータ露出を広げる。

記事は、承認済みAPIと文書化されたintegration patternを使うこと、destination、secret、certificate、integration credentialをライフサイクル管理すること、OAuth 2.0、mTLS、allow-listing、rate limiting、threat protectionを適用することを挙げている。

自分向けには、Cloud Connector設定と公開resourceのレビューを定例化したい。Connectivityは便利設定ではなく、オンプレ/クラウド境界を開ける統制点。誰が、どのsubaccountから、どの内部ホスト/ポート/パスへ到達できるかを、構成図ではなく棚卸し表として持つ必要がある。

採用判断

判断軸評価メモ

結論として、このテーマはCloud ERP移行やJoule導入前の「セキュリティ質問票」に使える。特にAIを入れる案件では、モデル名や機能名より先に、どの業務データがプロンプト/検索文脈/回答/ログへ流れるかを確認する方が実務的。

自分向けメモ

  • Cloud ERPセキュリティは、S/4HANA権限設計だけで完結しない。BTP、SaaS、Integration、AI、契約まで横断で見る。
  • JouleやBusiness AIは、画面の追加機能ではなく「業務データを別の処理系へ渡す流れ」として扱う。
  • 入口のSSO/MFAができていても、各SaaSの業務ロール、OAuth client、技術ユーザー、管理者委任は別に棚卸しする。
  • SAP BTP destinationとCloud Connectorは、拡張開発チーム任せにせず、Basis/セキュリティ側でも所有者、用途、到達先、secret期限を確認する。
  • 生成AI HubやJouleを使う場合は、利用可能モデル、リージョン、保持、学習利用有無、subprocessor、契約条項をSAP NoteやTrust Center、DPAと合わせて確認する。
  • 「Clean Core」はアップグレード性だけでなく、攻撃面を減らすセキュリティ原則として説明できる。
