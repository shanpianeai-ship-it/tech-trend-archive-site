2026-06-27 SAP / ERP importance: high
Summary

Lemvigh-MuellerがSAP基盤上で発注確認PDF処理をAIエージェント化した事例。PoCではなく本番運用、10週間導入、90%超のタッチレス処理という具体値があり、ERP業務AIの現実的な設計材料になる。

SAP発注確認AIエージェント化はERP業務AIの実装例として読む

要約

2026年6月26日、SAP Newsはデンマークの卸売企業Lemvigh-Muellerが、仕入先から届く発注確認PDFやメールの処理を複数AIエージェントで自動化した事例を公開した。Discordポールでは7番「SAP事例: 発注確認10万件をAI化」が1票で最多だったため、午前枠の解説対象にした。

この事例の価値は、生成AIを「便利な要約チャット」ではなく、SAP Cloud ERP PrivateやSAP BTP上の実業務プロセスに組み込んでいる点にある。メールを受け、PDFを読み、購買発注と照合し、価格・数量・納期差異を見つけ、人間の確認や後続ワークフローへ回す。ERPの構造化データと、仕入先文書という非構造データの間を、AIエージェントが埋めている。

数字も具体的だ。SAP Newsでは年間約175,000件の購買発注、2,000超の仕入先、約60%の非構造な発注確認、10週間での本番化、3〜4人分相当のリソース再配置見込みが示されている。SAPの顧客事例ページでは、90%超のタッチレス処理、約98%のマッチング精度、数週間で約23%の仕入先オンボードという実績が補足されている。

背景

発注確認は地味だが、ERP運用では非常に現実的なボトルネックになる。購買発注を出した後、仕入先からPDFやメールで届く確認書には、数量、単価、納期、部分納品、代替品などの差分が含まれる。ここを見落とすと、在庫計画、納期回答、顧客向け可用性、支払処理に影響が広がる。

従来のRPAやOCRは、帳票形式が揃っていれば強い。しかし、仕入先ごとに形式が異なるPDF、長い文書、メール本文、添付ファイル、表記ゆれ、部分的な変更を扱うと、ルールベースの保守コストが上がりやすい。Lemvigh-Muellerも過去にRPAや従来型自動化を試したが、期待する効果を得られなかったと説明されている。

今回の設計では、単一の巨大AIに全部を任せるのではなく、責務を分けた複数エージェントを業務フローに組み込んでいる。SAP Newsでは、メールを受け取って関連確認書を振り分けるエージェント、文書を読んでデータを抽出するエージェント、SAP上の購買発注と照合して差異を判定するエージェントという構成が説明されている。SAPの顧客事例では、SAP Cloud ERP Private、SAP AI Launchpad、SAP AI Core、SAP BTP、SAP Cloud SDK for AIといったSAP側の基盤も示されている。

何が重要か

ERP業務AIは「文書読解」だけでは終わらない

この事例は、AI-OCRの延長として見ると少し足りない。重要なのは、抽出した値をSAPの購買発注と照合し、業務上の判断に使える差異へ変換している点だ。

処理段階AIに任せることERP側で重要なこと
受信仕入先メールと添付確認書の識別共有メールボックス、対象仕入先、対象業務範囲
読解PDFやメールから数量、価格、納期を抽出マスタ、購買発注、品目、単位、通貨との整合
照合発注内容との差異を検出許容差、例外ルール、承認要否
後続処理自動更新、メール応答、例外起票へ接続監査、変更履歴、人間レビュー、エラー時復旧

生成AI導入で本当に難しいのは、非構造データを読むことだけではない。読んだ内容を、SAP側のマスタ、伝票、権限、承認、監査に接続する部分が本番化の肝になる。

「人を置き換える」より「例外へ寄せる」設計

Lemvigh-Muellerの説明では、目的は人員削減ではなく、購買担当者を例外対応や高付加価値業務へ移すことだとされている。これはERP業務AIの現実的な落としどころとして重要。

観点全自動を狙う設計例外集中を狙う設計
目標人間の作業を完全に消す定型チェックを減らし、差異だけ人間へ回す
リスク誤判定がそのまま業務影響になる人間レビューの境界を作りやすい
導入しやすさ精度要求が高く、合意形成が難しい既存業務の負荷軽減として始めやすい
運用指標完全自動率、エラー率タッチレス率、マッチング精度、例外処理時間

SAP顧客事例の90%超タッチレス処理や約98%マッチング精度は、この「例外集中型」のKPIとして読むべき数字。全件をAIが勝手に処理するのではなく、大半の単純一致を流し、差異のあるものを購買担当者が見る構造にすると、現場にも説明しやすい。

Clean Coreと拡張基盤の話でもある

SAP事例ページでは、clean core strategyとSAP BTP上の拡張基盤が触れられている。これはBasis/ERP運用目線では見逃せない。AIエージェントをERP本体へベタ書きするのではなく、SAP Cloud ERP Privateを記録系として残し、SAP BTPやAI Core側で文書読解・推論・照合・ルーティングを担う構成にしている。

この分離には意味がある。

  • ERP本体の標準性を保ちながら、非構造文書処理の変化に追随しやすい。
  • AIモデルやプロンプト、文書処理ロジックをERPアップグレードと切り離して改善できる。
  • 権限、API、監査、例外処理を明示的な接続点として設計しやすい。
  • 仕入先、メールボックス、業務領域を段階的に広げられる。

逆に言えば、この設計を真似るにはBTP、API、Cloud SDK、権限、運用監視、ジョブ失敗時のリカバリをセットで考える必要がある。AIエージェントのデモだけでは、本番業務には届かない。

10週間導入は「範囲の切り方」が効いている

10週間で本番化という数字は目立つが、単純に「SAP AIはすぐ入る」と読むのは危険。成功要因は、対象業務を発注確認という明確な単位に絞り、仕入先メールと購買発注の照合にKPIを置き、ビジネス担当とSAP担当が密に協働できた点にある。

成功要因実務での意味
対象業務が明確発注確認、購買発注照合、差異検出に絞れる
効果が測りやすいタッチレス率、マッチング精度、処理時間で評価できる
例外境界がある価格・数量・納期差異を人間に戻せる
SAP連携が深いERPの購買発注を正として照合できる
現場アクセスがある業務担当とSAP担当が短い反復で仕様を詰められる

つまり、自社で応用するなら「AIに何でも聞けるようにする」より、「月間件数が多く、非構造文書が絡み、ERPの正データと照合でき、例外を人間に戻せる」業務を探すのが先になる。

自分向けメモ

  • SAP系のAIエージェント導入は、Jouleの画面機能だけでなく、BTP/AI Core/API連携で既存業務に差し込む方向を見る。
  • 発注確認、請求書、納品書、作業報告書、監査証跡など、「非構造文書 + ERP正データ照合 + 例外レビュー」の形は横展開しやすい。
  • 本番化の評価指標は、モデル単体精度よりもタッチレス処理率、例外検出率、誤更新率、処理遅延、リカバリ時間に置く。
  • RPAで詰まった業務ほど、単純なUI自動化ではなく、文書理解・照合・例外ルーティングに分解して考える。
  • Clean Coreを守るなら、AIロジックはERP本体改修ではなくBTP側やAPI連携側に寄せ、監査と承認を明示する。
