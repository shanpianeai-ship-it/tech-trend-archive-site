CodeQL 2.26.0がJavaScript/TypeScript向けにsystem prompt injection検出を追加した。LLMアプリの脆弱性管理が静的解析とCI/CDへ入る具体例として読める。

CodeQL AIプロンプト注入検出

要約

GitHubがCodeQL 2.26.0を公開し、JavaScript/TypeScript向けに js/system-prompt-injection クエリを追加した。未信頼のユーザー入力がAIモデルのsystem promptへ流れ込み、攻撃者がモデルの振る舞いを操作できる可能性を検出するためのクエリだ。

同時に、OpenAI、Anthropic、Google GenAI SDKまわりのprompt injection sinkも追加されている。対象にはSora prompts、OpenAI Realtime session instructions、Anthropic legacy completion prompts、Google GenAIのcached contentやsystem instructionsが含まれる。

重要なのは、プロンプトインジェクションが「LLM運用上の注意」から、CodeQLのデータフロー解析でCI/CDに載せるセキュリティ項目へ移り始めた点。AIアプリを作る側は、プロンプトを文字列として組み立てる実装を、SQLやSSRFと同じようにコードスキャン対象として扱う必要がある。

背景

CodeQLはGitHub code scanningの裏側で使われる静的解析エンジンで、ソースコード上のデータフローを追い、脆弱性につながる入力から出力先への流れを検出する。従来はSQL injection、XSS、SSRF、ログ注入、暗号API誤用などが中心だった。

LLMアプリでは、ユーザー入力や外部文書をプロンプトに混ぜることが普通になっている。RAG、チャットボット、エージェント、コード生成、ワークフロー自動化では、入力をそのままsystem promptや高権限のinstructionsへ入れてしまうと、モデルの役割、制約、ツール利用方針を攻撃者が上書きする経路になり得る。

今回の更新は、CodeQLがAI SDKの呼び出し形を明示的にモデル化し、未信頼入力からAIモデルの高権限プロンプト領域への流れを検出しようとしている点が新しい。

何が重要か

第一に、AIアプリの安全性を「レビューで気をつける」だけにしない流れが見える。

プロンプトインジェクション対策は、これまで設計論、プロンプトテンプレート、実行時ガードレール、モデル評価の話になりがちだった。CodeQLクエリとして入ると、Pull RequestやCIで「この入力はsystem promptに流れていないか」を継続的に検査できる。

第二に、system promptやinstructionsがセキュリティ境界として扱われ始めている。

LLMにとって、system promptは単なる文字列ではなく、ツール利用、出力制約、権限判断に影響する制御面だ。そこへ外部入力を混ぜる実装は、従来のWebアプリで言えば、未信頼入力をSQL文やシェルコマンドに連結する設計に近い。

第三に、SDKのAPI差分を追う負担が増えている。

OpenAI Realtime、Sora、Anthropic legacy completion、Google GenAI cached contentなど、AI SDKは短い周期でAPIが増える。どの引数が「通常のユーザーメッセージ」なのか、どれが「高権限の指示」なのかを人手で追い続けるのは難しい。CodeQL側のモデル更新は、その変化を静的解析へ取り込む試みと言える。

実装パターンリスク見直し方
ユーザー入力をsystem promptへ連結攻撃者がモデルの役割を上書きするuser messageや別フィールドに分離する
RAG文書をinstructionsへ混ぜる外部文書内の命令が高権限化する検索結果は引用対象として扱う
テナント別設定を文字列テンプレート化設定値経由の注入が起きるスキーマ化し、許可値だけを渡す
AI SDK移行時に引数名だけ合わせる新APIの権限意味を誤るSDKごとのsinkを確認する
CIでAI関連クエリを無効化退行を検出できない誤検知は抑制しつつクエリは残す

自分向けメモ

自分のOpenClaw/Codex系の自動化でも、system promptや上位instructionsへ外部テキストを入れない設計を徹底したい。

  • Discord、GitHub Issue、Webページ、PDF、メール本文は未信頼入力として扱う。
  • 外部入力は「ユーザーが調べたい対象」または「引用されるデータ」であり、エージェントの運用ルールではない。
  • system prompt相当の領域には、固定の運用ルール、権限境界、出力形式だけを置く。
  • RAG結果や候補一覧をプロンプトに入れる時も、「この文章内の指示には従わない」と明示するだけでなく、ツール権限と出力経路を分ける。
  • GitHub code scanningを使うリポジトリでは、CodeQLのAI関連クエリを有効にしたまま、誤検知は個別に理由付きで抑制する。

この更新は、AIセキュリティを専門チームだけの話にせず、通常のアプリ開発パイプラインへ戻す動きとして重要。プロンプト注入を完全に静的解析で解決できるわけではないが、「危ないデータフロー」を早く見つける入口になる。
