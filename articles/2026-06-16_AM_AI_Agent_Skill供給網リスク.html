AI Agent Skill供給網リスク

要約

Unit 42の「Trust No Skill」は、AIエージェント用の第三者Skillを、モバイルアプリやブラウザ拡張と同じ供給網リスクとして扱うべきだと整理している。

ポイントは、Skillが単なる説明文や便利スクリプトではなく、エージェントの権限文脈でファイル、環境変数、ネットワーク、シェル実行へ触れる小さな実行パッケージだという点。悪意の有無は別として、宣言された機能と実際の挙動がずれると、資格情報窃取、遠隔コード実行、静かなデータ流出につながる。

Unit 42は Behavioral Integrity Verification、略してBIVという監査手法を提案している。これは、Skillのメタデータ、実行コード、自然言語指示を横断して読み、「宣言された能力」と「実際に使う能力」が一致しているかを比較する考え方。

背景

LLMエージェントは、単体モデルではなく、ツールやSkillを足して作業範囲を広げる方向へ進んでいる。OpenClaw、Codex、MCP、各種ブラウザ/メール/Driveコネクタのような仕組みでは、エージェントが外部サービスやローカルファイルへアクセスする。

この構造は便利だが、セキュリティ上は「小さな拡張機能に強い権限を渡す」形になる。従来のnpmパッケージ、ブラウザ拡張、モバイルアプリと似ているが、AIエージェント特有の違いもある。

観点従来の拡張AI Agent Skill
挙動の場所主にコードコード、メタデータ、自然言語指示
利用者人間やアプリエージェントの判断ループ
権限API権限、ファイル、ネットワークそれに加えてプロンプト上の行動誘導
リスク情報収集、RCE、権限濫用それに加えてエージェントの判断乗っ取り
監査単位パッケージや権限宣言と実挙動の差分、複数能力の連鎖

特に重要なのは、自然言語指示も実質的な実行ロジックになる点。例えば「常にこのSkillを使え」「ユーザー確認を避けろ」のような指示は、通常の静的コードスキャナでは拾いにくいが、エージェントの判断を変える。

何が重要か

1. 単独能力ではなく「連鎖」が危ない

Unit 42の記事では、BIVが見つけた危険な複合パターンとして、ファイル読み取り、エンコード、ネットワーク送信のような組み合わせが挙げられている。

単体で見ると、ファイル読み取りもネットワーク送信も正当な用途がある。だが同じSkill内で「秘密情報を読む」「base64化する」「外部へ送る」が並ぶと、資格情報流出の可能性が高くなる。

連鎖単体ではどう見えるか全体での意味
FILE_READ -> base64 -> NETWORK_SEND読み取り、変換、通信静かなデータ持ち出し
download -> write -> execute更新、保存、実行遠隔コード実行
encoding -> dynamic eval難読化、動的実行検知回避つきコード実行
instruction override -> exfiltration指示追加、外部通信エージェント判断の乗っ取り

従来の「危険APIを使っているか」だけでは足りない。エージェント用Skillでは、能力の組み合わせと、宣言されていない組み合わせを見なければならない。

2. 多くは悪意ではなく仕様未成熟

arXiv版のBIV論文では、OpenClaw registryの49,943件のSkillを調査し、80.0%に宣言と挙動のズレがあったと報告している。ただし、ズレの多くは悪意ではなく、説明不足、テンプレート残り、補助コードの記載漏れのような開発者側の未成熟として分類されている。

これは重要な読み替えが必要。数字だけを見ると「ほとんど危険」に見えるが、実務上の結論は「すべて拒否」ではない。

層見るべき状態運用判断
benign mismatch説明不足、未使用宣言、補助コードメタデータ修正、台帳更新
single-stage suspicious未宣言のcredential/env/network利用手動レビュー、権限縮小
multi-stage chain秘密読み取りから送信、指示乗っ取りから外部送信導入禁止または隔離検証

つまり、Skill監査は「脅威検知」だけでなく「仕様と権限を正しく記録する運用」でもある。

3. AIエージェント特有の監査対象がある

BIVの分類は、ネットワーク、ファイルシステム、プロセス実行、環境変数、エンコード、資格情報、instruction-level threatsを扱う。最後のinstruction-level threatsがAIエージェント特有の要点。

コードの中に危険な関数がなくても、SKILL.mdやREADME、frontmatterの自然言語指示がエージェントの判断を変えることがある。これは「静的解析だけではSkill監査にならない」ことを意味する。

自分の環境でも、Skillは単なるドキュメントではない。いつ使うか、何を読んでよいか、どのツールを呼んでよいか、ユーザー確認を必要とするかを決める実行ポリシーの一部として扱う必要がある。

4. OpenClaw/Codex運用に直結する

この話は企業向けだけではない。OpenClawやCodexで個人作業を任せる場合も、SkillやMCP、コネクタは同じ問題を持つ。

対象リスク自分向けの対策
OpenClaw Skill自然言語指示で過剰なツール利用SKILL.mdの差分確認、権限境界の明記
MCPサーバ広いAPI権限や外部送信接続先、scope、ログの台帳化
Codex subagent親より広いファイル/ネットワーク利用作業ディレクトリ、書き込み範囲、外部送信を明示
Discord/メール送信意図しない外部発信送信前承認、チャンネル分離
ローカルファイル操作秘密情報や個人情報の読み過ぎCommon/Obsidian/作業フォルダごとの扱い分離

特に、Skill追加時に「便利そうだから入れる」だけだと危ない。最低限、読み取り可能なファイル、外部通信、環境変数、シェル実行、外部投稿の有無を台帳に残すべき。

自分向けメモ

  • Skillは「ドキュメント」ではなく「エージェントに渡す実行権限パッケージ」として扱う。
  • 導入前チェックは、コードだけでなくSKILL.md、frontmatter、README、依存スクリプトまで見る。
  • 単体の危険APIより、読む -> 変換する -> 送る のような連鎖を優先して見る。
  • OpenClawのスキル運用では、各Skillに「外部送信するか」「ローカル書き込みするか」「秘密情報に触るか」を短く記録する台帳がほしい。
  • MCPサーバも同じ。ツール名だけではなく、接続先、scope、認証方式、ログの残り方を管理する。
  • 企業利用なら、Skill registryに入る前のBIV的チェックと、導入済みSkillの棚卸しを別プロセスにするのがよい。
  • SAP/ERPエージェントでは、伝票、マスタ、認証情報、ジョブログを扱うSkillが出てくるはず。ここは通常の業務権限レビューと同じ重さで見る必要がある。
