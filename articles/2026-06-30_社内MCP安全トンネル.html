Summary

OpenAI Secure MCP Tunnelは、社内やローカルのMCPサーバーを公開せずChatGPT/Codexへつなぐ設計。MCP普及後の企業内ツール接続、権限境界、監査の実務論点を整理できる。

社内MCP安全トンネル

要約

OpenAIのSecure MCP Tunnelは、社内ネットワーク、開発者のローカル環境、Kubernetes、VMなどにあるMCPサーバーを、インターネットへ直接公開せずにChatGPTやCodexから利用できるようにする仕組み。

発想は単純で、プライベート側に置いた小さなトンネルクライアントがOpenAI側へアウトバウンドHTTPS接続を張る。OpenAI製品からのMCPリクエストはOpenAIホストのトンネルエンドポイントに入り、プライベート環境内のクライアントがそれを拾って、許可されたローカルMCPサーバーへ転送し、応答を同じ経路で返す。

重要なのは「MCPを便利につなげる機能」ではなく、「社内ツールをAIエージェントへ渡すとき、ネットワーク境界をどう崩さずに運用するか」という設計論になっている点。MCPが普及すると、ファイル、DB、社内API、運用ツールをAIに触らせる需要が増える。その時に、公開エンドポイント、VPN、汎用トンネルではなく、狭く、監査しやすく、明示的に許可された接続だけを作る発想が必要になる。

自分向けには、OpenClawやCodexにローカル/社内ツールを増やす時の基準として読むのがよい。AIエージェントの能力を増やすほど、MCPサーバーそのものが新しい実行入口になる。便利さより先に、どのサーバーを、誰の権限で、どの経路から、どこまで到達可能にするかを決める必要がある。

背景

MCPは、AIアプリケーションが外部システムへ接続するための標準プロトコルとして広がっている。公式サイトでも、ローカルファイル、DB、検索、カレンダー、Notion、開発ツールなどをAIアプリへつなぐ標準ポートのような位置づけで説明されている。

ただし、企業内で価値の高いMCPサーバーほど、外部公開したくない場所にある。業務DB、運用ツール、社内検索、チケット、ソースコード、管理APIなどは、インターネットから直接叩ける形にするべきではない。かといって、ChatGPTやCodexのようなホスト型AI製品から利用したい需要は強い。

従来の選択肢は、公開エンドポイントを作る、サードパーティのトンネルを使う、VPN/ネットワークピアリングで広くつなぐ、といったものだった。どれもMCP用の細い接続としては重いか、境界が広すぎる。Secure MCP Tunnelは、この隙間を「プライベート側から始まるアウトバウンド接続」と「顧客が運用する検査可能なクライアント」で埋める。

何が重要か

1. 到達性を逆向きに作る

Secure MCP Tunnelの中心は、プライベート側が先にOpenAIへ接続すること。MCPサーバーは外部からのインバウンド通信を受けず、クライアントがOpenAI側のトンネル制御面を長いポーリングで見に行く。

方式何を広げるか問題
公開エンドポイントMCPサーバーをインターネットから到達可能にする境界が弱くなり、WAF/認証/運用負荷が増える
VPN/ピアリングネットワーク同士を広く接続するMCP用途には権限範囲が大きすぎる
汎用トンネル第三者の中継経路を追加する追加ベンダーの審査、ログ、契約、信頼境界が増える
Secure MCP Tunnel顧客側クライアントから狭いアウトバウンド経路を張るMCP用途に絞った到達性を作れる

これは、AIエージェントに社内ツールを渡すときの基本形になり得る。外から開けるのではなく、中から許可された接続だけを作る。ネットワークの都合ではなく、権限設計の都合に合わせた接続にする。

2. MCPサーバーを「実行入口」として扱っている

MCPは、単なるデータ取得APIではない。ツール呼び出しを通じて、ファイル操作、検索、DB参照、クラウド操作、社内ワークフロー実行につながる。つまりMCPサーバーは、AIが使う実行入口になる。

見方軽く見た場合実務上の見方
MCPサーバーLLMに便利なツールを足す部品社内システムへの権限付き実行入口
トンネル接続できればよい通信路監査・認可・境界を左右する基盤
ローカル設定開発者の便利設定サプライチェーン/権限拡大の入口
ツール一覧機能カタログAIに実行させてよい操作範囲

Secure MCP Tunnelの設計が「明示的な宛先設定」「顧客運用クライアント」「検査可能性」を強調しているのは、この前提があるからだと思う。MCPが便利なほど、接続経路は雑に増やしてはいけない。

3. アウトバウンドHTTPSとlong-pollは地味だが運用しやすい

OpenAIの説明では、最初のトランスポートとしてlong-pollを選んだ理由も示されている。企業ファイアウォールやプロキシ環境で扱いやすく、クライアント側が処理できる量だけ仕事を拾うため、自然なバックプレッシャーになる。

設計要素意味
アウトバウンドHTTPS既存の企業ネットワーク制御に乗せやすい
long-poll常時双方向ソケットより運用が読みやすい
SSE転送MCPのストリーミング応答や途中イベントを扱える
ローカルadmin/health UI起動、到達性、設定、ログを運用者が確認できる

AI基盤は派手なモデル性能に目が行きがちだが、社内運用ではこういう「退屈な通信方式」のほうが通しやすい。特にBasis/情シス目線では、プロキシ、証明書、監査ログ、ヘルスチェック、障害時切り分けが説明できるかが重要になる。

4. オープンソースの顧客側クライアントが信頼境界を支える

Secure MCP Tunnelでは、顧客環境内で動くクライアントがオープンソースとして公開されている。GitHubのREADMEでは、/healthz、/readyz、/metrics、/ui を持つ運用者向けdaemonとして説明され、ローカルMCP、VM、Kubernetes、プライベートネットワークで使う前提が示されている。

これは大事。OpenAI側のトンネルサービスはホストされていても、社内ネットワーク内で動くコードは顧客が確認し、設定し、監視できる。どのアウトバウンド接続を開くか、どのローカルMCPへ転送するか、どの証明書やプロキシ設定を使うかを見られる。

エンタープライズ導入では「AI製品が社内に入ってくる」のではなく、「社内で検査可能なクライアントが、許可されたAI製品向けに細い出口を作る」と説明できるかが通しやすさを左右する。

5. HarpoonはREST APIにも同じ考え方を広げている

OpenAIの記事では、MCP以外の既存REST APIにも同じ狭い接続モデルを広げるHarpoonにも触れている。既存の社内APIがすべてMCP化されているわけではないため、ラベル付けされた許可済みRESTターゲットだけをトンネル経由で呼ぶ考え方。

ただし、ここでも汎用ネットワークブリッジにはしない。許可済みターゲット、HTTPメソッド、レスポンスサイズ、タイムアウト、リダイレクト、アクセス制御で狭くする。これは、AIエージェントが社内APIへ触る時の現実的な移行路になる。

自分向けメモ

  • MCPサーバーを追加するときは「便利ツール」ではなく「権限付き実行入口」として棚卸しする。
  • ローカルMCPでも、将来ホスト型AIや外部エージェントへつなぐ可能性があるなら、最初から宛先、権限、ログ、停止方法を明示する。
  • localhost や社内ネットワークを信用境界として雑に扱わない。エージェントがブラウザ、MCP、設定ファイルをまたぐと、ローカル境界は攻撃面になる。
  • OpenClaw/Codex運用では、MCP設定ファイルの差分、起動中のMCPサーバー、外部公開の有無を定期チェック対象にするとよい。
  • 企業向けに説明するなら、「AIに社内ネットワークを開ける」のではなく、「顧客運用クライアントが許可済みMCP/RESTターゲットだけを外向きに中継する」と言い換えると通りやすい。
