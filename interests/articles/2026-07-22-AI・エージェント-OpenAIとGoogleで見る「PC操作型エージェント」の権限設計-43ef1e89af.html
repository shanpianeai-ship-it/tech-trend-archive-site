Summary

OpenAIとGoogleのComputer Use系エージェントを、個人PCで使う前提で確認ゲート・外部送信制限・ログを軸に比較した。

OpenAIとGoogleで見る「PC操作型エージェント」の権限設計

要約

PCを触るエージェントは、性能より「事故を起きにくくする境界設計」が先決で、 比較対象はモデルやUI操作の差分よりも、確認ゲート・外部送信制限・実行ログの3点で見ると実務効率が高い。

OpenAI系は「関数呼び出し」「ガードレール」「ヒト介入」中心、Google系は「Computer Use（画面制御）」中心で、 どちらも本質的には権限を分離して承認を入れる方向だ。 個人運用では、ブラウザ自動化を常用権限と同じ文脈で動かさないのが先に有効。

公式ソースから見た違い

1) 実行基盤の定義

  • OpenAI: ツール利用は「関数（function）/ツール呼び出し」でAPIに明示。モデルが必要だと判断した際に tool call を返し、結果を再入力して最終応答を作る前提。
  • Google: Computer Use はスクリーンショットを伴い、computer_use でブラウザ/モバイル/デスクトップへUI操作を指示。

1ステップごとに function_call 相当の行動提案を受け、スクリーンショットと結果を再送して反復ループする。

  • 意味: OpenAIは「APIで呼べる行動」を前提に組む傾向、Googleは「画面操作を状態遷移で回す」モデルが明確。

2) 安全制御の位置

  • OpenAI: ガードレールを入力/出力/ツールへ分け、サイドエフェクト時は人の承認（human review）で停止させる設計が明示されている。

（承認が必要な tool を持たせ、run を一旦中断→判断→再開する流れ）

  • Google: Computer Use は safety_decision を返し、require_confirmation や blocked を扱える。

さらにプロンプトインジェクション検出を有効化でき、危険な画面誘導への対応を前提にしている。

  • 意味: OpenAIは実行前の承認フロー寄り、Googleは実行時の安全判定ループ寄り。実務では両方必要。

3) 権限境界の発想

  • OpenAI: MCP/Connector は require_approval を使った制御が前提で、信頼できるサーバに対してだけ使うことを強調。

また、sandbox Agent 構成で「制御面（harness）」と「実行面（compute）」を分離する設計を説明している。

  • Google: 管理エージェントやEnvironmentは sandboxed 環境を前提に、ネットワーク許可リスト（allowlist）で外部送信先を制限。

機密情報は必要最小範囲で注入し、権限の範囲を明示する方針を取っている。

  • 意味: OpenAI/Geminiともに、PC権限を直接広げるのではなく、実行環境を分断して危険を局所化する思想が共通している。

個人PCで使うなら「共通の最低制御」を先に作る

A. 承認ゲート

Googleの require_confirmation、OpenAIの approvals を参考に、次を一律停止対象にする。

  • 送信（POST/PUT/DELETE）を伴う操作
  • 資格情報入力・保存・更新
  • ファイル破壊的操作（削除・上書き）
  • 送金/決済/認証の代替トランザクション

B. 外部送信制限（出力先）

Googleの allowlist 構文を採用した最小制限をベースにする。

  • localhost 系や開発系ドメインのみ許可
  • 金融・個人情報領域は明示的許可外を禁止
  • 認証付き外部APIは短命トークンを使い、再利用不可で更新

C. ログを先に仕様化

自分用に最低4点を残すだけで、事故時にかなり復旧が早い。

  1. 開始時のプロンプト（要件 + 許可境界）
  2. 実行前の意図（承認対象なら誰が許可したか）
  3. 実行結果の要約（成功/失敗/停止理由）
  4. 例外・拒否・中断時の復旧手順

実装順（過剰調査を避けた1本構成）

  1. OpenAI側は Function Calling + Tool/Guardrails を使い、まずは「API実行」「DB更新」等の副作用ワークロードを定義。
  2. Google側は Computer Use では最初から browser 環境＋enable_prompt_injection_detection を有効化し、safety_decision を監視。
  3. 両者を同じ「承認エンジン」で統一し、停止したアクションだけをヒト判断で再開する。
  4. まずは 編集系 と 送信系 のみを許可し、検索・閲覧・ドラフト生成は無承認で許可、という段階導入を実施。

今回の結論

OpenAIもGoogleも、PC操作エージェント単体の「速さ」より、 どの行為を自動化し、どの行為で必ず止めるかを明文化した運用が重要。 個人のPC運用では、権限の中心を 確認ゲート（approval） > 外部送信制限（allowlist） > 実行ログ（audit） の順で固めると、事故時の影響を小さく保てる。
