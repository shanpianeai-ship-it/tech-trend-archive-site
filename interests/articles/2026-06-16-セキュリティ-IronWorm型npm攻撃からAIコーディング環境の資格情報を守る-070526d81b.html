Miasma/IronWorm型npm攻撃からAIコーディング環境の資格情報を守る

要約

Miasmaは、Red Hat Cloud Services配下のnpmパッケージを改ざんし、preinstallフックで開発機やCI/CDの資格情報を盗むサプライチェーン攻撃として報告された。Microsoftは、32個の改ざんパッケージと90超のバージョンが影響し、GitHub Actions OIDCのtrusted publishing経路を悪用したため、改ざんパッケージが正規のprovenance署名を持って見えた点を重く見ている。

この攻撃がAIコーディング環境で厄介なのは、単にnpmトークンを盗むだけではない点にある。OSVの記録では、GitHub PAT、npm publish token、クラウド認証情報、Kubernetes service account token、Vault token、.npmrc、.netrc、shell historyなどが狙われ、さらに.claude/settings.jsonや.vscode/tasks.jsonを使った永続化も記録されている。つまり、Claude Code、Codex、OpenClaw、VS Code、CI runnerが集まる場所は、攻撃者にとってかなり効率のよい侵入口になる。

結論として、個人のAIコーディング環境では「npm installは低リスクな準備作業」と見なさない方がよい。特にMCPサーバー、CLI補助ツール、AIエージェント連携、GitHub Pages公開自動化のように、ローカルファイル・GitHub・Discord・クラウド・トークンへ近い依存は、通常のフロントエンド依存より一段厳しく扱うべきである。

なぜ今見る価値があるか

今見る価値は、AI開発環境が「依存パッケージ」と「実行権限」と「資格情報」を同じ作業面に置きがちだからだ。

Microsoftの分析では、攻撃はnpm install時のpreinstallで自動実行され、Nodeからshell、Bun、二段目payloadへ進む。Linux CI/CD runnerが主な標的とされつつ、macOSやWindowsの開発機でも動作する。OpenClawやCodexのような長時間実行環境では、ローカル作業ディレクトリ、GitHub remote、Discord連携、Pages公開、各種APIキーが一つの作業文脈に寄りやすい。便利さの裏側で、盗まれたときの被害半径も広がる。

また、Miasmaは「怪しいパッケージを直接入れたら危ない」という単純な話ではない。trusted publishingやprovenance署名のような正規の仕組みを通ったように見えるため、署名や出所表示だけで安心しにくい。パッケージ名、バージョン、スクリプト、lockfile差分、実行環境、トークン権限を合わせて見る必要がある。

調査メモ

Microsoftは、RedHatInsights/javascript-clientsのCI/CDパイプライン侵害から、@redhat-cloud-servicesスコープの複数npmパッケージが改ざんされたと説明している。改ざんパッケージにはMiasmaのキャンペーンマーカーが含まれ、GitHub Actions OIDCの公開フローを通じて配布された。インストール時にはpackage.jsonのpreinstallが発火し、4MB超のdropperがBun runtimeを取得して二段目payloadを動かす流れだった。

OSVのMAL-2026-5129は、対象の一つとして@redhat-cloud-services/hcc-feo-mcpを挙げている。記録されているリスクはかなり広い。AWS、Azure、GCP、Vault、Kubernetes、GitHub、npmの資格情報、CI環境変数、ローカル設定ファイル、shell履歴が窃取対象になる。Docker socketが使える環境ではコンテナ外への脱出やsudoers改変も示されている。

AIコーディング環境で特に見るべきなのは、.claude/settings.jsonと.vscode/tasks.jsonへの干渉だ。前者はAIエージェントの設定、後者はエディタ作業の自動実行に近い。ここを改ざんされると、ユーザーが意識しないタイミングで外部コマンドや追加サーバーが起動する可能性がある。MCPサーバーやAI用CLIをnpm経由で入れる運用では、設定ファイルの差分監視が防御線になる。

GitHub AdvisoryとOSVは、該当パッケージが入った端末は完全侵害として扱い、別端末から秘密情報をローテーションすることを推奨している。これはやや強い表現だが、今回のようにローカルファイル、CI変数、クラウドメタデータ、GitHub/npm publish権限まで狙う攻撃では妥当な前提だと見てよい。

個人環境での実務対策は、次の順に切るのが現実的だ。まず、最近追加したnpmグローバルCLI、MCPサーバー、AI補助ツールを棚卸しする。次に、package.jsonとlockfileの差分、preinstall/postinstall/prepareを持つ依存を確認する。さらに、.claude/settings.json、.vscode/tasks.json、MCP設定、OpenClaw/Codex設定、GitHub Actions workflowの差分を見る。最後に、GitHub、npm、クラウド、Discord bot、AI APIキーのスコープと保存場所を見直す。

個人向けの読みどころ

個人の運用では、OpenClawがDiscordポールを読み、Markdownを書き、GitHub Pagesへpushし、公開URLまで確認する。これは便利だが、GitHub、Discord、ローカルObsidian、Node build、cronが同じ流れに入っているということでもある。

今回の読みどころは、AIエージェント自体よりも「AIエージェントが使う周辺npm」と「設定ファイル」を守ることだ。CodexやOpenClawを直接攻撃しなくても、MCPサーバーや補助CLIのpreinstallを踏ませ、.claude/settings.jsonや.vscode/tasks.jsonを汚染できれば、次回以降の作業に入り込める。

実務的には、次の小さな台帳をObsidianに作ると効果が出やすい。

  • AI/MCP npm台帳: パッケージ名、用途、インストール方法、固定バージョン、最終確認日
  • postinstall系チェック: preinstall、postinstall、prepareを持つ依存と、その実行理由
  • 設定ファイル監視: .claude/settings.json、.vscode/tasks.json、MCP設定、OpenClaw設定の差分
  • 資格情報棚卸し: GitHub token、npm token、Discord bot token、AI API key、クラウドCLIログインの保存場所
  • 侵害時の初動: ネットワーク切断、別端末からトークン失効、GitHub/npm監査ログ確認、該当依存削除ではなく端末再構築判断

この興味レポート自動化にも応用するなら、node scripts/build.mjsの前後でgit diffを確認し、公開対象に内部パスや秘密情報が混じっていないかを見る運用は続けたい。npm依存を増やすときは、便利なライブラリかどうかだけでなく、インストール時スクリプトとメンテナ権限も確認対象に入れる。

注意点

この記事は公開情報にもとづくセキュリティ運用メモであり、特定端末の侵害有無を診断するものではない。不審なnpmパッケージ、身に覚えのないAI/MCP設定、予期しないGitHub Actions workflow、未知の外部通信、資格情報流出の疑いがある場合は、該当端末を信頼せず、別端末からトークン失効とログ確認を行うべきである。

また、Miasma/IronWormという呼称やキャンペーン範囲は、ベンダーや研究者によって表現が揺れる可能性がある。実務判断では、Microsoft、OSV、GitHub Advisory、npm公式・GitHub公式の情報を優先し、二次解説は補助として読むのがよい。
