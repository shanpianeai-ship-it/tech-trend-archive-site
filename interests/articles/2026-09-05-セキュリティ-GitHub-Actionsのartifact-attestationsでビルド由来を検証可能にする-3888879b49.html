GitHub Actionsのartifact attestationsでビルド由来を検証可能にする

Summary

GitHub公式のartifact attestationsを使うと、バイナリやコンテナイメージがどのworkflowで生成されたかを後から確認しやすくなる。導入時はプラン条件、最小権限、対象指定、検証手順まで一体で設計したい。

導入前に確認すること

GitHub Actionsのartifact attestationsは、ビルド成果物に対して「どこで、どのように作られたか」を示す由来情報を付けるための機能です。対象はバイナリやコンテナイメージで、workflowにattestation生成ステップを加えることで、後から成果物のbuild provenanceを確認できる状態にできます。

ただし、使える範囲はリポジトリ種別とプランに左右されます。現行のGitHubプランでは利用できますが、Bronze、Silver、Goldのようなレガシープランでは利用できません。また、Free、Pro、Teamではpublicリポジトリが対象で、privateまたはinternalリポジトリで使うにはGitHub Enterprise Cloudが必要です。まず対象リポジトリで機能を使えるかを確認するのが出発点です。

バイナリに由来証明を付ける

バイナリ成果物にattestationを付ける場合、workflow側で必要な権限を明示します。基本はid-token: write、contents: read、attestations: writeです。OIDCトークンを扱うための権限、リポジトリ内容の読み取り、attestationを書き込む権限を、それぞれworkflowに持たせます。

そのうえで、バイナリを生成した直後のステップにactions/attest@v4を追加し、subject-pathで対象ファイルの場所を指定します。重要なのは、署名やattestationを「最後にまとめて付ける飾り」と考えないことです。どのビルドステップで作られたどの成果物に対する由来情報なのかが追えるように、生成直後の流れに組み込むほうが運用しやすくなります。

コンテナイメージではdigestを基準にする

コンテナイメージの場合は、バイナリの権限に加えてpackages: writeも必要です。attestationの対象指定にはsubject-name、subject-digest、push-to-registry: trueを使います。

subject-nameは、ghcr.io/user/appのような完全修飾のイメージ名で指定し、タグは含めません。実体の識別にはsubject-digestを使い、値はsha256:HEX_DIGESTの形式にします。docker/build-push-actionを使っているworkflowでは、そのステップのdigest出力をattestationの入力に渡せます。タグは動かせる名前になり得るため、検証可能性を高めるにはdigestを基準に対象を結び付ける設計が重要です。

SBOMとlinked artifactsも運用に入れる

artifact attestationsはSBOMにも使えます。事前に対象成果物のSBOMを生成し、actions/attest@v4でsbom-pathを指定します。バイナリではsubject-pathで対象成果物を示し、SBOMファイルの場所をsbom-pathで対応付けます。コンテナイメージでも、対象のイメージ名とdigestに加えて、JSON形式のSBOMファイルを指定します。

さらに、linked artifacts pageへ成果物の記録を作る運用もあります。自動でstorage recordを作成するには、push-to-registry: trueが設定されていることと、workflowにartifact-metadata: write権限があることの両方が必要です。このページでは、成果物のビルド履歴、デプロイ記録、保存情報を確認でき、脆弱な成果物を所有チーム、ソースコード、ビルド実行へ結び付ける手がかりになります。

生成だけで終わらせない

attestationは、付けた時点で成果物が安全だと断定する仕組みではありません。価値が出るのは、生成されたattestationをGitHub CLIで検証し、どの成果物をどの条件で受け入れるかを運用に組み込んだときです。

そのため、導入時はworkflowへのステップ追加だけでなく、権限の過不足、対象ファイルやdigestの指定、SBOM生成の有無、linked artifactsへの記録条件、検証コマンドを実行するタイミングまで決めておく必要があります。artifact attestationsは供給網リスクをなくすものではありませんが、成果物の由来を後から確かめられる状態にし、調査や判断の足場を増やす実用的な仕組みです。
