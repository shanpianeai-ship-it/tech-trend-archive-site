GitHub Actionsセルフホストランナーを個人Macで動かすリスク棚卸し

要約

GitHub Actionsのセルフホストランナーは、自分のMacやローカルサーバーをCI実行環境として使える便利な仕組みである。ローカルのCPU、GPU、特殊なツール、LAN内サービスを使える一方で、GitHub公式は「OSやソフトウェアの更新は利用者責任」「ジョブごとにクリーンなインスタンスになるとは限らない」と説明している。つまり、GitHub-hosted runnerと同じ感覚で、外部PRや未検証のワークフローを個人Macに流すと危ない。

今回のDiscordポールは、該当日のポールメッセージを確認できず、有効票なし扱いにした。候補一覧から、自宅Mac、OpenClaw、GitHub Pages、ローカル秘密情報がつながる可能性が高いこのテーマを自動選定した。

なぜ今見る価値があるか

個人の自動化では、GitHub Actionsでビルドし、ObsidianやPagesの生成物を更新し、必要ならDiscordへ通知する、という流れを作りたくなる。ここでセルフホストランナーを使えば、ローカルにしかないデータや重いビルド環境をそのまま使える。しかしそれは、CIジョブに「自分の作業端末でコマンドを実行する権限」を渡すことでもある。

特に危ないのは、外部由来のコードやメタデータがビルド手順に入る場合だ。GitHub Security Labは、pull_request_target と未信頼PRのチェックアウトを組み合わせると、リポジトリの書き込み権限やシークレットを奪われうると繰り返し警告している。GitHub公式のセキュリティガイドも、pull_request_target や workflow_run を未信頼コードの処理と混ぜないように整理している。

調査メモ

  • GitHub公式は、セルフホストランナーを「利用者がデプロイ、管理するシステム」と定義している。GitHub-hosted runnerより環境を自由にできるが、OSや周辺ソフトウェアの更新、実行環境の維持は利用者側の責任になる。
  • セルフホストランナーは、ジョブごとに必ずクリーンなインスタンスになるわけではない。前ジョブのファイル、キャッシュ、ツール設定、認証情報の痕跡が残る設計だと、次のジョブに影響する。
  • GitHub公式のセキュリティガイドは、シークレットの最小権限、GITHUB_TOKEN の権限制限、ログに出た秘密情報の削除とローテーション、環境シークレットへのレビュー要求を推奨している。
  • 未信頼入力をシェルスクリプトへ直接展開すると、PRタイトルやブランチ名のような文字列でもコマンド注入の入口になる。公式は、可能ならAction化し、インラインシェルでは中間環境変数に入れて引用するやり方を勧めている。
  • pull_request_target と workflow_run は、権限付きコンテキストを扱えるため便利だが、未信頼PRのコードや成果物をそのまま実行するとリポジトリ侵害につながる。GitHub Security Labは、未信頼PRは低権限の pull_request 側で処理し、権限付きワークフローでは成果物をデータとして扱う分離を示している。
  • ラベルやランナーグループは、どのジョブがどのランナーに流れるかを制御するための重要な境界になる。self-hosted だけで広く受けるのではなく、用途別ラベルを付け、想定ジョブだけを流す設計が必要になる。

個人Macで避けたい構成

最も避けたいのは、普段使いのMacを常時オンラインのセルフホストランナーにして、複数リポジトリや外部PRのジョブを受ける構成である。開発用のSSH鍵、GitHubトークン、クラウドCLIの認証、Obsidian vault、ブラウザプロファイル、OpenClaw設定が同じユーザー領域にあるなら、CIジョブはかなり近い場所で動く。

次に危ないのは、pull_request_target で外部PRを受け、actions/checkout でPR側のコードを明示的に取ってビルドする構成である。これはGitHub Security Labが「pwn request」として説明している典型パターンに近い。シークレットや書き込み権限を持つワークフローで、攻撃者が差し込んだビルドスクリプト、テスト、依存関係、インストールスクリプトを実行してしまう。

また、Pages公開や自動コミット用のトークンをランナー上に常置する構成も扱いに注意がいる。GITHUB_TOKEN で足りる範囲はワークフロー内の最小権限に寄せ、個人アクセストークンやローカル秘密鍵は「なぜ必要か」「どのジョブだけが読めるか」「漏れた時に何をローテーションするか」を先に決めるべきである。

使うならこの範囲に絞る

個人Macでセルフホストランナーを使うなら、用途をかなり狭くするのがよい。

  1. 自分だけが書き込むプライベートリポジトリに限定する。
  2. 外部PR、fork PR、未信頼コードのビルドには使わない。
  3. runs-on は self-hosted 単独ではなく、mac-local-pages のような用途別ラベルを必須にする。
  4. ランナー用OSユーザーを普段使いユーザーから分け、ホームディレクトリ、SSH鍵、ブラウザ、Obsidian vaultへ触れないようにする。
  5. ワークフローの permissions は基本 contents: read から始め、必要なジョブだけ最小限に上げる。
  6. シークレットが必要な処理はGitHub Environmentsのレビューや手動実行に寄せる。
  7. ジョブ終了後に作業ディレクトリを消し、残すキャッシュを明示する。
  8. ローカルネットワーク、Docker socket、クラウドCLI認証へ触れるジョブは別ランナーに分ける。

この条件でも、個人Macは「便利なCI資源」ではなく「強い権限を持った実行端末」と考えるべきである。安全側に倒すなら、公開リポジトリや外部PRのCIはGitHub-hosted runner、ローカル限定の重い処理だけを手動トリガーのセルフホストランナーにする分担が扱いやすい。

OpenClaw運用への当てはめ

OpenClawや興味レポートの運用では、ローカルファイルの読み書き、Pages生成、git push、Discord通知が連続する。これをGitHub Actionsのセルフホストランナーへ移す場合、ランナーは単に node scripts/build.mjs を動かすだけでなく、記事原稿、候補一覧、ローカル設定、公開用リポジトリへ近づく。

そのため、現時点での実務的な結論は、セルフホストランナーを常設の自動記事作成基盤にしないことだ。使うとしても、次のような限定用途がよい。

  • Pagesのビルド確認だけを、読み取り専用トークンで実行する。
  • 生成物のpushはローカルCronまたはGitHub-hosted runner側に寄せる。
  • 外部Web調査、Discord入力、Markdown生成をランナー上で混ぜない。
  • ランナー登録情報、ラベル、対象リポジトリ、許可ワークフローを候補一覧や運用ルールと同じように台帳化する。

セルフホストランナーは、ローカル自動化をGitHubから起動できるようにする強力な橋である。ただし、橋をかける相手はGitHubのワークフロー全体であり、PR、Action、依存関係、ログ、成果物まで含まれる。個人運用では、最初から「何でも動かせるMac」ではなく「この1ジョブだけを受ける隔離端末」として設計するのがよい。
