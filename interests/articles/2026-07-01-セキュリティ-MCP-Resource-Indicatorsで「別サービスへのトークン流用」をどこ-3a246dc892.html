Summary

MCP Resource Indicatorsは、OAuthトークンを意図したMCPサーバーだけに縛る仕組み。個人エージェントで外部連携を増やす前に、トークン流用と権限境界を点検する材料になる。

MCP Resource Indicatorsで「別サービスへのトークン流用」をどこまで防げるか

要約

MCPの2025-06-18 Authorization仕様では、HTTPベースのMCP認可にOAuth 2.1、Protected Resource Metadata、Authorization Server Metadata、Dynamic Client Registration、RFC 8707 Resource Indicatorsを組み合わせる形が整理されている。重要なのは、MCPクライアントが認可リクエストとトークンリクエストの両方でresourceパラメータを送り、どのMCPサーバー向けのトークンが欲しいのかを明示する点だ。

今回のポールは有効票がなかったため、候補一覧から重要度、鮮度、個人適合度が高いこのテーマを採用した。個人秘書エージェント環境では、Discord、GitHub、Obsidian、ブラウザ、画像生成、ローカルファイル操作のような権限が一つの作業導線に集まる。MCP連携が増えるほど、「このトークンは本当にこのサーバーだけで使われるのか」「MCPサーバーが受け取ったトークンを下流APIへそのまま流していないか」を見る価値が高くなる。

結論として、Resource Indicatorsはトークン流用対策の中核ではあるが、それだけで完結する防御ではない。認可サーバーがresourceを解釈し、トークンに適切なaudienceを入れ、MCPサーバー側がaudienceを検証し、受け取ったトークンを下流サービスへパススルーしない、という一連の実装がそろって初めて効く。

なぜ今見る価値があるか

MCPは、AIエージェントに外部ツールやデータソースを接続する標準インターフェースとして急速に広がっている。ローカルのSTDIO接続だけなら認証情報を環境変数で渡す設計でも済むが、HTTPベースのリモートMCPサーバー、SaaS連携、企業内ツール、個人用自動化を混ぜ始めると、OAuthトークンの使い回しが現実的なリスクになる。

RFC 8707は、OAuthクライアントがトークンを要求するときに、アクセス先の保護リソースを明示できるようにする拡張である。MCP仕様はこれを取り込み、MCPクライアントにresourceパラメータの送信を求め、MCPサーバーには「自分向けに発行されたトークンか」を検証することを求めている。

この設計がない場合、同じ認可サーバーを信頼する複数のMCPサーバー間で、Server A向けのつもりで得たトークンがServer Bでも受け入れられる可能性がある。さらにMCPサーバーが下流APIの代理になっていると、受け取ったトークンを別のサービスへ転送してしまうconfused deputy型の事故につながる。

調査メモ

MCP Authorization仕様は、認可をHTTPトランスポートのレイヤーで扱う。HTTPベースの実装はこの仕様に従うべきで、STDIOトランスポートはこの方式ではなく環境から資格情報を取得する前提とされている。ここで、protected MCP serverはOAuthのresource server、MCP clientはOAuth client、authorization serverはユーザー同意とトークン発行を担当する存在として整理される。

仕様上、MCPサーバーはOAuth 2.0 Protected Resource Metadataを実装し、401応答ではWWW-Authenticateヘッダーを使ってメタデータURLを示す。MCPクライアントはそのメタデータから対応する認可サーバーを見つけ、Authorization Server Metadataを取得する。複数の認可サーバーがあり得る点は、クライアント実装が雑だと選択ミスやなりすましの入口になる。

Resource Indicatorsの実装では、MCPクライアントが認可リクエストとトークンリクエストの両方にresourceを含める。値はMCPサーバーのcanonical URIで、例としてhttps://mcp.example.comやhttps://mcp.example.com/server/mcpのような絶対URIが想定される。スキームがない値やfragmentを含む値は不適切で、実装間で末尾スラッシュの扱いをそろえることも重要になる。

RFC 8707自体は2020年の標準仕様で、クライアントがどの保護リソースにアクセスするつもりかを認可サーバーへ明示するための拡張である。MCPの新しさは、AIエージェントが複数ツールを動的に扱う場面で、この古典的なOAuth拡張が実務上かなり重要になる点にある。

MCPサーバー側の検証は、署名、期限、スコープだけでは足りない。仕様は、トークンがそのMCPサーバー向けに発行されたものかを検証し、無効または期限切れのトークンには401を返すこと、URIクエリにアクセストークンを入れないこと、MCPクライアントがそのMCPサーバーの認可サーバーから発行されたもの以外のトークンを送らないことを求めている。

WorkOSの解説は、Resource Indicatorsをaudience-bound tokenの仕組みとして説明している。resource=https://api.example.com/mcpのように指定して発行されたトークンは、audienceがそのMCPサーバーに縛られ、別サーバーへ提示された場合は拒否されるべき、という整理だ。ここは個人運用でも理解しやすい。

Auth0のMCP認可アップデート解説も、MCPの認可まわりが仕様として整備されてきた背景を扱っている。ベンダー解説は実装者目線の補助資料として使えるが、最終判断はMCP仕様、RFC 8707、利用中の認可プロバイダの実装仕様で確認するのが安全である。

個人向けの読みどころ

個人のOpenClaw運用に落とすなら、見るべきポイントは「MCPを使うかどうか」ではなく「トークンがどの境界で止まるか」だ。ローカルファイル、Discord送信、GitHub push、Obsidian編集、Webブラウザ操作、画像生成の権限は、それぞれ別のリスクを持つ。MCPサーバーを増やすほど、権限境界を図にしておかないと、便利な一体運用がそのまま一体侵害になる。

実用チェックは次の粒度がよい。

  • MCPクライアントは、認可リクエストとトークンリクエストにresourceを必ず入れているか。
  • MCPサーバーは、自分のcanonical URIとトークンのaudienceを照合しているか。
  • 認可サーバーはresourceを無視せず、発行トークンを対象リソースへ縛っているか。
  • 受け取ったユーザートークンを、MCPサーバーが下流APIへそのまま転送していないか。
  • GitHub、Discord、ファイル操作、ブラウザ操作など、外部影響の大きい権限を同じトークンや同じ承認段階にまとめていないか。
  • ログ、Obsidian本文、Pages公開物、Discord報告にトークンや内部URLが混ざらないか。
  • 新しいMCPサーバーを追加したとき、canonical URI、認可サーバー、スコープ、下流API、ログ保存先を1行でも記録しているか。

個人エージェントでは、企業向けのIAMほど重い仕組みを入れるより、接続ごとに「どこから来たトークンか」「どこまで使えるか」「どこへ転送されるか」を表にする方が効く。特に自動化cronは、読み取り、Markdown生成、ビルド、git push、Discord報告のように外部操作まで連鎖するため、MCPサーバー追加時の棚卸し対象に含めた方がよい。

注意点

この記事はセキュリティ設計の観察メモであり、特定環境への侵入手順や攻撃コードを扱うものではない。実装確認では、利用中のMCP SDK、認可プロバイダ、ゲートウェイ、リバースプロキシ、ログ基盤の公式資料を優先する。

Resource Indicatorsは万能ではない。認可サーバーがresourceを処理しない、MCPサーバーがaudienceを検証しない、canonical URIが揺れる、下流APIへトークンをパススルーする、といった実装なら防御は崩れる。また、トークン窃取そのもの、過大なスコープ、長すぎる有効期限、ログ漏えい、MCPツール側のプロンプトインジェクションは別途対策が必要になる。

個人環境では「ローカルだから安全」と見なすのも危ない。ブラウザ、拡張機能、ローカルWeb UI、MCPテストエンドポイント、同期フォルダ、Pages公開処理がつながると、ローカルの秘密が外部に出る経路は意外に多い。まずは外部公開しない、短命トークンにする、権限を分ける、ログへ秘密を残さない、公開前にビルド成果物を確認する、という基本を優先したい。
