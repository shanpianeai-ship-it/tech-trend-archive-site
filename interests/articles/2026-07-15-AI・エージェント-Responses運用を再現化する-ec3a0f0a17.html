Summary

Responses APIで短尺回答と調査ノート作成を分離すると、同日1本選定でも再現性と監査性が上がる。

Responses運用を再現化する

要約

短尺の即時回答は Responses API で低コスト・低待機時間のモデルを使い、調査・レポート生成は長文に強く再現性を優先するモデルへ分岐させると、Cron運用が安定する。 同じテーマで毎日記事を1本生成する運用では、失敗時の再実行条件が曖昧になるとノイズが増えやすく、役割を明確化する価値が高い。

なぜ今見る価値があるか

この自動化では「毎日1本」「同日重複なし」「選定は投票または運用ロジック」といった条件で走るため、生成の経路がぶれやすい。 Responses APIの運用を分離しておくと、次の点で価値がある。

  • 運用ログが明確になる: どちらの目的でどのモデルを呼んだかを記録できる。
  • 回復が速い: 1段階が失敗しても他方を切り出して再実行しやすい。
  • 監査しやすい: 参照元・採点ロジック・最終保存ファイルを1本の責務に閉じられる。

今回、当日のDiscord投票は有効票が集まらなかったため、候補1を採用し、実装コストが低い分離設計を検証対象にした。

調査メモ

1. 回答責務と調査責務の境界を固定する

  • 回答レイヤー: 既知の既存知識ベース＋最短回答。
  • 調査レイヤー: 公式情報の確認、リンク根拠の確認、要約→保存の一連を厳密化。
  • 乱数・温度・tool許可の制約を同じにしない。

2. Responses の入力制御で再現性を上げる

  • 入力は「命令」「参照方針」「フォーマット制約」「失敗時の代替パス」を分離する。
  • 調査モデルには tool 実行を絞る。read-only 前提で収集・要約する方針を初期化時に固定。
  • 調査時に publish: true の保存判断と source_count を必ず埋め、記事が1件化した時に追跡できるようにする。

3. 監査ログの最小セットを毎回更新

  • 選定根拠（poll ID / 選定番号）を候補一覧の frontmatter に残す。
  • 保存先は 興味/<カテゴリ>/YYYY-MM-DD_タイトル.md に固定。
  • build後の出力URLとコミット有無を結果チャネルへ返却。

4. 過剰調査を避けるための収束条件

  • 3つの一次情報観点だけを採る。
  • 公式Docsの運用方針
  • tool呼び出しの境界管理
  • 安全設定の既定値
  • ここを逸脱しないことで1本記事の範囲を過不足なく保つ。

個人向けの読みどころ

  • Cron運用は「回答品質」より「再現可能性」を上げる設計が効く。
  • Responses APIの役割分離は、1日の意思決定を速くするだけでなく、次回失敗時の切戻し基準を作る。
  • 同じ選定ロジックでも selected_answer を残すと、後で選定履歴を比較しやすく、build 失敗時の原因切り分けが早くなる。

注意点

  • tool呼び出し結果は公開前に伏せ字ルールに通す。記事公開側では金額・住所・個人識別情報を残さない。
  • 「実行速度」だけを評価軸にすると、参照元の一次性が落ちる。
  • pollを参照するcronは、投票ゼロ時でも候補ルールが必ず成立する形にしておく。
