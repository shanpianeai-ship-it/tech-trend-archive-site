Summary

npmの長期トークン、install script、依存更新を、Codex/OpenClawのローカル実行環境でどう閉じ込めるかを整理する。AIコーディング環境の点検表として使える。

npm防御をCodex環境へ落とす

要約

今回のDiscordポールは、指定された poll_message_id の poll.results.answer_counts が空で、有効票なしだった。そのため候補一覧から、ローカルのAIコーディング環境に直接効く「npm防御をCodex環境へ」を選定した。

npmのサプライチェーン防御は、公開パッケージ作者だけの話ではない。CodexやOpenClawがローカルで npm install、npm run build、node scripts/build.mjs を実行する環境では、依存パッケージのinstall script、漏れたnpm token、広すぎる環境変数、無造作な更新がそのまま作業端末のリスクになる。対策は「npmを使わない」ではなく、トークンを短命化し、publish権限をCIへ寄せ、インストール時の実行を疑い、AIエージェントに渡す作業ディレクトリと秘密情報を小さくすることだ。

なぜ今見る価値があるか

npm公式ドキュメントでは、2025年11月以降はgranular access tokenのみがサポートされ、legacy access tokenは削除済みと説明されている。granular tokenは、対象パッケージやスコープ、組織、期限、IP範囲、read-only/read-writeを絞れる。つまり、まだ古い感覚で「npm tokenをCIやローカルに長く置く」運用をしているなら、現行のnpm側の設計思想とずれている。

さらにnpmは、trusted publishingでOIDCを使い、GitHub Actions、GitLab CI/CD、CircleCIなどのワークフローから長期npm tokenなしでpublishできるようにしている。npm docsは、trusted publishingを「長期write tokenのリスクをなくす」仕組みとして説明している。GitHubもnpm package provenanceを、パッケージをソースリポジトリとビルド手順へ検証可能に結びつける仕組みとして紹介している。

Codex環境で重要なのは、この流れを「自分がpublishするパッケージ」だけでなく、「日々AIに触らせるローカル開発環境」へ翻訳することだ。AIエージェントは便利だが、コマンドを代行する以上、悪意あるinstall scriptや過大な環境変数に対しては普通の開発者端末より事故が速く進む。

Codex環境でのリスク

第一に、長期npm tokenの露出である。.npmrc、CIのsecrets、シェルの環境変数、過去ログ、スクリーンショット、プロンプト添付にwrite tokenが残っていると、AIが直接使わなくても作業中に読み取れる範囲へ入る。特にpublish権限と2FA bypassを持つtokenは、流出時の影響が大きい。

第二に、install scriptである。npmパッケージは、preinstall、install、postinstall などで任意の処理を走らせられる。依存追加やクリーンインストールをAIに任せると、ユーザーがpackage.jsonを読む前にローカルコマンドが動く可能性がある。

第三に、AIエージェントの作業範囲が広すぎる問題である。npm install 自体の危険だけでなく、同じプロセスがGitHub token、Discord token、Pages repo、Obsidian vault、SSH agent、クラウド認証情報を見られる状態だと、依存パッケージのスクリプトが触れる範囲も広がる。

まずやる設定

個人のnpm publish運用では、可能ならtrusted publishingへ寄せる。GitHub Actionsなどの対応CIでpublishできるパッケージは、長期npm write tokenを置かず、OIDCで短命な認証へ移す。provenanceを付けられるパッケージは、ビルド元と手順を追えるようにする。

tokenが必要な場合も、granular tokenを使い、read-onlyを基本にする。write tokenは対象パッケージ、期限、IP範囲を絞り、2FA bypassは本当に必要なpublish経路だけにする。ローカルMacの普段使いシェルにwrite tokenを常駐させない。

Codex/OpenClawでnpmを触る時は、環境変数の棚卸しを先に行う。NPM_TOKEN、GitHub PAT、クラウド鍵、Discord bot token、OpenAI API keyなどを、不要な作業ディレクトリやサブプロセスに渡さない。AIがnpm installを実行する作業では、publish用の秘密情報を同じ環境に置かないのが基本になる。

依存追加時のチェック

依存を追加する時は、パッケージ名だけで判断しない。少なくとも、公式リポジトリ、npm上のprovenance表示、公開元、最近のpublish履歴、install scriptの有無、依存数、メンテナ変更の有無を見る。小さなユーティリティほど代替が簡単なので、依存を増やす価値があるかも確認する。

既存プロジェクトでは、lockfile差分を見る。AIが package-lock.json を大きく更新した場合、直接追加した1パッケージ以外に何が増えたかを確認する。ビルドが通ることと、依存更新が安全であることは別の話だ。

npm install --ignore-scripts は万能ではないが、未知の依存を調べる最初の段階では有効なブレーキになる。必要なnative buildやpostinstallがある場合は、なぜ必要かを確認してから通常installへ戻す。CIや本番ビルドで必要なscriptまで壊さないよう、恒久設定にする前にプロジェクト単位で判断する。

AIエージェント向けの運用線引き

Codexにnpm作業を任せる時は、次の線引きが現実的だ。

  1. 依存追加前に、目的と候補パッケージを短く説明させる。
  2. 初回調査では公式docsや既存コードを読み、すぐinstallしない。
  3. installが必要な場合、不要な秘密情報を外した環境で実行する。
  4. lockfile差分、install script、増えた依存の数を確認する。
  5. publish、npm login、token作成、2FA bypass変更はAIに実行させない。
  6. Pages生成やローカルbuildのような低リスク作業と、npm publishのような高リスク作業を同じ自動化に混ぜない。

このレポートを書いている興味レポート運用も、node scripts/build.mjs とgit pushを日次で実行する。ここに依存追加やnpm updateを混ぜると、記事公開Cronがパッケージ更新経路にもなってしまう。公開ビルドCronは、既存依存で生成するだけに留め、依存更新は別作業として扱う方がよい。

自分用チェックリスト

  • npm publishはtrusted publishingへ寄せられるか。
  • ローカル .npmrc にwrite tokenが残っていないか。
  • tokenはgranular、期限付き、対象限定、read-only基本になっているか。
  • 2FA bypass付きtokenを普段のCodex環境に置いていないか。
  • AIに渡すシェル環境から不要な秘密情報を外しているか。
  • 新規依存のinstall scriptを確認したか。
  • lockfile差分をレビューしたか。
  • Cronや自動ビルドの中で依存更新をしない設計になっているか。
