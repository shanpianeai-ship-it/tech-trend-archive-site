Mac mini上でObsidianを使ったレポート管理方法・ベストプラクティス調査

Summary

Mandayのレポート管理は、[内部パス] をObsidian Vaultとして開くか、将来的な拡張を考えて ~/Documents/MandayVault/ のような専用Vaultを作り、その中に Reports/ を置く構成が現実的です。現時点では「隠しフォルダを避けて見つけやすくする」という要件が強いため、短期的にはDesktopの report フォルダをそのままVault化するのが最短です。

ただし、長期運用では 専用Vault + Reports/ 配下にレポート格納 + YAML Properties + タグ + 内部リンク + 定期バックアップ がベストです。ObsidianはMarkdownファイルをローカルフォルダに保存するため、Mandayが生成するMarkdownレポートとの相性は非常に良いです。

結論

  • 短期推奨: [内部パス] をObsidianのVaultとして開き、既存レポートをそのまま管理する。
  • 中長期推奨: ~/Documents/MandayVault/Reports/ へ移行し、Reports/, Topics/, Templates/, Attachments/, Indexes/ で管理する。
  • レポートは今後も YAML frontmatter / Properties付きMarkdown で出力する。
  • タグは増やしすぎず、research, report, real-estate, pokemon-card, ops, obsidian など大分類を中心にする。
  • 詳細分析のインプット用途では、各レポートに source_task, area, asset_type, status, created, updated, tags を持たせると再利用しやすい。
  • Syncはバックアップではない。Mac miniを主端末として、Time Machine/Git/ローカルバックアップのいずれかを別途用意するべき。
  • 現在のMac miniでは obsidian-cli は入っているが、Obsidian本体の設定ファイルは見つからず、/Applications/Obsidian.app も未検出。実装前にObsidian本体のインストール・Vault作成が必要。

Findings

1. Obsidianの基本仕様: Vaultは普通のフォルダ

ObsidianはノートをMarkdown形式のプレーンテキストとしてVault内に保存します。Vaultはローカルファイルシステム上の通常フォルダで、サブフォルダも含みます。外部エディタやスクリプトでMarkdownを編集しても、Obsidian側が変更を追従します。

このため、Mandayのレポート出力先をVault内に置けば、特別なDB連携なしにObsidian管理へ移行できます。

注意点:

  • Vault内にさらにVaultを作るのは避ける。内部リンク更新が正しく動かない可能性がある。
  • Vault直下に .obsidian/ が作られ、テーマ・プラグイン・ワークスペースなどVault固有設定が入る。
  • .obsidian/workspace.json などは頻繁に更新されるため、Git管理する場合は除外候補。

2. 推奨Vault構成

案A: 最短構成 — [内部パス]

``text [内部パス] ├── 2026-04-28-research-....md ├── 2026-04-29-research-....md └── .obsidian/ ``

メリット:

  • 今の保存先を変えずに済む。
  • Finderから見つけやすい。
  • Manday側の変更が少ない。

デメリット:

  • レポート以外のメモ、テンプレート、添付、索引が増えると散らかる。
  • Desktop直下は誤操作や整理対象になりやすい。
  • 将来、レポート以外の知識管理もしたくなった時に狭い。

向いているケース:

  • まずObsidianでレポートを開いて検索・閲覧できればよい。
  • 実装を小さく始めたい。

案B: 推奨構成 — 専用Vaultを作る

``text [内部パス] ├── Reports/ │ ├── RealEstate/ │ ├── PokemonCards/ │ ├── Ops/ │ └── Misc/ ├── Topics/ │ ├── 不動産投資.md │ ├── 台東区.md │ └── Obsidian運用.md ├── Indexes/ │ ├── Reports Index.md │ └── Research Queue Index.md ├── Templates/ │ └── Report Template.md ├── Attachments/ └── .obsidian/ ``

メリット:

  • レポート以外の知識ノート、索引、テンプレート、添付を自然に追加できる。
  • 長期運用・検索・バックアップ・Git管理がしやすい。
  • ObsidianのGraph view、内部リンク、Propertiesを活かしやすい。

デメリット:

  • 現在の [内部パス] から移行が必要。
  • 個人さんがFinderで探す場所が変わる。

推奨判断:

  • 今すぐ運用開始: 案A
  • 本格運用・自動化実装: 案B

3. レポートMarkdownの標準フォーマット

Mandayのレポートは、今後もObsidian Propertiesとして読めるYAML frontmatterを先頭に置くべきです。

推奨Properties:

```yaml --- title: 東京都台東区入谷エリア不動産投資概況 created: 2026-04-29 updated: 2026-04-29 type: report status: done source_task: research-20260429-002 category: real-estate area: 東京都台東区入谷 asset_type:

  • 区分マンション
  • 一棟アパート
  • 戸建

tags:

  • research
  • report
  • real-estate
  • taito
  • iriya

related:

  • "[[不動産投資]]"
  • "[[台東区]]"

--- ```

ポイント:

  • Propertiesは小さく、機械可読な値に寄せる。
  • Markdown本文の要約・結論・Findingsは本文に書く。
  • tags はObsidian標準のタグとして使う。
  • 内部リンクをPropertiesに入れる場合は "[[リンク名]]" のように引用符を付ける。
  • source_task はMandayのキューIDと接続するキーとして重要。

4. タグ設計

タグは増やしすぎると破綻するため、次の3層程度に抑えるのがよいです。

共通タグ

  • research
  • report
  • summary
  • draft
  • done

領域タグ

  • real-estate
  • pokemon-card
  • ops
  • ai
  • obsidian

補助タグ

  • tokyo
  • taito
  • arakawa
  • investment
  • market-research

避けたいタグ:

  • 長すぎるタグ
  • 日本語・英語が混在して同じ意味のタグが乱立する状態
  • 物件名やカード名など粒度が細かすぎるタグ

細かい対象名はタグではなくPropertiesまたは内部リンクに寄せるのがよいです。

5. 内部リンクと索引ノート

Obsidianの強みは内部リンクです。レポート本文末尾に Related セクションを置き、関連テーマへリンクします。

例:

```markdown

Related

  • [[不動産投資]]
  • [[台東区]]
  • [[入谷]]
  • [[中古戸建投資]]

```

加えて、索引ノートを作ると後から見返しやすくなります。

例: Indexes/Reports Index.md

```markdown

Reports Index

不動産投資

  • [[2026-04-28-research-20260428-004-[具体地名伏せ]中古戸建不動産投資方針-物件-費用感調査]]
  • [[2026-04-29-research-...-東京都台東区入谷...]]

運用

  • [[2026-04-29-research-20260429-001-Mac-mini上でObsidianを使ったレポート管理方法-ベストプラクティス調査]]

```

Obsidianはファイル名変更時に内部リンクを自動更新できます。スクリプトでファイル移動・リネームをする場合は、単純な mv よりObsidian CLIやObsidian内操作を使うとリンク保全の面で安全です。

6. 検索・絞り込み方針

実装上は、以下で探せるように設計するとよいです。

  • ファイル名: YYYY-MM-DD-task-id-title.md
  • Properties:
  • source_task
  • type
  • status
  • category
  • area
  • asset_type
  • タグ:
  • #real-estate
  • #pokemon-card
  • #obsidian
  • 本文見出し:

ObsidianのPropertiesは検索にも使えるため、後で「不動産」「台東区」「done」「2026年4月作成」のような絞り込みがしやすくなります。

7. obsidian-cli / 自動化

現在Mac miniにはコミュニティ版の obsidian-cli が入っています。

確認結果:

``text /opt/homebrew/bin/obsidian-cli ``

主な機能:

  • create: ノート作成
  • search: ノート名検索
  • search-content: 本文検索
  • move: ノート移動・リネーム、リンク更新
  • frontmatter: frontmatter閲覧・変更
  • print-default: デフォルトVault確認
  • set-default: デフォルトVault設定

ただし現時点では default vault が未設定です。

``text Cannot find vault config, please use set-default command to set default vault or use --vault flag ``

実装方針:

  1. Obsidian本体をMac miniにインストールする。
  2. Vaultを作る。
  3. obsidian-cli set-default "<vault-folder-name>" でデフォルトVaultを設定する。
  4. Mandayのレポート作成後、必要に応じて obsidian-cli search-content や frontmatter を使う。
  5. ファイル移動・リネームは可能なら obsidian-cli move を使う。

補足:

  • Obsidian公式にもCLI機能がありますが、利用にはObsidian本体側でCLIを有効化する必要があります。
  • 現在入っている obsidian-cli はコミュニティ版で、OpenClawのobsidian skillもこのCLIを前提にしています。
  • 実装では「直接Markdownを書き込む」だけでも十分動きます。CLIは検索・移動・リンク更新の補助として使うのが安全です。

8. バックアップと同期

Obsidianの公式ドキュメントでは、SyncとBackupは別物とされています。Syncは複数端末間で最新状態を揃えるための仕組みで、データ消失や破損に備える専用バックアップではありません。

推奨:

  • Mac miniを「主バックアップ端末」と位置づける。
  • 最低限、Time Machineまたは別ディスクへの定期バックアップを設定する。
  • 可能ならGitでVaultをバージョン管理する。
  • Git管理する場合、.obsidian/workspace.json と .obsidian/workspaces.json は変更頻度が高いため .gitignore 候補。
  • Obsidian Sync/iCloud/Dropbox等を使う場合でも、別途一方向バックアップを持つ。

9. Manday実装への落とし込み

Phase 1: 現行フォルダをVault化

  • Obsidianをインストール。
  • [内部パス] をVaultとして開く。
  • Mandayの保存先は現状維持。
  • 既存レポートのYAML frontmatterを必要に応じて正規化。
  • Reports Index.md を作成する。

Phase 2: レポート出力ルールを標準化

  • task-queue/PROCESSING.md のテンプレートに以下を追加:
  • category
  • source_task
  • related
  • 任意で area, asset_type, topic
  • レポート末尾の Related を必須化。
  • Sourcesを必ずMarkdownリンクで管理。

Phase 3: 専用Vaultへ移行

  • ~/Documents/MandayVault/ を作成。
  • Reports/, Topics/, Indexes/, Templates/, Attachments/ を作成。
  • 既存 [内部パス] を Reports/ へ移動。
  • queue_task.py の REPORTS_DIR を ~/Documents/MandayVault/Reports へ変更。
  • Obsidian CLI default vault を設定。

Phase 4: 自動索引・検索補助

  • レポート作成後に Indexes/Reports Index.md を自動更新。
  • source_task からキュー状態に戻れるようにする。
  • category ごとの索引を自動生成。
  • obsidian-cli search-content で過去レポートを検索し、類似調査の再利用を可能にする。

10. 推奨実装案

現時点での最適解は以下です。

```text 短期: [内部パス] をObsidian Vault化

中期: [内部パス] Index.md を追加 レポートfrontmatterを標準化

長期: [内部パス] に移行 GitまたはTime Machineでバックアップ Obsidian CLIで検索・リンク保全・索引更新を自動化 ```

この順番なら、個人さんが今すぐレポートをFinder/Obsidianで見られる利便性を保ちつつ、将来的な知識管理Vaultへ自然に移行できます。
