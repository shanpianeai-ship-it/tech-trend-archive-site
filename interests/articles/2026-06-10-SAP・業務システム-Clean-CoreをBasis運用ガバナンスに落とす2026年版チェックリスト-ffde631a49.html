Clean CoreをBasis運用ガバナンスに落とす2026年版チェックリスト

要約

SAPのClean Coreは、単に「標準改修を減らす」「BTPへ逃がす」という技術スローガンではなく、2026年時点ではBasis/運用チームが日々の変更管理に組み込むべきガバナンス項目として見る方が実務に効く。

SAP公式はClean Coreを、ERPを俊敏で費用対効果が高く、継続的なイノベーションを取り込める状態に保つための戦略として説明している。5つの原則は、プロセス、拡張性、データ、インテグレーション、オペレーション。Basis目線では、このうち拡張性だけでなく、データ、連携、運用まで含めて「リリースのたびに壊れにくい変更か」「標準アップグレードを妨げないか」「誰が例外を承認したか」を記録する仕組みに落とす必要がある。

結論として、Clean Core運用は次の6点を最低ラインにする。

  1. カスタムオブジェクトと拡張を棚卸しする。
  2. 新規開発はReleased API、ABAP Cloud、Key User Extensibility、Side-by-Sideを優先する。
  3. ATCのClean Core系チェックを開発時と移送前に実行する。
  4. SAP Cloud ALMまたは同等の台帳でClean Core状態を可視化する。
  5. 例外は期限、理由、代替案、撤退条件つきで承認する。
  6. リリース影響分析を、技術部門だけでなく業務オーナーへ説明できる形にする。

なぜ今見る価値があるか

2026年のS/4HANA移行やRISE with SAPの文脈では、Clean Coreは移行プロジェクトの設計原則から、移行後の運用品質を測る物差しに変わっている。投票では 2. Clean Core運用チェックリスト に1票が入り、afternoon枠の最多票だった。

重要なのは、Clean Coreを「開発標準」だけに閉じないこと。SAP公式のERP Clean Coreページでは、標準プロセス、モダンな拡張、信頼できるデータとAI、標準化された連携、運用ガバナンスをまとめて扱っている。つまりBasis担当者が見るべき対象は、Zプログラムだけではない。ICF/OData/API、RFC、ジョブ、権限、データ増加、監視、移送、例外承認まで含めた運用設計になる。

個人向けには、SAP BasisのYouTube/記事ネタとしても使いやすい。「Clean Coreとは何か」ではなく、「Basis担当者は明日から何を台帳化し、どの会議で何を止めるべきか」に落とせるから。

調査メモ

1. Clean Coreは5原則で見る

SAP公式のERP Clean Core Strategyでは、Clean Coreを継続的な業務変革と近代化を支える原則群として扱っている。FAQでは、5つの guiding principles として、Processes、Extensibility、Data、Integrations、Operations が挙げられている。

Basis運用に翻訳すると、次のようになる。

原則Basis運用で見るもの失敗パターン
Processes標準プロセスからの乖離、業務アドオン、例外運用業務都合の小改修が恒久化する
ExtensibilityReleased API、BAdI、Key User、Developer、Side-by-Side未リリースAPIや改修が増える
Dataマスタ品質、データ増加、保持期間、アーカイブ移行・AI活用・性能問題で詰まる
IntegrationsAPI、RFC、IDoc、イベント、認証、監視点対点連携が増え、影響範囲が読めない
Operations監視、移送、権限、変更管理、例外承認Clean Coreがプロジェクト標語で終わる

ここでのポイントは、Basisが「開発方式を決める人」ではなくても、「変更を本番へ入れてよい状態か」を判定するゲートキーパーにはなれること。Clean Coreは設計思想だけでなく、移送前チェック、月次レビュー、リリース前影響分析の入力にする。

2. 拡張方式は「どこに作るか」より「アップグレード時に壊れにくいか」で見る

SAP公式のClean Core extensibility資料は、必要な拡張を許しつつ、スムーズなアップグレードと拡張管理を可能にすることを目的としている。Private Edition向け資料でも、ABAP Cloud開発モデル、既存カスタムコードの変換、ABAP Test Cockpitによるガバナンスが扱われている。

Basis運用の判断軸は、次の順番でよい。

  1. 標準機能や設定で吸収できるか。
  2. Key User Extensibilityで足りるか。
  3. Released API/BAdI/CDS view/RAPなど、公開された拡張ポイントで実装できるか。
  4. Side-by-Sideで切り離す方がよいか。
  5. Classic ABAPや内部オブジェクト参照が必要なら、例外管理に入れるか。

「BTPならClean Core」という単純化は危ない。Side-by-Side化しても、連携が密結合、認証が属人化、監視が抜ける、障害時の責任境界が曖昧なら、汚れは別の場所へ移動しただけになる。逆にオンスタックでも、Released APIとABAP Cloudの制約を守り、ATCで継続確認できるなら、運用上は管理しやすい。

3. ATCを移送ゲートにする

SAP LearningのClean Core development教材では、ABAP Cloud開発やClean Coreチェックに関連するATC check variantが説明されている。特に、ABAP_CLOUD_DEVELOPMENT_DEFAULT、ABAP_CLOUD_READINESS、Released API、Classic API、Internal Object、Not Recommendedを分けるClean Core向けカスタムvariantの考え方は、Basis運用にそのまま使える。

運用チェックとしては、次の形にする。

タイミング実行することBasisが確認する証跡
開発開始使用予定API、拡張方式、パッケージ方針を確認設計書、API根拠、例外有無
開発中ATCを定期実行ATC結果、未解消finding
移送前Priority 1/2やClean Core違反を確認移送番号、ATC実行結果、免除申請
本番前影響範囲、ロールバック、監視項目を確認リリース判定メモ
リリース後ジョブ、連携、性能、エラーを監視Cloud ALM/監視ログ

例外はゼロにできない。だから「誰が承認したか」「いつ見直すか」「次のリリースで置き換える候補は何か」を残す。例外を記録しないClean Core運用は、時間が経つと単なる精神論になる。

4. SAP Cloud ALMのClean Coreビューは運用会議の材料にする

SAP Help PortalのCloud ALM System Viewは、software stack、extensibility、data、integration KPIに基づいてClean Core complianceを概観できると説明している。Operations Viewはoperations principleに基づくClean Core complianceを扱う。ExtensibilityやCustomer Objectsの画面では、カスタムコード分布やClean Core complianceの深掘りができる。

これは「ダッシュボードを眺める」ためではなく、月次またはリリース前の運用会議に使うもの。Basisが見るべき問いは次の5つ。

  • カスタムオブジェクトは増えているか、減っているか。
  • 未リリースAPI参照や内部オブジェクト参照はどこに残っているか。
  • データ量や連携数の増加が、性能・監視・障害対応を難しくしていないか。
  • 次回アップグレードで影響を受けそうな拡張はどれか。
  • 例外が「期限切れの恒久例外」になっていないか。

Cloud ALMがない環境でも、同じ観点をExcelやObsidianで台帳化できる。ただし、手作業台帳にするなら、更新責任者、更新タイミング、移送番号との紐づけを決めないとすぐ腐る。

5. 2026年版Basisチェックリスト

Clean CoreをBasis運用へ落とすなら、チェックリストはこれくらい具体化した方がよい。

項目確認内容NGならどうするか
拡張方式標準、Key User、Developer、Side-by-Side、Classic ABAPのどれか理由を設計書へ追記
APIReleased APIまたは公式拡張ポイントか代替APIを探す。なければ例外申請
カスタムコードATC結果、Cloudification Repository、未解消findingPriorityに応じて移送停止または条件付き承認
改修・コピーSAP標準オブジェクト改修、コピー、暗黙enhancement撤退計画をつける
連携点対点、RFC、IDoc、OData、イベント、認証方式監視と責任分界を追加
データテーブル増加、保持期間、アーカイブ、削除方針性能・保守計画に入れる
権限新規ロール、技術ユーザー、過剰権限SoD/監査観点でレビュー
運用監視、ジョブ、エラー通知、問い合わせ先運用設計がない変更は本番投入しない
例外理由、期限、承認者、代替案期限なし例外を認めない
アップグレード次回リリース影響、テスト観点リリース前テストに入れる

Basis担当者が強く見るべき赤信号は、未リリースAPI、SAP標準改修、コピー改修、監視のないSide-by-Side、責任者不明の技術ユーザー、期限なし例外。この6つは、後でアップグレードや障害対応の負債になりやすい。

個人向けの読みどころ

個人向けの一番おいしい切り口は、「Clean Coreを開発者向けのきれいごとで終わらせない」こと。Basis実務では、開発チームに対して次のように聞けると強い。

  • この変更は標準機能では吸収できない理由がありますか。
  • 使っているAPIはReleased APIですか。
  • ATCの結果と未解消findingを見せられますか。
  • 本番後の監視項目と障害時の切り戻しはありますか。
  • 例外なら、いつ解消する予定ですか。

動画や記事にするなら、タイトルは「Clean Coreとは何か」より「Basis担当者がClean Coreで止めるべき変更10選」の方が刺さる。RISE with SAPやS/4HANA Cloud Private Editionでも、顧客側に残る責任は消えない。むしろ、ベンダー管理範囲と顧客管理範囲を分けて、変更理由、例外、監視、業務影響を説明する仕事が重くなる。

注意点

  • この記事は公開情報をもとにした運用整理メモであり、個別SAP環境への適用指示ではない。
  • SAP Notes、保守契約、Cloud/Private Cloud/On-Premiseの責任分界、社内変更管理を優先する。
  • SAP Community記事の一部はブラウザ上でJavaScript/認証確認が必要だったため、本文ではSAP公式サイト、SAP Help Portal、SAP Learning、公開検索で確認できた範囲を中心に整理した。
  • Clean Coreの成熟度やATC variantは、利用しているS/4HANAリリース、ABAP Platform、BTP ABAP Environment、契約条件で変わる。導入環境の公式HelpとSAP Noteを必ず確認する。
  • Side-by-SideやBTP採用は万能ではない。連携、認証、監視、費用、障害時責任を合わせて設計する必要がある。
