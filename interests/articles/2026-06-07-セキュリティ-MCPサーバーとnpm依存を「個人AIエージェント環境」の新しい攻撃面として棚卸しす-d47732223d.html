MCPサーバーとnpm依存を「個人AIエージェント環境」の新しい攻撃面として棚卸しする

要約

OpenClaw、Codex、Claude Code、Cursor、WindsurfのようなAIエージェント環境では、従来の「アプリの依存ライブラリ」だけでなく、MCPサーバー、ローカル設定ファイル、シェル実行権限、GitHub/npm/クラウド資格情報、DiscordやObsidianなどの連携先がまとめて攻撃面になる。

2026年春から初夏にかけて、MCPそのものの設計・実装リスクと、npm供給網攻撃がAIコーディングツールを狙う動きが重なって見えてきた。Microsoftは2026年6月2日、Red Hat系npmスコープの32パッケージ・90超バージョンが改ざんされ、preinstallフックから資格情報を盗むMiasmaキャンペーンを分析している。Endor Labsは2026年2月、typosquat npmパッケージがローカルに悪性MCPサーバーを登録し、AIコードアシスタント経由でSSHキーやAWS資格情報を読ませるSANDWORM_MODEを報告した。

結論として、個人AIエージェント環境は「便利なローカル秘書」ではなく、「自分の開発機、Obsidian、GitHub、公開サイト、メッセージングを横断できる自動化基盤」として棚卸しすべきである。MCPサーバーは依存パッケージと同じく管理対象に入れ、インストール元、権限、設定ファイル、起動方法、通信先、秘密情報の置き場所を定期点検するのが現実的な防御ラインになる。

なぜ今見る価値があるか

今見る価値は、攻撃者が「AIエージェントの入り口」を実際に狙い始めている点にある。

MicrosoftのMiasma分析では、改ざんされたnpmパッケージが正規のGitHub Actions OIDC公開フローを通って配布され、見かけ上は真正なprovenance署名を持っていた。インストール時にはnpmのpreinstallフックが自動実行され、GitHub、npm、AWS、Azure、GCP、Vault、Kubernetes、SSH、ブラウザ、ウォレットなどの資格情報を狙う。これは「怪しい野良スクリプトを実行したら危ない」ではなく、「正規に見える依存を更新しただけで開発機とCI/CDが危ない」という話である。

Endor LabsのSANDWORM_MODE報告では、npmマルウェアがAIコードアシスタントのローカル設定へ悪性MCPサーバーを登録し、プロンプトインジェクションを使ってAI側に秘密情報を読ませる流れが示されている。つまり、攻撃者はnpm、MCP、AIアシスタント、ローカルファイルを1本の攻撃経路として扱っている。

さらに公式MCPドキュメントも、Confused Deputy、Token Passthrough、SSRF、Session Hijacking、Local MCP Server Compromise、Scope Minimizationを主要なセキュリティ論点として挙げている。これはMCPが単なる便利プロトコルではなく、認可、セッション、外部API、ローカル実行をまたぐセキュリティ設計対象だということを意味する。

調査メモ

個人環境で最初に見るべき攻撃面は、大きく5つに分けられる。

1つ目は、MCPサーバーのインストール元と起動方法。npx、uvx、ローカルclone、Docker、Homebrew、npm global installなど、どの経路で起動しているかを一覧化する。毎回ネットワークから最新コードを取る形は便利だが、供給網攻撃の影響を受けやすい。固定バージョン、lockfile、ローカルclone、Dockerイメージのdigest固定を使えるものは使う。

2つ目は、MCP設定ファイル。Claude Desktop、Claude Code、Cursor、Windsurf、Continue、OpenClaw系の設定には、サーバー名、command、args、env、接続先URL、APIキーが集まる。ここに身に覚えのないサーバー、過剰なenv、0.0.0.0待受、広すぎるファイルアクセスがないかを見る。

3つ目は、npm依存とスクリプト実行。Miasmaのようなpreinstallフック、SANDWORM_MODEのようなtyposquat、悪性MCP注入は、npm install や npm update のタイミングで入ってくる。特にAIツール、MCPサーバー、CLI補助ツール、テンプレート生成系は、開発機の資格情報に近い場所で動くため、通常のフロントエンド依存より警戒度を上げる。

4つ目は、秘密情報の置き場所。MCP設定にAPIキーを直書きする、.envを広く読める場所に置く、GitHub tokenやnpm tokenを長寿命のまま常用する、クラウドCLIがログイン済みの状態でエージェントにシェルを渡す、という形は被害半径を広げる。OSキーチェーン、短命トークン、スコープ限定、プロジェクト別env、公開前のsecret scanningを組み合わせたい。

5つ目は、ツール呼び出しログと停止手順。MCPサーバーやエージェントが何を読んだか、どのコマンドを実行したか、どこへ通信したかを最低限追える状態にしておく。違和感があったときに、MCP設定を外す、該当npmパッケージを削除する、トークンを失効する、GitHub/npm/クラウド側の監査ログを見る、という順番をあらかじめ決めておく。

個人向けの読みどころ

個人の環境に引き寄せるなら、OpenClawやCodexの強さは「ファイル、Discord、Obsidian、GitHub Pages、cron、ブラウザ、ローカルコマンドをまたげる」ことにある。一方で、攻撃面も同じ場所に生まれる。

現実的な棚卸しは、次の粒度でよい。

  • MCP/ツール連携台帳: サーバー名、用途、起動コマンド、インストール元、更新方法、読めるディレクトリ、使う資格情報
  • npm/Node台帳: グローバルnpm、各プロジェクトのlockfile、preinstall/postinstallを持つ依存、最近追加したCLI
  • 資格情報台帳: GitHub、npm、OpenAI、Anthropic、Discord、クラウド、Obsidian関連で、どこに保存されているか
  • 公開系チェック: GitHub Pagesへ出るMarkdownに個人情報、内部パス、秘密情報が混ざらないか
  • 失効手順: 疑わしいときにまず切るトークン、見るログ、消す設定ファイル

特にこの興味レポート自動化は、Discordポールを読み、Markdownを作り、サイトをビルドし、git pushし、公開URLを確認する。自動化としてはかなり強いので、成功ログだけでなく「どの入力を信頼したか」「どの外部情報を命令として扱わなかったか」「どのファイルを公開したか」を残す価値がある。

当面の実務メモとしては、MCPサーバーを増やす前に1枚のObsidian台帳を作り、追加時に必ず「何を読めるか」「何を書けるか」「ネットワークへ出るか」「秘密情報を持つか」を書くのがよい。面倒でも、あとから思い出すより安い。

注意点

この記事は公開情報にもとづくセキュリティ運用メモであり、特定環境の侵害有無を断定するものではない。実際に不審な通信、見覚えのないMCP設定、予期しないnpmパッケージ、資格情報流出の疑いがある場合は、該当トークンの失効、ログ確認、端末隔離、専門家確認を優先する。

MCP関連の脆弱性情報は更新が速い。ベンダーブログやセキュリティ企業の記事には未検証・誇張気味の表現が混ざることもあるため、実装判断では公式MCP仕様、プロジェクトのリリースノート、GitHub Advisory、CVE/NVD、ベンダー公式情報を合わせて確認する。

また、MCPやAIエージェントを全面停止すれば安全になるわけではない。重要なのは、用途ごとに権限を絞り、信頼境界を分け、設定と依存を見える化すること。便利さを捨てるより、エージェントを「管理対象の自動化基盤」として扱うほうが続けやすい。
