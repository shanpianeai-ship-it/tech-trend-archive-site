2026-04-28 OpenClaw・Obsidian運用

Qwen ローカルと GPT-5.5 クラウド併用 OpenClaw 運用設計調査

サマリー

OpenClaw は「状態管理・短い確認・定型タスク」をローカル Qwen に寄せ、「複数ソース調査・重要判断・長文レポート・失敗コストが高い外部送信前レビュー」を GPT-5.5 に寄せる二層運用が適している。

推奨構成は以下。

  • Qwen ローカル: heartbeat の軽い巡回、キュー状態確認、Markdown/ログ整理、既存メモリからの候補抽出、下書き・分類・TODO 化、日次小タスク。
  • GPT-5.5 クラウド: 新規スキル設計のレビュー、メモリ昇格判断、複数 Web ソース調査、リスク判断、対外文面の最終化、長文レポート。
  • OpenClaw ハーネス: AGENTS.md/HEARTBEAT.md/MODEL_POLICY.md/タスクキュー/スキルを薄いルーターとして使い、モデル分担は「タスク種別・リスク・外部送信有無・必要な根拠数」で決める。

費用面では、Qwen はローカル実行のため API の per-token 課金はないが、マシン購入費・電気代・実行速度・メンテナンスがコストになる。GPT-5.5 は OpenAI 公式価格ページ上、短文コンテキストで入力 $5.00 / 1M tokens、cached input $0.50 / 1M tokens、出力 $30.00 / 1M tokens、長文コンテキストで入力 $10.00 / 1M tokens、出力 $45.00 / 1M tokens とされている。ただし価格・モデル名・利用条件は変更されやすく、運用開始時に公式ページで再確認が必要。

調査条件

  • 調査日: 2026-04-28 JST
  • 対象: OpenClaw を、ローカル Qwen とクラウド GPT-5.5 の併用で運用する設計
  • 想定モデル:
  • ローカル: ollama/qwen3.5:9b 相当、または同等の Qwen ローカルモデル
  • クラウド: openai-codex/gpt-5.5 / GPT-5.5 系
  • 制約:
  • 本タスクでは MEMORY.md と memory/YYYY-MM-DD.md には書き込まない。
  • Web ソースは公開ドキュメント中心。OpenClaw の実装・モデル価格・Qwen モデル仕様は更新される可能性がある。

2. スキル作成の分担例

OpenClaw のスキルは AgentSkills 互換の SKILL.md を持つフォルダで、workspace skills が最も高い優先度を持つ。したがって、ローカル Qwen には「既存作業から手順を抽出して skills/<name>/SKILL.md の草案を作る」役を任せやすい。

推奨フロー:

  1. Qwen: 作業ログ・手順を読み、スキル化候補を抽出。
  2. Qwen: name、description、手順、禁止事項、検証コマンドを含む草案を作成。
  3. GPT-5.5: 以下をレビュー。
  • 説明文が過剰に広くなく、必要時だけ呼ばれるか。
  • 外部 API 書き込み、削除、権限昇格、秘密情報の扱いが安全か。
  • 既存スキルと重複していないか。
  1. Qwen: レビュー結果を反映し、形式・リンク切れ・相対パスをチェック。

事務作業の例:

  • 「請求書 PDF を受け取ったら、ファイル名を YYYY-MM_取引先_金額.pdf に直す」スキルは Qwen が草案化。
  • 「会計システムにログインして提出する」ような外部送信・金銭処理を含むスキルは GPT-5.5 が安全レビューし、最終実行は人間承認にする。

3. メモリ管理の分担例

OpenClaw のメモリは plain Markdown で、MEMORY.md が長期記憶、memory/YYYY-MM-DD.md が日次メモとして扱われる。重要なのは「ローカルモデルに全部保存させる」のではなく、Qwen は候補抽出まで、GPT-5.5 または人間が昇格判断をすること。

推奨フロー:

  1. Qwen: 今日・昨日の日次メモから候補を抽出。
  • 好み、恒久的なルール、プロジェクト方針、反復する失敗を候補化。
  • 一時的な予定、古い作業ログ、秘密情報は除外候補にする。
  1. GPT-5.5: 長期記憶に値するか評価。
  • 将来の行動が変わるか。
  • ユーザーのプライバシーを不要に広げないか。
  • 矛盾・期限切れがないか。
  1. 人間承認後: MEMORY.md に短く保存。

事務作業の例:

  • Qwen: 「毎月25日に経費精算がある」「領収書はGoogle Driveの特定フォルダ」などを候補抽出。
  • GPT-5.5: 「長期保存するなら、具体的な個人情報や認証情報を含めず、運用ルールだけ残す」と整える。

4. ハートビートの分担例

OpenClaw の heartbeat は定期的な main-session turn で、デフォルトでは 30 分程度の間隔、何もなければ HEARTBEAT_OK を返す契約になっている。cron と違い、タスクレコードを作らず、柔軟な巡回・文脈依存の気づきに向いている。

推奨:

  • 通常 heartbeat は Qwen
  • キュー確認、メール/カレンダーの軽い分類、天気、未完了タスクの棚卸し。
  • HEARTBEAT.md は短くし、Qwen が迷わないチェックリストにする。
  • GPT-5.5 にエスカレーションする条件
  • 重要メールへの返信案が必要。
  • 契約、金銭、個人情報、外部送信が絡む。
  • 複数ソースの確認が必要。
  • 「今ユーザーに割り込むべきか」の判断が難しい。

事務作業の例:

  • Qwen heartbeat: 「本日14:00に会議。30分前になったら通知」「未読メールに請求書らしき件名があるか確認」。
  • GPT-5.5: 「取引先からの督促メールに対する返信文を、過去経緯と添付ファイルを踏まえて作る」。

5. コンテキスト設計

OpenClaw のセッションは DM、グループ、cron、webhook 等でルーティングされ、cron は fresh session、heartbeat は main session の文脈を使う。したがって、コンテキストは「常時必要」「heartbeat だけ必要」「重調査だけ必要」に分ける。

推奨ファイル分離:

  • AGENTS.md: 全体方針、赤線、メモリ方針、外部送信ルール。
  • SOUL.md: 口調・振る舞い。頻繁に変えない。
  • USER.md: ユーザーに関する安定情報。必要最小限。
  • HEARTBEAT.md: 30分〜数時間ごとの巡回リスト。短く保つ。
  • MODEL_POLICY.md: Qwen/GPT-5.5 の分担ルール。
  • task-queue/PROCESSING.md: queue 処理の手順。
  • skills/*/SKILL.md: 特定作業の手順。必要時だけ読む。

モデル別のコンテキスト方針:

  • Qwen: 小さいコンテキスト、明確な手順、チェックリスト、JSON/Markdown の状態ファイル中心。
  • GPT-5.5: 調査条件、複数ソース、判断基準、過去経緯を含めてもよい。ただし秘密情報・全メモリ丸投げは避ける。

6. ハーネス作成・タスクキュー運用

ハーネスは「モデルを賢くする」よりも「失敗しにくくする」ために作る。Qwen は deterministic なスクリプトと相性がよく、GPT-5.5 は調査・判断・文章化に強い。

推奨ハーネス:

  • queue_task.py のような状態管理スクリプト:
  • next / start-next / note / done / block を明確化。
  • Qwen が実行しても事故りにくい。
  • MODEL_POLICY.md:
  • research / report は GPT-5.5。
  • organize / summary / other は Qwen。
  • レポートテンプレート:
  • サマリー、調査条件、結果、根拠・参照URL、不確実性・注意点、次アクション候補、メモリ保存候補 を固定。
  • エスカレーション条件:
  • Web ソース 3件以上。
  • 金銭・契約・外部送信。
  • MEMORY.md 書き込み。
  • 新規スキルで外部 API 書き込みを伴う。

事務作業の例:

  • Qwen: 毎朝「未処理領収書一覧」「今日の会議」「期限切れ TODO」を1つの Markdown にまとめる。
  • GPT-5.5: 月末に「今月の経費・請求・未返信重要メール」を横断して、抜け漏れリスクを評価する。

7. 実際の調査タスクの分担

今回のような調査では以下がよい。

  1. Qwen: キューからタスクを開始し、調査テーマ・出力パス・必須セクションを確認。
  2. GPT-5.5: 複数 Web ソースを取得し、根拠付きで統合。
  3. GPT-5.5: 価格根拠・不確実性を明示し、レポート本文を書く。
  4. Qwen: 保存後のキュー done 処理、一覧更新、短い完了サマリー。

実調査を Qwen だけにしない理由:

  • 複数ソースの整合性確認が必要。
  • 価格・モデル名・仕様は変わりやすく、不確実性の扱いが重要。
  • 日本語での運用設計・事例化は長文統合能力が効く。

8. 日々の小さな実行タスク例

Qwen 向き:

  • メール件名の分類: 「要返信」「請求書」「ニュースレター」「スパム候補」。
  • カレンダーから今日の予定を抽出し、移動が必要なものだけリスト化。
  • Downloads や作業フォルダのファイル名候補を作る。
  • 経費精算用に領収書ファイルを月別に整理する案を出す。
  • 日次メモから TODO を抽出。
  • タスクキューの queued/running/blocked/done 一覧化。

GPT-5.5 向き:

  • 重要メールの返信文作成。
  • 契約書・見積書・請求書の内容確認とリスク指摘。
  • 長い会議メモから意思決定と未決事項を整理。
  • 複数候補サービスの比較表作成。
  • 失敗時の影響が大きい自動化スキルの設計レビュー。

人間承認を必須にすべきもの:

  • メール送信、SNS投稿、外部フォーム送信。
  • 支払い、契約、削除、権限変更。
  • MEMORY.md への長期保存。
  • 個人情報・秘密情報のクラウド送信。

不確実性・注意点

  • GPT-5.5 価格は変動する: 本レポートでは OpenAI 公式価格ページ取得時点の表示を根拠にした。運用開始時・月次レビュー時に再確認する。
  • Qwen の「無料」は限界費用の話: per-token API 課金はないが、電気代、ハードウェア、メモリ使用、速度低下、Ollama/モデル更新の運用コストはある。
  • ローカル Qwen は秘密情報に強いが、万能ではない: クラウド送信を避けたい下処理には向くが、重要判断や複数ソース統合では GPT-5.5 に劣る可能性がある。
  • OpenClaw の設定キー・CLI は更新される: 実設定変更前には openclaw config schema や公式 docs を確認する。
  • 自動化の権限設計が重要: Qwen に外部送信・削除・支払い権限を直接与えると、低コスト化より事故リスクが大きくなる。
  • メモリはプライバシー面の負債にもなる: 候補抽出と保存を分離し、長期保存は人間承認または GPT-5.5 レビューを挟む。
  • Web ソースには検索結果由来の低信頼ページが混じる: 重要根拠は公式 docs、公式 pricing、公式 model library を優先した。
