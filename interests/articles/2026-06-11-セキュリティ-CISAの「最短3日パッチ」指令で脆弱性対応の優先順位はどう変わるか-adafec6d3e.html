Summary

2026年6月10日、CISAは Binding Operational Directive 26-04「Prioritizing Security Updates Based on Risk」を公開した。

CISAの「最短3日パッチ」指令で脆弱性対応の優先順位はどう変わるか

要約

2026年6月10日、CISAは Binding Operational Directive 26-04「Prioritizing Security Updates Based on Risk」を公開した。対象は米国のFederal Civilian Executive Branch機関だが、内容は一般企業の脆弱性管理にもかなり参考になる。

ポイントは、すべての脆弱性をCVSSの高低だけで並べるのではなく、公開露出、KEV登録、攻撃自動化のしやすさ、攻撃成功時の技術的影響で期限を変えること。最も危険な組み合わせでは、3日以内の修正または緩和に加えて、侵害有無を確認するフォレンジック・トリアージも求められる。

これは「AIで攻撃が速くなるから全部を急げ」という話ではない。むしろ、限られた運用リソースを本当に危ない資産へ寄せるための優先順位表である。SAP、Windows、VPN、クラウド、公開Web、管理コンソールを持つ現場なら、「今月中に全部パッチ」よりも、「インターネット公開かつ悪用済みかつ自動化可能なものを先に潰す」という運用に寄せるべきだ。

なぜ今見る価値があるか

CISAは今回の指令で、AIが脆弱性発見と攻撃自動化を速める可能性を明示している。従来は「月次パッチ」「重大度Critical/High」「KEVに入ったら急ぐ」という運用でも、ある程度は説明しやすかった。しかし、公開資産に対する自動化攻撃が速くなると、月次サイクルでは間に合わない領域が増える。

WIREDやCybersecurity Diveの報道でも、CISA側は「攻撃者が自動化で大規模に突けるシステムを数週間放置できない」という趣旨を説明している。Nextgov/FCWは、CISAが大規模な民間機関で分析したところ、3日カテゴリに入る脆弱性インスタンスは約1%にとどまり、60%以上は次回の大きなシステム更新まで延期可能だったと報じている。

ここが重要で、3日パッチ指令は「全部を3日で直せ」ではない。公開されていて、実際に悪用されていて、自動化されやすく、攻撃成功時にシステム制御まで持っていかれるものを、他より先に扱うためのルールである。

調査メモ

CISA BOD 26-04の判断軸は4つある。

1つ目はAsset Exposure。脆弱な資産がインターネットなどの公衆ネットワークから、未認証または信頼できない主体に到達可能かを見る。VPN装置、境界FW、公開Web、公開API、リモート管理画面、クラウド上の公開サービスはここに入りやすい。

2つ目はKEV Status。CVEがCISAのKnown Exploited Vulnerabilities Catalogに入っているかを見る。KEV入りは「実際に悪用が確認されている」ことを示すため、単なる理論上の脆弱性より優先度が高い。

3つ目はExploit Automation。攻撃者が exploit の手順を自動化できるかを見る。認証不要、スキャンしやすい、攻撃コードが単純、インターネット全体へ横展開しやすいものは、AIや自動化ツールの恩恵を受けやすい。

4つ目はTechnical Impact。攻撃成功時に部分的な制御で済むのか、システムの完全制御や認証情報奪取まで行くのかを見る。CISAの定義では、ログイン認証情報を安定して露出させる場合も total control に含まれる。

運用上の読み替えはこうなる。

条件現場での扱い
公開資産 + KEV + 自動化可能 + total control休日・夜間でも例外対応候補。パッチ、遮断、緩和、侵害確認を同時に走らせる
公開資産 + KEV + partial control通常の月次を待たず、短期SLAで処理する
公開資産だがKEVなしCVSSだけでなく、PoC公開、自動化可能性、製品の露出度で繰り上げ判断する
非公開資産 + KEV内部到達経路、認証情報流出、横展開リスクを見て期限を決める
非公開資産 + KEVなし + 自動化困難計画停止や次回メンテで処理してよい候補

フォレンジック・トリアージの実装ガイダンスも実務的である。CISAは、スコープ特定、証拠保全、重要パッチと安定化、封じ込め、分析、エスカレーション判断という流れを示している。これは「パッチを当てたら終わり」ではなく、「すでに入られていないか」を見る工程を最初から組み込むということだ。

個人向けの読みどころ

SAP Basisや業務システム運用に引き寄せるなら、この指令の価値は「パッチ適用順の説明責任」を作れる点にある。

たとえば、同じCriticalでも、インターネット公開のVPN装置、SAP Web Dispatcher、公開Fiori、境界WAF、Windowsの公開RDP、クラウド管理APIと、社内限定の検証サーバーでは扱いを変えるべきである。CISA式に並べると、次のような判断表が作れる。

  • 公開露出: 外部から直接到達できるか
  • 悪用実績: KEV、ベンダー警告、攻撃観測があるか
  • 自動化: スキャンから侵入まで機械的に回せるか
  • 影響: 権限昇格、認証情報奪取、任意コード実行、横展開につながるか
  • 業務影響: 止められるか、緩和できるか、代替経路があるか
  • 侵害確認: ログ、EDR、WAF、認証履歴、設定変更履歴を見られるか

この表を使うと、「なぜこのSAP関連パッチを先にやるのか」「なぜこの検証機は次回メンテでよいのか」を説明しやすい。特にBasis向けコンテンツにするなら、月次パッチ運用を否定するのではなく、月次パッチの前に差し込む緊急レーンをどう作るかが題材になる。

個人運用でも同じで、OpenClawやGitHub Pages、Discord連携、ローカルCLI、公開サイトを持つなら、まず見るべきは公開面と認証情報に近いところである。公開サイトそのものより、git push権限、GitHub token、npm token、クラウド認証、公開されるMarkdownの情報漏えいのほうが被害半径は大きい。

注意点

この記事は公開情報にもとづくセキュリティ運用メモであり、法令・監査・インシデント対応の専門助言ではない。実際の組織運用では、契約、監査要件、業務停止リスク、変更管理、ベンダーサポート条件を合わせて判断する必要がある。

CISA BOD 26-04は米国FCEB機関向けの拘束力ある指令であり、日本企業や個人環境にそのまま義務として適用されるものではない。ただし、KEV、公開露出、自動化可能性、技術影響を使った優先順位付けは、SAP/Windows/クラウド/境界機器を抱える現場でも再利用しやすい。

また、3日以内にベンダーパッチが存在しない場合もある。その場合は、パッチだけに固執せず、公開停止、アクセス制限、WAF/IPSルール、該当機能の無効化、ネットワーク分離、認証強化、監視強化、代替システム切替を含めて「リスクを下げた」と説明できる状態にするのが現実的である。
