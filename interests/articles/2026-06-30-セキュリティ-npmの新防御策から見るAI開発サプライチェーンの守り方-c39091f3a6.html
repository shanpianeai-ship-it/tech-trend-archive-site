Summary

npmのstaged publishing、install時の明示許可、重要アカウント保護を整理する。AI開発で依存関係が増えるほど、個人秘書エージェント環境の防御策として効く。

npmの新防御策から見るAI開発サプライチェーンの守り方

要約

2026年5月から6月にかけて、GitHub/npmはnpmのサプライチェーン防御を大きく強めている。5月22日にはstaged publishingが一般提供となり、CI/CDが作ったパッケージをそのまま公開せず、メンテナの2FA承認を挟んでからregistryへ出す運用が使えるようになった。同時に、Git、remote URL、file、directoryなどregistry外の依存取得元を明示的に制御する--allow-*系の設定も広がっている。

6月9日にはnpm v12の破壊的変更予定として、依存パッケージのpreinstall、install、postinstallをデフォルトで実行しない方針が示された。6月25日には、広く使われるパッケージを管理する高影響アカウントについて、メール変更や2FAリカバリコード利用後に72時間のread-only保護を入れる施策も追加された。

今回のDiscordポールは有効票がなかったため、候補一覧から重要度、鮮度、個人適合度が高いこのテーマを採用した。OpenClaw、Codex、MCP、GitHub Pages、Discord連携のようにNode製ツールや外部パッケージを使う個人環境では、npmの新デフォルトを「企業向けの大きな話」ではなく、日常のAI開発端末を守る具体策として読める。

なぜ今見る価値があるか

AIエージェント開発は、依存関係を増やしやすい。MCPサーバー、ブラウザ自動化、Discord連携、Markdown変換、画像処理、CLI補助、GitHub Pagesビルドなど、便利な部品を足すたびにnpmパッケージ、GitHub URL、remote tarball、postinstallスクリプトが入り込む余地ができる。

ここで危ないのは、悪性コードがアプリ本体に入ることだけではない。npm installは開発端末やCIの権限で動くため、環境変数、.npmrc、GitHubトークン、npmトークン、SSH鍵、作業フォルダ、Obsidian vault、Desktop配下のファイルに近づける。AI秘書環境では、その端末がさらに外部送信、git push、Discord投稿、Web調査、ファイル整理まで担当するため、依存関係の汚染がそのまま自動化基盤全体の汚染になりうる。

GitHub/npmの新施策は、この攻撃面を3方向から狭めている。公開時にはstaged publishingで人間承認を挟む。取得時にはGitやremote URLなど非registry依存を明示許可に寄せる。実行時にはinstall scriptをデフォルト停止へ寄せる。さらに、高影響アカウントの乗っ取り直後に悪性版を出される時間帯を、72時間のread-only状態で止めようとしている。

調査メモ

GitHubの2026年5月22日のChangelogでは、staged publishingが一般提供になったと説明されている。通常のnpm publishはパッケージ版をすぐ利用可能にするが、staged publishingではprebuilt tarballをstage queueへ置き、メンテナが明示的に承認してから公開する。CI/CDやOIDCを使うtrusted publishingでも、人間の2FA承認を最後に挟める点が重要である。

同じ発表では、npm CLI 11.15.0以降で--allow-file、--allow-remote、--allow-directoryが追加された。既存の--allow-gitと合わせ、local tarball、remote URL、local directory、Git依存のようなregistry外取得元を制御できる。2026年時点では一部のデフォルトはまだ緩いが、.npmrcやpackage.jsonで先に厳しくできる。

6月9日のnpm v12予告では、依存パッケージのinstall script実行が明示許可制へ寄る。npm v12では、依存のpreinstall、install、postinstallが、プロジェクトで許可されない限り実行されない予定である。native addonの暗黙のnode-gyp rebuildも対象に含まれる。npm 11.16.0以降では警告として事前確認でき、npm approve-scripts --allow-scripts-pendingで保留中のスクリプトを見て、信頼するものだけをallowlist化できる。

6月25日の高影響アカウント保護は、アカウント乗っ取り後の典型的な流れを止める施策として読める。高影響アカウントがメールアドレスを変える、または2FAリカバリコードを使うと、72時間read-onlyになり、以前のメールアドレスへ通知される。この間、パッケージのinstallやdownloadは続くが、publish、token管理、package visibility変更、organization/team membership変更などregistryやセキュリティに影響する操作は止まる。

Cloud Security Allianceの2026年6月11日のwhitepaperは、npmがAI/ML基盤や開発ツールの配布層にもなっていることを強調している。CSAは、TeamPCP、Miasma、TanStack侵害、Red Hat Cloud Servicesスコープの侵害などを背景に、install script、Git/remote依存、token窃取、CI/CD認証情報、AI/ML toolingを横断したリスクとして整理している。細部はベンダー評価や公開情報に依存するため個別事案の断定は避けるべきだが、npmをAI開発サプライチェーンの基盤として扱う視点は有用である。

防御策を作業フローに落とすと、次のようになる。

場面これまでの危険新しい読み方
パッケージ公開CIが奪われると即座に悪性版公開staged publishingで人間の2FA承認を挟む
依存取得GitHub URLやremote tarballが自然に混ざる--allow-gitや--allow-remoteを明示許可に寄せる
install時実行postinstallが端末権限で即実行npm v12前にapprove-scriptsで棚卸しする
メンテナ乗っ取りメール変更後すぐtoken発行とpublish高影響アカウントは72時間read-onlyで止める
AI開発端末依存追加が秘密情報と外部送信権限へ近い依存検証環境と普段の作業環境を分ける

個人向けの読みどころ

個人の環境では、興味レポートCronが候補Markdown、Discordポール、Web記事を読み、Markdown保存、node scripts/build.mjs、git push、Discord報告まで行う。これは便利だが、入力、ビルド、公開、外部送信が同じ流れにある。npmのサプライチェーン防御は、この流れのうち「ビルドやツール追加で外部コードを入れる瞬間」を厳しく見る材料になる。

まず、既存のPagesビルドのように自分で管理している固定スクリプトは比較的扱いやすい。一方で、新しいMCPサーバー、CLI、ブラウザ自動化ツール、Markdownプラグイン、画像処理パッケージを追加する時は、npm install自体を外部コード実行の入口として扱うべきだ。

実用ルールはこのくらいがよい。

  1. 新しいnpm系ツールは、普段のホームディレクトリやObsidian vaultに近い場所でいきなり試さない。
  2. lockfileがあるプロジェクトではnpm installよりnpm ciを優先する。
  3. GitHub URL直指定、remote tarball、local file/directory依存は、通常のregistry依存より一段危険として扱う。
  4. npm 11.16.0以降を使える環境では、v12移行前にinstall scriptの警告とapprove-scripts結果を確認する。
  5. .npmrc、.env、GitHubトークン、Discordトークン、OpenAI系APIキーを、検証用プロジェクトやコンテナへ無条件に渡さない。
  6. 自動化Cronで外部パッケージを更新した直後は、生成物だけでなくgit diff、公開対象JSON、Discord報告文も確認する。

OpenClaw運用に引き寄せると、権限の境界は「AIが何を読めるか」だけでなく、「依存追加時に何が実行されるか」にも置くべきだ。候補一覧やWeb記事のプロンプトインジェクションを警戒するのと同じくらい、パッケージのinstall script、Git依存、remote URL依存、npmアカウント乗っ取りも現実的な入口になる。

注意点

npm v12の予定は強い改善だが、万能ではない。明示許可したスクリプトは実行されるし、Git依存やremote URL依存も許可すれば使える。攻撃者はinstall時ではなくimport時に動くコード、正規メンテナのアカウント侵害、CI/CDのsecret、レジストリ外配布、開発者をだますREADMEやissueコメントなど、別の経路へ移る可能性がある。

また、staged publishingや高影響アカウント保護は、主にパッケージを公開する側の防御である。利用者側は、公開されたパッケージを無条件に信じない、lockfileを固定する、スクリプト実行を棚卸しする、検証環境を分ける、秘密情報を渡さない、という地味な運用が必要になる。

この記事は公開情報をもとにした防御側の調査メモであり、悪性パッケージの再現や攻撃手順は扱わない。実際に不審なnpmパッケージを入れた疑いがある場合は、lockfile、install時刻、npm cache、temp配下、外向き通信、GitHub/npm/APIキーの利用履歴を確認し、必要なら認証情報をローテーションする。
