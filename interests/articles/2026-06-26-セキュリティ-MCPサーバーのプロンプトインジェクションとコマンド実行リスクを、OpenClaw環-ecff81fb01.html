MCPサーバーのプロンプトインジェクションとコマンド実行リスクを、OpenClaw環境でどう棚卸しするか

要約

MCPは「LLMに道具を渡す標準」なので便利だが、リスクは通常のWebアプリよりも少し嫌な形で出る。攻撃者が直接コマンドを打たなくても、GitHub Issue、git log、ツール説明文、OAuth URL、ローカルMCPサーバー設定などを経由して、エージェントが自分で危険なツール呼び出しへ進む可能性がある。

OpenClaw環境で見るべきポイントは、MCPそのものを怖がることではなく、次の3つを分けて棚卸しすること。

  • 外部テキスト: Discord、GitHub、Web、Obsidian内の未検証メモなど、プロンプト注入が混ざり得る入力。
  • 実行権限: ローカルファイル、シェル、Git、ブラウザ、Discord送信、Pages公開など、実害につながるツール。
  • 境界設定: どのツールを自動実行してよいか、どこで確認を挟むか、どの資格情報をどの範囲に閉じるか。

なぜ今見る価値があるか

MCPの攻撃面は、2025年以降の実証やadvisoryでかなり具体化している。GitHub MCPを使った間接プロンプトインジェクションでは、公開リポジトリのIssueに置かれた指示が、私有リポジトリ情報の流出につながる流れが示された。別のGit系MCPサーバーでは、child_process.exec に未検証入力を渡す実装により、コマンドインジェクションとRCEがGitHub Advisoryで公開されている。

OpenClawは、ローカルファイル、Obsidian、Discord、GitHub Pages、cronをつなぐため、MCPリスクの実験場としても実運用環境としても攻撃面が広い。特に「外部から入ったテキストを読んだ直後に、ローカル操作や公開送信をする」自動化は、便利さと危険さが同じ場所にある。

調査メモ

MCP公式のSecurity Best Practicesは、MCP固有の注意点として confused deputy、token passthrough、SSRF、session hijacking、local MCP server compromise、OAuth URL validation、stdio transport in proxy scenarios、scope minimization を挙げている。個人運用では全部を企業レベルで実装するより、まず「ローカルMCPサーバーはユーザー権限で動く」「OAuthやURLを雑に開かない」「MCPサーバー追加時に実行コマンド全文を見る」という基本を守るのが効く。

GitHub Advisory GHSA-3q26-f695-pp76 / CVE-2025-53107 は、@cyanheads/git-mcp-server の <= 2.1.4 が影響を受け、2.1.5 で修正済みとされている。原因は、MCPツールがGit操作用のシェルコマンドを文字列結合し、未検証入力を child_process.exec に渡していたこと。advisoryは、execFile のように引数を配列で渡すAPIを使う回避策を示している。

Invariant LabsのGitHub MCP実証は、ツール自体が悪意あるものでなくても危険が起きる点が重要。公開Issueに置かれた悪意ある指示をエージェントが読み、信頼済みのGitHubツールを連鎖的に使って、私有リポジトリ情報を公開PRへ流すという構図だった。これは「ツールが公式なら安全」ではなく、「外部コンテンツを読んだあとのツール連鎖が安全か」を見る必要があるという話。

同じくInvariant LabsのTool Poisoning Attackは、MCPツール説明文にユーザーには見えにくい悪意ある指示を埋め込む攻撃を示している。ユーザー画面では足し算ツールに見えても、モデルには「設定ファイルやSSH鍵を読め」といった隠れ指示が見える可能性がある。ツール説明文そのものを信頼境界の内側に置いてはいけない。

2026年のMCP脅威分析論文でも、ツールメタデータに混ざる悪意ある指示、つまりtool poisoningが、クライアント側で特に影響の大きい脆弱性として整理されている。対策としては、静的なメタデータ検査、モデルの判断経路の追跡、異常行動検出、ユーザーに見える透明性の向上が提案されている。

個人向けの読みどころ

OpenClaw運用に引き寄せると、棚卸しは次の表で十分に始められる。

領域見るもの最初の対策
入力Discord、GitHub Issue、Webページ、Obsidian未整理メモ外部入力を読んだ直後の送信・削除・公開・シェル実行を高リスク扱いにする
実行exec、Git操作、ファイル移動、Discord送信、Pages push自動実行できるコマンド範囲を限定し、危険操作は確認またはログ必須にする
MCPサーバーインストール元、起動コマンド、環境変数、アクセスできるディレクトリ使っていないサーバーを無効化し、起動コマンド全文と権限を記録する
認証情報GitHub token、Discord token、ローカル設定ファイルスコープを狭くし、公開リポジトリと私有データを同じ資格情報で扱わない
cron無人で動く記事化、build、commit/push、通知「読み取りだけ成功」を成功扱いにせず、失敗時は公開送信前に止める

特にこの興味レポート自動化は、Discord投票、候補Markdown、Web調査、Markdown生成、GitHub Pages反映、Discord報告が1本につながっている。実運用としては便利だが、外部テキストから公開成果物までの距離が短い。候補一覧やポール結果は信頼済み入力に見えるが、元の情報源やDiscord内容に注入文が混ざる可能性は残る。

現実的な運用ルールは、次の5つ。

  1. MCPサーバー一覧を作り、用途、起動コマンド、権限、資格情報、最終利用日を記録する。
  2. 新しいMCPサーバーやスキルを入れる時は、公式・信頼できる配布元、依存、起動コマンドを確認する。
  3. 外部テキストを読んだ直後の git push、Discord送信、ファイル削除、シェル実行は高リスク操作としてログに残す。
  4. GitHubやDiscordのトークンは、必要最小限のスコープに分ける。公開リポジトリと私有情報を広いトークンでまたがせない。
  5. 自動化Cronは、途中失敗を成功扱いにしない。今回のように「投票読み取りだけで完了しない」という条件は、セキュリティ面でも正しい。

注意点

この記事はセキュリティ棚卸しのための調査メモであり、特定環境の完全な監査結果ではない。実際のOpenClaw設定、インストール済みMCPサーバー、トークン権限、cron権限は別途ローカルで確認する必要がある。

また、MCPのリスクは「MCPだから危険」というより、「LLMが外部入力を解釈し、権限ある道具を選んで実行する」ことから生じる。対策も、モデルの賢さに期待するより、権限分離、スコープ最小化、ログ、確認ポイント、サンドボックス化に寄せるのが堅い。
