Summary

Responses APIで外部コネクタを運用するなら、モデルごとに許可範囲を分離し、実行権限・ログ責任・例外時の停止基準を明示するのが安全側の設計。

Responses APIでコネクタ境界を分ける

要約

Responses APIを用いた自動化では、モデルに対して「実行可能なコネクタ」と「実行範囲」を明確に分ける設計が崩れやすい。今回は、Codex運用を前提に、 「どのコネクタをどのタイミングで呼ぶか」「その呼び出しログをどこまで残すか」「失敗時にどこで止めるか」を3階層で固定する。

1. コネクタ境界の分割: ロール別とモデル別

単一のエージェントにすべてのコネクタを持たせると、以下が起きやすい。

  • 予期せぬコマンド実行が入る
  • 失敗時の影響範囲が読みづらい
  • 監査時に「誰が何を実行したか」が追いづらい

実運用では、少なくとも以下に分割すると扱いやすい。

  1. readonly 系: 取得・参照のみ（公開情報収集、検索、読み取り）
  2. write 系: ファイル更新・文書生成（対象フォルダ限定）
  3. external 系: 外部実行・投稿・通知（Discord/GitHub/外部API操作）

候補テーマの文脈では、第一段では readonly のみで検討し、external を後段に昇格する方式が安全。

2. tool 設定の設計ルール

OpenAIの公式ドキュメントで示される Responses API / tools 構成は、実際には「1回の応答で何を実行し、何を許可しないか」を宣言するのが本体。

実務で効く原則は次の3点。

  • ツール一覧は allowlist 的に最小集合だけ持つ
  • tool_choice 相当の呼び出し制御で「自動実行」/「確認付き実行」を切り替える
  • 実行結果は原則はstructuredで受け取り、失敗時は safe-fail（中断・再試行・上位へ昇格）

Codex向けCronでは、ここを厳密化すると事故率が下がる。

3. ログと監査の粒度

境界設計は権限制御だけでなく、監査可視化で成立する。最低限必要なのは以下。

  • 候補ファイル読み取り時刻、poll message id
  • 選定ID（投票ID or fallback ID）
  • 実行したコマンド名（read/build/git）
  • 変更ファイルパス（candidate frontmatter / 記事パス）

今回はこの原則に従い、候補一覧frontmatterへ selected_* を追記し、同一日1本記事化を担保する。

4. Codex運用への落とし込み

固定化すると運用が安定するポイント。

  • poll の結果が空でも、候補の優先度ルールを先に持つ
  • publish 対象は明示した1ファイルだけに絞る
  • build は失敗時に結果チャンネルで即報告し、再実行条件を明確化する

この観点で、候補選定と記事生成を分離し、1日1本に限定する現運用は妥当。

調査メモ（最小）

  • OpenAI公式DocsのResponses API/Tools系ガイドでは、実行可能ツール設計と出力制御の意図が中心。
  • OpenAI Help（Agents/Tools関連）では、権限境界を小さな単位で分解する運用が再現性を上げる考え方が一貫している。
  • MCP/コネクタ運用に関する一般的な安全原則（最小権限・明示的な許可・監査ログ）は、今回のCron設計に直接適用できる。
