RISE with SAP Private Cloud時代に残る顧客側Basis業務と高付加価値領域

Summary

RISE with SAP / SAP S/4HANA Cloud Private Editionでは、インフラ運用・基盤監視・標準パッチ適用などはSAP側へ大きく移る。一方で、顧客側Basisの価値は消えず、むしろ「責任分界を読める」「業務影響を技術証拠に落とせる」「SAP/BTP/ネットワーク/証明書/性能/運用設計/サポートを横断できる」人材に集中する。個人さんの場合、HANA性能分析、STRUST/PSE、Cloud ALM、BTP連携、RISE責任分界の既存関心と相性が非常に良い。

結論

  • 低付加価値のBasis作業は減るが、顧客側Basisの高付加価値化は進む。 OS/DB/インフラの日常運用そのものより、業務SLA、監視設計、問題切り分け、SAPへのエスカレーション、変更・リリース調整、セキュリティ/証明書/接続設計が重要になる。
  • RISE時代の顧客側の主戦場は「共同管理モデルの司令塔」。 SAP公式はPrivate Cloud ERPをshared management modelとして説明し、SAP管理・顧客管理・共同管理の責任を分けている。顧客はビジネスプロセス、権限、カスタマイズ、業務要件、変更タイミング、影響判断を握り続ける。
  • Cloud ALMを中心に、業務×技術の監視設計をできる人材が強い。 SAP Cloud ALMはCloud subscription等に含まれ、実装・運用の中心入口として、Business Process Monitoring、Integration & Exception Monitoring、Real User Monitoring、Health Monitoringを提供する。
  • 個人さんが伸ばすべき最短ルートは、HANA性能分析の深さを維持しつつ、Cloud ALM/RISE責任分界/BTP connectivity/証明書/経営層説明へ広げること。 「手を動かすBasis」から「証拠でSAP・顧客・経営を動かすBasisアーキテクト」へ寄せるのがよい。

調査条件

  • 対象: RISE with SAP / SAP S/4HANA Cloud Private Edition時代の顧客側Basis業務、高付加価値コンサル領域、責任分界、Cloud ALM、監視、性能、証明書、BTP連携、運用設計、エスカレーション、経営層向け説明、キャリア価値。
  • 調査日: 2026-04-30 JST
  • 参照方針: SAP公式ページ、SAP Help/Support、SAP Community by SAP、公開SAP契約文書・サービス説明文書を優先。PDF本文は一部Web抽出が難しかったため、検索結果で確認できる文書名・バージョンと、取得可能なSAP公式HTML本文を併用。
  • 個人さん前提: SAP Basis/HANA/RISE、Cloud ALM、Thread Sampling、SQL workload、PlanViz、STRUST/PSE、BTP名前解決・接続、責任分界に強い関心・実務文脈あり。

Findings

1. RISE Private Cloudの本質: 「Basis不要」ではなく「責任分界が変わる」

SAPのCloud ERP Private説明では、SAP Cloud ERP Privateは専用・single-tenant環境で、RISE with SAPがソフトウェア、インフラ、managed servicesを束ね、顧客のクラウド移行を支援するものと説明されている。SAPはshared management modelを掲げ、SAP-managed / customer-managed / jointly managedの3層で責任を分ける。

実務上の読み替えは以下。

領域RISE前オンプレBasisRISE PCE後の顧客側価値
インフラ/OS/DB基盤顧客または運用委託が直接運用SAP/ECS側が多く担う。顧客側はSLA・変更影響・証拠確認・要求管理へ移る
アプリBasisトランスポート、ユーザー、接続、ジョブ、性能、証明書依然残る。むしろSAP側権限がない分、切り分け力と依頼精度が重要
監視CCMS/SolMan/個別監視中心Cloud ALMを中心に業務・統合・ユーザー体感・技術ヘルスを再設計
障害対応自社でログ取得・再起動・パッチ顧客側は業務影響、再現条件、時系列、技術証拠を整理しSAPへエスカレーション
変更管理自社裁量が大きいSAP実行・顧客タイミング決定・共同調整が増える

SAPはSAP-managed responsibilitiesとしてインフラ管理、システム監視、セキュリティ更新を挙げる一方、customer-managed responsibilitiesとしてbusiness process customizationsやbusiness user authorizationsを顧客側に残すと説明している。またmajor initiatives such as ERP upgradesは顧客が業務都合でタイミングを決め、SAPが技術実行する共同管理とされる。

2. 顧客側に残るBasis業務一覧

A. 責任分界・契約・運用要求管理

残る業務:

  • SAP Roles & Responsibilities / Service Description Guide /契約・補足資料の読み解き。
  • 「これはSAP作業か、顧客作業か、共同作業か」を案件・障害・変更ごとに判断。
  • SAP For Me / case / service request / maintenance window / upgrade計画の顧客側統制。
  • SAP標準作業に顧客固有の業務制約、ピーク時間、監査要件を反映。
  • クラウド事業者、SAP ECS、顧客ネットワーク、アプリ運用、業務部門のRACI整理。

高付加価値ポイント:

  • 契約文書を読めるだけでなく、現場のインシデント・変更要求へ翻訳できること。
  • 「SAPに依頼すべき具体作業」「顧客側が先に集めるべき証拠」「SLA/業務影響として主張する材料」を分けられること。

B. Cloud ALM中心の監視・運用設計

SAP Cloud ALMは、SAP landscapeを管理するcentral entry pointで、content-driven guided implementationとhighly automated operationsを提供するnative cloud solutionと説明されている。Enterprise Support等を含むクラウドサブスクリプションに含まれる。SAP Cloud ALM for Operationsは、hybrid/SAP-centric landscape across technologiesの中央入口、monitoring and alerting、process/integration/user/application/cloud service横断のend-to-end visibilityを提供する。

顧客側に残る業務:

  • Cloud ALM導入方針、スコープ、接続、権限、通知先、Alert Inbox運用。
  • Business Process MonitoringのKPI選定、業務部門とのしきい値合意、アラート対応フロー。
  • Integration & Exception MonitoringでIDoc/API/CPI/AIF/連携基盤の監視粒度を決める。
  • Real User MonitoringでFiori/UI5/WebGUI/HTTP/RFC/Dialog等のユーザー体感とバックエンドを結びつける。
  • Health Monitoringで技術メトリクスのトレンド・リソース不足・サービスヘルスを確認。
  • 「監視を入れた」ではなく、誰が何分以内に何を見るか、SAP caseに何を添付するかまで設計。

個人さん向けの勝ち筋:

  • Cloud ALMを単なる監視画面ではなく、業務SLA・性能分析・SAPエスカレーションの証拠基盤として設計する。
  • Thread Sampling/SQL workload/PlanViz/ST03の深掘り分析と、Cloud ALMのユーザー体感・業務KPI・連携エラーを接続する。

C. 性能分析・HANA/ABAP/SAP Gatewayの切り分け

RISEではSAP側が基盤運用を担っても、性能問題の起点は顧客業務・カスタムコード・SQL・バッチ・連携・ユーザー導線に残ることが多い。顧客側Basis/性能コンサルの価値はむしろ上がる。

残る業務:

  • ST03/STAD/SQL Monitor/SQL workload/PlanViz/Thread Sampling等による顧客側根因仮説の作成。
  • Cloud ALM Real User MonitoringのE2E response time、backend/network/client切り分けとABAP/HANA分析の接続。
  • SAPに対するcase起票時、時間帯、ユーザー、トランザクション、SQL hash、スレッド状態、待機、業務影響を整理。
  • 「SAP管理領域の問題」か「顧客アプリ/カスタム/業務処理の問題」かの境界判断。
  • 性能改善ロードマップ: Quick win、カスタムコード修正、ジョブ再配置、HANA統計/SQL設計、業務プロセス変更。

高付加価値ポイント:

  • RISEではOSレベルに直接触れない場面が増えるため、顧客側から見える証拠を最大化する設計が重要。
  • SAPに「遅いです」と投げるのではなく、「何時何分、どの業務、どの要求、どのSQL/待機/コンポーネントで、なぜSAP側調査が必要か」を提示する能力が差別化になる。

D. 証明書・STRUST/PSE・信頼関係

証明書はRISE時代でも顧客側に強く残る。BTP、Cloud Connector、SAP Analytics Cloud、外部API、SAML/OIDC、Principal Propagation、メール、Web Dispatcher/ICM、SSL client/server PSEなど、境界をまたぐ接続では顧客・SAP・外部サービスの共同作業になりやすい。

SAP HelpのCloud Connector手順では、Cloud Connectorのsystem certificateは定期更新が必要で、更新しないと接続が停止する可能性があると明記されている。またABAP側ではTrust Manager（STRUST）でSSL server Standardへ証明書をインポートし、ICMやrule-based certificate mappingを設定する手順が示されている。

残る業務:

  • STRUST/PSEの棚卸し、期限管理、更新手順、CSR/p7b/ルート・中間証明書の管理。
  • SAP側作業依頼と顧客側インポート作業のRACI整理。
  • BTP/Cloud Connector/Principal Propagation/IdP/SAML/OIDCの信頼関係設計。
  • 証明書障害時の切り分け: 期限切れ、チェーン不備、SAN/CN不一致、SNI、TLS version、ICM、proxy、DNS。

個人さん向けの勝ち筋:

  • STRUST/PSEの実務知識は、RISEでも希少価値が高い。これをCloud Connector/BTP/IdP/外部連携まで広げると「接続・認証の事故を未然に防ぐ人」になれる。

E. BTP連携・Cloud Connector・名前解決/ネットワーク

RISEではERPがSAP管理下に移っても、周辺連携は顧客固有で残る。BTP、Integration Suite、Cloud Connector、Private Link/VPN、DNS、IdP、API Management、SAC、外部SaaSとの接続は、顧客側アーキテクトの設計余地が大きい。

SAP HelpのCloud Connector設定では、SAP BTP Cloud Connectorを利用するためにCloud to On-Premise、virtual/internal host mapping、resource path許可、Principal Propagation、X.509証明書などの設定が必要とされる。これはまさにBasis・ネットワーク・セキュリティ・アプリの交差点。

残る業務:

  • 連携方式選定: API、IDoc、RFC、OData、CPI/Integration Suite、Event Mesh等。
  • 名前解決、TLS、プロキシ、Cloud Connector、subaccount、destination、認証方式の設計。
  • Private Cloud ERPとBTP/外部SaaS/オンプレ周辺の通信経路・監視・障害時切り分け。
  • Integration & Exception Monitoringで技術エラーを業務文脈（受注番号、社員ID等）に結びつける。

F. 権限・セキュリティ・監査対応

SAPは顧客側にbusiness user authorizationsが残ると説明している。加えて、SoD、監査証跡、特権ID、外部連携権限、BTP role collection、Cloud ALM権限、証明書・鍵管理などは顧客ガバナンス領域。

残る業務:

  • Fiori/ABAP/BTP/Cloud ALM/IdPをまたぐ権限設計。
  • 監査・内部統制向け説明: 誰が何を承認し、どのログで証明するか。
  • SAP管理領域と顧客管理領域を分けたリスク説明。
  • セキュリティパッチの技術実行はSAP側でも、影響判定・テスト・業務承認は顧客側。

G. 運用設計・エスカレーション・経営層説明

RISE移行後に失敗しやすいのは「SAPが全部やる」と誤解し、顧客側の運用設計を薄くすること。実際には、SAP caseの品質、業務影響の説明、内部合意、リリースタイミング調整、業務部門とのコミュニケーションは顧客側の責任として残る。

残る業務:

  • L1/L2/L3/SAP escalationの運用フロー設計。
  • 重大障害時のwar room運営、時系列、顧客影響、回避策、SAP依頼事項の整理。
  • 経営層向けに「何がSAP責任で、何が顧客判断で、どこにリスクが残るか」を1枚で説明。
  • SLA/SLO、RTO/RPO、メンテナンスウィンドウ、business continuityの説明。
  • Post Incident Reviewで再発防止をCloud ALM監視・証明書期限管理・変更管理へ落とす。

3. 高付加価値コンサル領域

  1. RISE責任分界/RACI診断

契約・R&R・SDG・現行運用を突き合わせ、顧客側に残る作業、SAP依頼作業、共同作業を可視化する。

  1. Cloud ALM運用設計

Business Process / Integration / Real User / Health / Job / Synthetic monitoringを、業務SLAとSAP case証拠に直結させる。

  1. HANA/ABAP性能アドバイザリー

RISE環境で取得可能なデータを前提に、Cloud ALM→ST03/STAD→SQL workload→PlanViz/Thread Samplingへつなぐ分析パターンを標準化する。

  1. 証明書・接続信頼性アセスメント

STRUST/PSE/Cloud Connector/IdP/BTP destination/API証明書の期限・所有者・更新手順・障害時対応を棚卸しする。

  1. BTP連携アーキテクチャレビュー

ERP Private Cloud、BTP、Integration Suite、外部SaaS、顧客ネットワークをまたぐ名前解決、認証、監視、障害切り分けを設計する。

  1. エスカレーション成熟度診断

SAP caseの起票品質、Very High相当時の判断、CIC/サポート連絡、業務影響記述、添付証跡テンプレートを整備する。

  1. 経営層向けRISE運用リスク説明

「クラウド化で何が楽になり、何が残り、何を投資すべきか」をTCO・リスク・SLA・人材価値で説明する。

4. 個人さんへの推奨成長領域

優先度順。

  1. Cloud ALM for Operations 実装・設計力
  • まずBusiness Process Monitoring、Integration & Exception Monitoring、Real User Monitoring、Health Monitoringを一通り触れる。
  • 既存のHANA/ABAP性能分析とつなげ、「Cloud ALMで検知→SAP標準ツールで深掘り→SAP caseへ証拠化」の型を作る。
  1. RISE R&R / SDG読解とRACIテンプレート化
  • SAP公式R&R、Service Description Guide、Trust/Security資料を読み、作業別RACI表を作る。
  • 顧客説明用に「SAPがやること / 顧客がやること / 共同でやること / 誤解しやすいこと」を日本語で整理。
  1. 証明書・BTP Connectivity専門性
  • STRUST/PSEの既存知識をCloud Connector、Principal Propagation、BTP destination、IdP、SAML/OIDC、API証明書へ拡張。
  • 期限管理・更新手順・障害切り分けのチェックリスト化が実務価値大。
  1. 性能分析の「経営翻訳」
  • SQL hashやThread Samplingの分析結果を、業務損失、処理遅延、SLA、顧客影響、改善投資判断へ翻訳する練習。
  • 経営向け1枚資料: 現象、影響、原因仮説、対策、SAP依頼事項、顧客判断事項。
  1. SAPサポート/エスカレーション設計
  • Very High相当の基準、業務影響の書き方、SAP For Me case品質、添付すべきCloud ALM/ST03/HANA証跡をテンプレ化。

5. 90日アクションプラン

0〜30日: 基礎資料と型作り

  • SAP公式R&R/SDG/Cloud ALM資料を読み、1枚のRISE責任分界チャートを作成。
  • Cloud ALMの4監視（Business Process / Integration / Real User / Health）について、目的・入力データ・見る人・アクションを表にする。
  • STRUST/PSE/BTP/Cloud Connectorの証明書期限管理テンプレートを作る。

31〜60日: 実務シナリオ化

  • 「Fioriが遅い」「IDoc連携失敗」「証明書期限切れ」「HANA CPU高騰」「SAP標準パッチ影響」の5ケースで、Cloud ALM→SAP標準ツール→SAP caseの証拠セットを作る。
  • HANA性能分析の既存ノウハウを、RISEで顧客側から取得可能な情報・SAP依頼情報に分解。
  • 顧客説明用RACI表と経営層向けスライド雛形を作る。

61〜90日: 提案メニュー化

  • 「RISE運用成熟度診断」「Cloud ALM監視設計」「証明書/接続リスク診断」「性能問題エスカレーション改善」の4メニューにまとめる。
  • 各メニューについて、目的、成果物、所要日数、入力資料、期待効果、価格感/工数感を定義。
  • 英語版のexecutive summaryとSAP caseテンプレートも作る。

不確実性・注意点

  • SAPのR&R/SDGは契約時期・国・SKU・個別契約・hyperscaler構成で差異があり得る。実案件では必ず対象契約の最新版で確認すること。
  • SAP公式PDFの本文抽出が一部困難だったため、レポートでは取得可能なSAP公式HTML本文と、検索結果で確認できるPDF文書名・バージョンを併用した。
  • Cloud ALMの機能は継続的に拡張されており、監視対象・データ保持・API・自動化機能は時点で変わる可能性がある。
  • RISE環境で顧客側が取得できる技術情報の粒度は、権限、導入構成、SAPサポート契約、セキュリティ制約で変わる。
  • 「顧客側Basisに残る業務」は会社の内製/外注方針、SIer/AMS体制、グローバル運用モデルによって大きく変わる。
